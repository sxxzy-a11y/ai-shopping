# 测试与评测

这个项目有两类验证，回答的问题不同：

- 自动化测试：代码有没有按预期工作；
- 效果评测：推荐结果是否和需求对得上。

两者不能互相替代。1037 条测试通过，不代表推荐一定符合用户预期；41 条评测用例全通过，也不代表系统在真实用户身上同样有效。

## 1. 自动化测试

运行全部测试：

```bash
pytest
```

当前收集到 **1037 条测试，分布在 34 个测试文件**。测试不需要网络，也不需要 API 密钥。

测试隔离由 `tests/conftest.py` 的 autouse 夹具完成：

- 设置文件指向临时目录；
- SQLite 数据库指向临时目录；
- 清除环境中的模型和向量密钥。

因此跑测试不会读写本机真实数据库，也不会消耗 API 额度。`pytest.ini` 把弃用警告提升为失败，避免升级时悄悄积累问题。

### 1.1 覆盖范围

| 范围 | 主要内容 |
|---|---|
| 业务规则 | 需求解析、预算边界、筛选、评分、排序、超预算处理 |
| 数据层 | 商品读写、价格记录、历史快照、收藏、按用户隔离、迁移 |
| 界面 | 用 Streamlit `AppTest` 无头渲染页面、表单交互、登录和访问边界 |
| 知识库 | 语料加载、切分、BM25、向量存储、检索阈值、知识管理 |
| AI | 解析、解释、问答、按路径的价格/参数/排他性校验、超时和失败降级 |
| Agent | 工具参数校验、只读边界、轮次上限、执行轨迹、降级 |
| 权限 | 普通用户 / 管理员页面可见性、数据层写入口校验、账号停用 |
| 端到端 | 完整分析链路、空输入、坏数据、数据库损坏、重复提交 |

常用命令：

```bash
pytest tests/test_recommender.py      # 筛选、评分、排序
pytest tests/test_app.py              # 页面与登录
pytest tests/test_knowledge_search.py # 知识检索
pytest tests/test_agent_tools.py      # 工具参数校验
pytest tests/test_acceptance.py       # 端到端验收
pytest -k "降级"                       # 按关键词筛选
```

### 1.2 不联网的 AI 测试

模型调用在测试里全部打桩，不请求真实接口。测试覆盖这些情况：

- 未配置密钥；
- 超时；
- 认证失败；
- 返回空正文；
- 返回非法 JSON；
- 返回数据中不存在的价格；
- 返回没有依据的参数；
- 返回“销量第一”这类排他性结论；
- Agent 参数不合法、工具返回错误、轮次用尽。

真实接口的连通性不在 `pytest` 里验证，避免测试依赖网络和额度。需要时手动运行：

```bash
python -c "from src import ai_service; print(ai_service.probe())"
```

或在应用内的“个人设置”页测试连接。

### 1.3 界面测试

`tests/test_app.py` 使用 Streamlit 的 `AppTest` 无头运行整个应用，覆盖：

- 未登录时只渲染登录页；
- 登录、注册、登出；
- 页面导航与角色可见性；
- 分析、比较、历史、AI 问答、管理员页面；
- 输入为空、数据加载失败等异常；
- 普通用户不能通过修改页面名进入管理页。

`AppTest` 和真实浏览器仍有差异。样式、CSS 和部分前端交互需要人工检查，不能只靠无头测试。

## 2. 效果评测

评测集在 `data/evaluation/cases.json`，版本 2.0，共 41 条用例。

每条用例包含：

- `id`：用例编号；
- `category`：需求理解、预算边界、不支持的品类、知识检索、语料外反例、比较、幻觉场景、工具调用；
- `origin`：这条用例为什么这样构造；
- `input`：用户输入；
- `expected`：预期结果。

运行：

```bash
python scripts/evaluate.py
python scripts/evaluate.py --only 知识检索
```

### 2.1 自动指标

| 指标 | 计算口径 | 当前结果 |
|---|---|---:|
| 需求理解准确率 | 标注字段逐项比对 | 25/25 |
| 硬性条件满足率 | 设置预算的用例中，推荐商品全部在预算内的比例 | 9/9 |
| 检索质量 | 知识检索用例的命中类型与反例检查 | 17/17 |
| 幻觉场景通过率 | 六类幻觉场景中行为符合预期的比例 | 6/6 |
| 推荐相关性 | 与人工标注的必含 / 必排集合比对 | 9/9 |

### 2.2 人工指标

以下两项没有自动测量：

| 指标 | 为什么不能自动算 |
|---|---|
| 任务完成率 | 需要看用户能否独立完成选购任务，涉及理解、操作和信任 |
| 证据支持率 | 需要人工判断推荐理由中的事实是否真的由资料支持 |

评测报告会把这两项单独列出，不折算进总分。

### 2.3 怎么读 100%

这些用例由项目自己构造和标注，天然偏向系统已有的能力。评测的作用是防止改动让已有能力退步，不是证明系统在真实市场上准确。

更具体地说：

- 41 条用例不是 41 个真实用户；
- 评测集建设过程中发现过缺陷，修复后重跑才全绿；
- 全绿之后再跑同一套题，只能说明没有退步；
- 要发现新问题，需要新增失败场景，而不是反复跑同一套。

## 3. 抗幻觉测试

当前测试覆盖的失败输入包括：

- 商品不存在；
- 商品缺参数；
- 预算低于所有候选；
- 知识库没有资料；
- 商品记录自相矛盾；
- 用户要求没有依据的性能结论；
- 模型返回资料中没有的价格；
- 模型返回“销量第一”“口碑最好”；
- 模型给 Agent 传入不存在的品类或商品 ID；
- 模型调用不存在的工具。

对应行为：

- 价格和排他性结论不通过时，丢弃 AI 文本，保留规则结果；
- 商品不存在或品类不支持时，明确说明，不返回编造结果；
- 缺参数时排除该维度，不补默认分；
- Agent 参数错误时拒绝调用，并把拒绝记入轨迹；
- 上游失败时降级，不展示半成品。

## 4. 测试边界

自动化测试不能覆盖：

- 真实模型输出质量；
- 浏览器里的 CSS 和动画；
- 多人同时访问时的并发；
- 长时间运行后的数据增长；
- 真实用户对推荐理由的理解和信任。

这些需要在比赛演示、人工复核或后续用户研究中验证。比赛材料里不应把自动化测试通过写成“系统没有缺陷”。
