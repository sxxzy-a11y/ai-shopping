### 1.2 测试隔离机制

`tests/conftest.py` 提供 `autouse=True` 的隔离夹具：

| 隔离项 | 做法 |
|---|---|
| 本地设置文件 | `ZHIGOU_SETTINGS_PATH` 指向 `tmp_path` |
| SQLite 数据库 | `ZHIGOU_DB_PATH` 指向 `tmp_path` |
| API 密钥 | `monkeypatch.delenv()` 主动移除 |

**效果**：跑测试不会消耗 API 额度、不会依赖网络、
不会读写你本机真实的数据库与设置文件。

`pytest.ini` 另设 `filterwarnings = error::DeprecationWarning`，
让弃用警告直接变成失败，避免积累技术债。

## 3. 推荐效果评估 📋

> **状态：规划中 —— 尚未建立任何效果评估机制。**

### 3.1 需要准备什么

一份**固定测试集**：**30–50 个代表性消费需求**，
由人工给出合理的预期条件和评价标准，覆盖：

- 不同预算档位
- 不同需求表达方式（完整 / 模糊 / 口语化）
- 商品缺失数据的情况
- 无匹配结果的情况
- 知识库检索情况（RAG 实现后）

### 3.2 五个指标

| 指标 | 定义 | 分母 |
|---|---|---|
| **硬性条件满足率** | 推荐结果中符合全部硬性条件的商品占比 | 推荐商品总数 |
| **推荐相关性** | 人工判断商品与用户需求是否相关 | 推荐商品总数 |
| **证据支持率** | 推荐理由中能由商品资料或知识库支持的事实占比 | 理由中的事实总数 |
| **检索质量** | 相关知识能否被检索到，引用是否准确 | 测试问题总数 |
| **任务完成率** | 用户能否通过系统完成预定的选购任务 | 测试需求总数 |

> ⚠️ **先明确分母、统计口径和人工标注方法，再报告实际测得的结果。**
> **不要在没有运行测试的情况下预先宣称准确率达到 95% 或其他数值。**

### 3.3 建议的实施方式

| 步骤 | 做法 |
|---|---|
| 1 | 把 30–50 个需求写成 JSON/YAML 固定测试集，纳入版本管理 |
| 2 | 写一个评估脚本，批量跑系统并导出结果快照 |
| 3 | 人工按上面五个指标标注，记录到 CSV |
| 4 | 评估脚本汇总生成报告，纳入比赛材料 |

**这个脚本不需要任何新功能**——用现有系统就能跑出指标。
它是当前**投入产出比最高**的待办项。

## 4. AI 幻觉测试

专门准备以下场景，验证系统能拒绝编造信息、明确说明限制，
并在适当情况下询问用户是否放宽条件。

| # | 场景 | 状态 | 现有防线 |
|---|---|---|---|
| 1 | 用户询问数据库中不存在的商品 | ✅ | 无匹配时说明原因 + 放宽建议 |
| 2 | 商品缺少某个参数 | ✅ | 缺失维度排除计算并注明 |
| 3 | 用户预算低于所有候选商品的价格 | ✅ | 无结果处理 + 超预算单列 |
| 4 | 知识库检索不到相关资料 | ✅ | 相关度低于阈值判定为检索不到，不展示任何来源 |
| 5 | 商品资料中出现互相矛盾的描述 | ✅ | `consistency.check_product()` 检测并标「资料存疑」 |
| 6 | 用户要求模型提供没有数据依据的性能结论 | ✅ | 参数数值校验 + 排他性结论校验 |

### 4.1 AI 输出的四道校验 ✅

解读文本生成后依次过四道检查，**任一失败即丢弃该条解读、保留规则算出的结果**。
总述与逐条解读走同一条链，规则详见
[docs/architecture.md §7](architecture.md#7-抗幻觉设计-)。

| # | 检查 | 实现 | 抓的是 |
|---|---|---|---|
| 1 | 价格 | `find_invented_prices()` | 顺口报一个数据里没有的价 |
| 2 | 参数数值 | `find_unsupported_spec_claims()` | 编一个重量、续航或容量 |
| 3 | 排他性结论 | `find_unsupported_claims()` | 「销量第一」「口碑最好」 |
| 4 | 存疑属性 | `find_flagged_claims()` | 就记录内部矛盾的地方下结论 |

配套测试：`tests/test_ai_service.py`（参数化多组用例，正例反例成对）。

**三类容易误杀的表述必须放过**（校验保守性的证据）：

- 「重量约 1.3 千克」← 数据是 1.28 千克，四舍五入不算编造
- 「在本次推荐中排名第一」← 系统**确实**会排序，这是真的
- 「第 1 名，88 分，2026 年」← 裸数字不是参数断言

> 这是本项目「抗幻觉」最具体的工程实现，
> 也是答辩时最值得展开讲的技术点之一。

### 4.2 数据侧的一致性检测 ✅

`src/consistency.py` 在加载时校验商品记录**自身**有没有矛盾——
字段都在、但互相打架。

| 规则 | 判定 |
|---|---|
| R1 档位越界 | tier 类字段不在 1–5 范围内 |
| R2 价格非正 | 价格存在但不是正数 |
| R3 优缺点重复 | 同一条描述同时出现在 pros 与 cons |
| R5 / R6 参数与文字冲突 | `has_dedicated_gpu: false` 却肯定式提独显；`foldable: false` 却肯定式提折叠 |

命中即标「资料存疑」，**但不影响筛选与评分**——数据质量问题不该转嫁成商品劣势。

**硬验收线**：这 6 条规则在现有 112 条商品上**误报为 0**
（`tests/test_consistency.py::test_real_catalog_is_not_flagged`）。
一条不准的规则会把正常商品污名化，比不做更糟。

**规则不是空转的证据**：`test_flag_fires_on_real_text_when_spec_contradicts`
拿真实商品的真实文案，只把参数从「有」改成「没有」，规则必须立刻响——
证明匹配器认得出真实文本里的肯定式提及，而不是碰巧什么都没匹配到。

### 4.2 其他抗幻觉约束 ✅

| 约束 | 落实 |
|---|---|
| AI 不参与排序 | 评分与排序完全由本地规则完成 |
| AI 解读不写入历史 | 报告保存的是规则算出的快照 |
| 缺失参数不当最低分 | 排除该维度并注明，不补默认分 |
| 未知参数不当零 | 比较表标注「信息缺失」，不用其他商品的值填充 |
| 不暴露堆栈 | 领域异常 → 中文文案，堆栈只进日志 |

## 4.5 知识检索回归基线 ✅

固定查询集写在 `tests/test_knowledge_search.py`，**11 条正例 + 4 条反例**。
它不只是「能不能检索到」，还要求**排第一的是正确的那一类**文档——
这是防「通用问题被答成具体商品」的关键。

| 类别 | 例子 | 要求 |
|---|---|---|
| 术语类 | 主动降噪和被动降噪有什么区别 | 排第一为服务级或品类级 |
| 通用选购类 | 通勤戴的耳机怎么选 / 机械键盘选什么轴 | 排第一为品类级 |
| 具体商品类 | 静谷 ANC Pro 怎么样 | 排第一为商品级 |
| 语料外（反例） | 今天天气怎么样 / 怎么给自行车补胎 | **返回空** |

**调参之后跑一遍就知道是变好还是变坏**：改语料、改类型系数、改阈值，
基线是唯一的客观依据。它也是「效果评测」子项目的雏形。

配套的调参记录：商品级系数由实测校准得出（0.55 时 7/8，0.45 时 8/8 + 4/4），
细节见 [architecture.md §8.3](architecture.md#83-两层加权) 与本变更的 tasks.md。

## 4.6 Agent 编排的测试基线 ✅

三个测试文件，各自守一条线：

| 文件 | 守什么 |
|---|---|
| `test_agent_tools.py` | 参数校验真的在拦；工具集只读 |
| `test_agent_runner.py` | 循环受控；轨迹是真的；失败必降级 |
| `test_ai_service.py`（部分） | `tools` 请求体与 `tool_calls` 解析 |

**参数校验的用例覆盖**：不存在的品类、负数与零预算、区间反了、超出比较数量、
编造的商品 ID、未注册的工具名、非法 JSON 参数。每一条都断言**错误说明里
点出了具体原因**——那才是模型下一轮改对的唯一线索。

**循环与轨迹的关键断言**：

- 轮次上限确实生效（构造一直请求工具的桩，断言在第 N 轮停止）
- 轨迹条数 == 实际调用次数（防「往里塞模型的思考文字」）
- 被拒的调用出现在轨迹里且状态为 `rejected`
- 无工具调用时轨迹为空（不是伪造的空步骤）

**降级的关键断言**：上游出错 / 超时 / 超轮次都能降级，且降级后
筛选、评分、排序一个不少——**不允许出现空白结果区**。

> 有一条既有测试因为「Agent 路径下不再调 `explain_recommendations`」而失效。
> 那次改的是**测试而不是代码**——被去掉的行为是设计 D7 有意为之的。

## 4.7 超预算条数如实展示 ✅

一条从真实观察反推出来的缺陷，测试基线钉住三件事：

| 断言 | 防什么 |
|---|---|
| 预算内条数 + 超预算**真实总数** == 候选总数 | 账面对不上（曾经 6 + 6 = 12 ≠ 16） |
| 调小预算内推荐上限，超预算列表条数不变 | 两个上限被合回一个参数 |
| 截断时展示真实总数并说明未列出几件 | 把截断后的长度说成总数 |

**根因值得记一笔**：`recommend()` 里两处共用了同一个 `limit`，而它的文档写的是
「预算内推荐条数上限」。归档的提案、设计、任务里**从没提过超预算列表要限条数**——
不是设计决策，是复用参数带出来的意外后果。界面又把列表长度当总数展示，
把「截断」这件事彻底抹掉了。

> 这类缺陷单元测试不会自己冒出来——它是**看界面时发现数字不对**才查出来的。
> 所以基线里那条「账面必须闭合」的断言最有价值：它把「数字自洽」变成了可自动检查的事。

## 6. 稳定性风险与验证

比赛现场最怕演示时崩。以下风险已识别并有对应验证：

| 风险 | 验证方式 | 状态 |

| 商品文件缺失/损坏 | 模拟删除与写坏 | ✅ 有测试 |
| 历史库损坏 | 模拟损坏文件 | ✅ 有测试 |

> 本项目天然满足：不配密钥时应用以本地演示模式运行，**全部功能可用**。
