## 2. 任务详情

### T1 账号安全加固 P0

**目标**：把演示级账号体系补到「公网短期演示不出事」的水平。

**背景与使用场景**
演示地址对外开放，默认允许自助注册；当前没有登录失败限流，也没有会话过期。
拿到链接的人可以无限次猜密码，离开电脑后登录态一直有效。这两条在演示现场最容易出事。

**具体任务**

- [ ] 登录失败计数：同一用户名 + IP 在 10 分钟内失败 5 次后锁定 15 分钟，返回中文提示与剩余时间
- [ ] 空闲超时：`session_state` 记录最后操作时间，30 分钟无操作自动登出并说明原因
- [ ] 绝对超时：登录后 8 小时强制重新登录，与空闲超时独立生效
- [ ] 失败计数落库（新表 + 迁移），重启不丢失；不记录明文密码，只记用户名、IP、时间

**验收标准**

- 连续 5 次错误密码后第 6 次被拒，提示含剩余锁定时间；等待期满后可正常登录
- 把 `session_state` 的最后操作时间改为 31 分钟前，下一次交互触发登出并保留原页面提示
- 计数在重启后仍生效（用 `scripts/restore_db.py --backup` 前后各测一次）
- 新增测试覆盖：锁定触发、锁定解除、空闲超时、绝对超时；`pytest -q` 全绿

**约束**

- 不改角色模型，权限判定继续留在数据层入口（`require_admin`）
- 不在日志里记录密码、密码哈希或完整 IP，IP 只保留网段
- 迁移必须是「建新表 → 兼容旧库」，旧库缺表时自动补，不要求用户手工操作

### T2 门禁收尾 P0

**目标**：把三项「信息性」检查变成真正的阻断门禁，或明确降级理由。

**背景与使用场景**
CI 已经能跑，但 mypy、coverage、docker、pip-audit 都带 `continue-on-error: true`。
现在的状态是「绿了不代表没问题」，时间一长就会被当成真的通过。

**具体任务**

- [ ] mypy：修掉剩余 13 处（`eval/checks.py` 7 处、页面 `Demand | None` 4 处、`settings` dict 类型 1 处、`analysis` lambda 2 处），转阻断
- [ ] coverage：补出基线数字，先设「不低于当前值」的下限，只升不降
- [ ] docker：确认首次构建结果后去掉 `continue-on-error`
- [ ] pip-audit：确认扫描口径后转阻断；若上游公告导致波动，改为「只对新引入漏洞失败」

**验收标准**

- `.github/workflows/ci.yml` 里 `continue-on-error: true` 全部移除，或在注释里写明保留原因与解除条件
- mypy 0 错误；coverage 报告可读且下限写进配置
- 故意引入一处类型错误 / 格式错误，CI 必须变红（验证门禁真的生效，不是只改配置）

**约束**

- 不为过门禁加 `# type: ignore` 掩盖；确需忽略时必须写明理由
- 全库格式化已完成，不允许再产生新的格式漂移

### T3 商品数据扩充与核验 P1

**目标**：把商品集从「演示够用」提升到「能支撑推荐结论」。

**背景与使用场景**
当前 20 件商品、2 个品类，全部 `unverified`，价格是参考价而非实时价。
用户按推荐买不到对应价格，或品类里只有 10 个候选时，「推荐」这件事的说服力就很弱。

**具体任务**

- [ ] 接入授权数据源，每条保留 `data_source`、`source_url`、采集时间
- [ ] 同一品类内补齐主流型号，目标每个品类 ≥ 30 条
- [ ] 抽样核验价格与关键参数，把 `data_status` 逐步改为 `verified`
- [ ] 参考价与实时价分列，不混用（schema 变更需同步 `tests/test_data_contract.py`）
- [ ] 新品类接入前先补 `config.SCORING_WEIGHTS` 与品牌加权，否则评分会静默跳过

**验收标准**

- `pytest tests/test_data_contract.py` 全绿；新增品类前该测试必须失败，补完权重后才通过
- 每个品类 ≥ 30 条，`verified` 占比 ≥ 50%
- `python -m eval.runner` 指标不低于当前基线，且失败用例只增不减（保留真实失败）

**约束**

- 不用爬虫抓未授权数据；不伪造 `verified`
- 数据变多后必须复跑评测，不能只换数据不更新结论

### T4 评测真实性 P1

**目标**：把「自建回归集」和「用户能否完成」区分开。

**背景与使用场景**
41 条用例由本项目构造并标注，天然偏向已有能力。全绿只能说明「没退化」，不能说明「好用」。
任务完成率与证据支持率至今没有人工测量。

**具体任务**

- [ ] 写一份统一任务脚本（3–5 个任务，每个含起点、期望结果、判定口径）
- [ ] 找 3 位不参与开发的人按脚本试用，记录完成率与卡点
- [ ] 补充真实用户问法，替换部分「项目已知能答」的用例
- [ ] 对推荐理由做证据支持率人工复核，结果写进 `docs/eval-report.md`

**验收标准**

- `docs/eval-report.md` 出现「任务完成率」与「证据支持率」两个实测值，附样本量与判定口径
- 评测集新增用例来自真实提问，`origin` 字段可追溯
- 失败用例保留；报告里能区分「自动指标」与「人工指标」

**约束**

- 不合成总分，不把主观判断写成测量结果
- 不为了让报告好看而删失败用例

### T5 持久化与接口 P2

**目标**：为多实例与外部调用做准备。**当前不是瓶颈，等 T1–T4 完成后再动。**

**背景与使用场景**
Streamlit Cloud 的文件系统是临时的，SQLite 不适合多实例并发写；现在是单实例演示，
多用户并发写、容器重启都会丢数据。第三方系统也无法直接调用推荐能力。

**具体任务**

- [ ] 换 PostgreSQL 或 MySQL；`src/database.py` 的 SQL 与迁移脚本同步
- [ ] 补完整迁移 + 备份 + 恢复演练（`scripts/restore_db.py` 已具备基础能力，需适配新库）
- [ ] 多用户场景补连接池与事务边界
- [ ] 按需抽 FastAPI：商品、推荐、比较、知识检索四个稳定接口

**验收标准**

- 迁移可从旧 SQLite 平滑升级，失败可回滚（用 `restore_db.py` 演练一次）
- 两个实例并发写不冲突；重启后数据完整
- 接口有 OpenAPI 文档与至少一条端到端测试

**约束**

- 不引入 ORM；不为了「看起来更大」拆微服务
- 接口不是当前瓶颈，先做完 T1–T4 再拆服务，返工更少

## 3. 开发方式

项目用 OpenSpec 记录需求与变更，每次改动按这个顺序走：

1. 在 `openspec/changes/` 建变更目录，写 `proposal.md`（改什么、不改什么）与 `tasks.md`（可勾选任务）；
2. 影响既有能力时补 delta spec，不直接改 `openspec/specs/`；
3. 一次只推进一个变更，每组改动跑相关测试；
4. 完成后归档到 `openspec/changes/archive/`，并同步 README 的功能表、测试数与本文件第 0 节基线。

这不是为了加流程，而是因为项目里有多条互相影响的约束（预算过滤、评分权重、AI 校验、权限边界）：
没有记录，改一处很容易把另一处弄坏。

## 4. 明确不做

- 支付、订单、购物车、物流和售后；
- 库存和履约；
- 电商平台实时爬虫；
- 真实用户评价和销量数据；
- 多商家入驻和复杂运营后台；
- 多租户和细粒度权限；
- 为「看起来更大」而增加没有数据支撑的品类；
- 引入 LangChain / 独立向量库 / 前后端分离 / 微服务（`openspec/project.md` 已定「架构债不还」）；
- 接入 Anthropic SDK（已评估：Anthropic 无 embedding 接口，换模型对推荐结果无实质提升，详见 `项目全面检查报告.md`）。

当前版本的目标是把一条决策链路做完整、做可检查。功能数量不是优先级。
