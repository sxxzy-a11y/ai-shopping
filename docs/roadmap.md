## 当前最需要补的

### 1. 商品数据

当前只有 20 件商品、2 个品类，且全部未逐条核验。比赛演示够用，但不足以覆盖真实购物需求。

下一步：

- 接入授权商品数据源，保留来源、采集时间和许可说明；
- 增加商品数量，优先补同一品类内的主流型号；
- 对价格和关键参数做抽样核验，逐步把 `data_status` 从 `unverified` 改为 `verified`；
- 把“参考价”和“实时价”分开，不混用。

### 2. 评测

41 条用例是自建回归集，不是用户研究。任务完成率和证据支持率还没有人工测量。

下一步：

- 找不参与开发的人按统一任务脚本试用，记录完成率和卡点；
- 增加真实用户问题，而不是只写项目已知能答的问题；
- 对推荐理由做证据支持率人工复核；
- 保留失败用例，不为了让报告好看而删掉。

### 3. 持久化与并发

Streamlit Cloud 的文件系统是临时的，SQLite 也不适合多实例并发写。当前只适合单实例演示。

下一步：

- 换 PostgreSQL 或 MySQL；
- 补迁移、备份和恢复流程；
- 为多用户场景增加连接池和事务边界；
- 部署时只跑一个写实例，读写分离再做。

### 4. 账号与安全

当前账号体系是演示级，没有登录限流、会话过期和找回密码。

下一步：

- 加登录限流和失败锁定；
- 用服务端会话或安全 Cookie 替代仅存在 `session_state` 的登录态；
- 补 CSRF 防护和安全响应头；
- 管理端加独立访问控制；
- 公开部署前做一次安全审查。

### 5. 接口与扩展

当前是 Streamlit 单体，没有 HTTP API。业务逻辑与界面已经分离，但第三方系统无法直接调用。

下一步：

- 按需抽出 FastAPI 接口；
- 把商品、推荐、比较、知识检索做成稳定服务；
- 再考虑更多品类和前端重写。

接口不是当前瓶颈。先把数据和评测做好，再拆服务，返工更少。

## 开发方式

项目使用 OpenSpec 记录需求和变更，每次改动尽量做到：

- 先写清楚要改什么、不做什么；
- 一次只推进一个变更；
- 每组改动跑相关测试；
- 完成后归档规格，不让文档和代码各说一套。

这不是为了增加流程，而是因为项目里有多条容易互相影响的约束：预算过滤、评分权重、AI 校验、权限边界。没有记录，改一处很容易把另一处弄坏。

## 明确不做

- 支付、订单、购物车、物流和售后；
- 库存和履约；
- 电商平台实时爬虫；
- 真实用户评价和销量数据；
- 多商家入驻和复杂运营后台；
- 多租户和细粒度权限；
- 为了“看起来更大”而增加没有数据支撑的品类。

当前版本的目标是把一条决策链路做完整、做可检查。功能数量不是优先级。
