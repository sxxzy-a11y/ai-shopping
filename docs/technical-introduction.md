## 0. 一页纸摘要

智购参谋是一个面向 3C 选购的单进程 Web 应用。它把一句口语化需求拆成结构化条件，在本地商品库中筛选、按需求匹配度打分排序，再用知识库和受控的 AI 工具补充解释与问答。它不承接交易，也不假装是实时比价平台。

一句话架构：

```text
Streamlit 界面（可替换）
        │ 直接函数调用
确定性内核：解析 → 筛选 → 评分 → 排序 → 比较 → 报告
        │ 可选外挂
AI 增强：需求解析 / 知识问答 / 只读 Agent 编排
        │
SQLite：商品库 + 历史库（两个文件）+ 知识语料（Markdown）
```

| 维度 | 当前事实 |
|---|---|
| 语言与框架 | Python 3.10+，Streamlit 1.51（界面） |
| 数据 | SQLite（stdlib `sqlite3`）、`data/products.json` 仅作种子 |
| 结构化校验 | pydantic 2.x（商品、需求、账号、工具参数） |
| 模型调用 | `httpx` 直连 OpenAI 兼容接口，不依赖厂商 SDK |
| 商品数据 | 20 件，2 个品类（笔记本 10 / 手机 10），13 个品牌，参考价 1499–11199 元 |
| 知识语料 | 3 份手写文档 + 20 条商品级合成条目；当前切出 38 个切片 |
| 评分 | 5 个维度、按品类加权，权重和为 1 |
| 检索 | BM25（默认）/ 可选向量检索，阈值 + 相对截断，最多 3 条 |
| Agent | 4 个只读工具，最多 5 轮，全程记录执行轨迹 |
| 测试 | 38 个 `test_*.py`；实测收集 1084 条（含参数化展开） |
| 评测 | 41 条自建用例，本次重跑 41/41 通过 |
| 运行依赖 | streamlit、pandas、pydantic、httpx、numpy（+ pytest 开发依赖） |

## 1. 项目定位

### 1.1 要解决的三个问题

1. **需求说不清**：用户知道“2000 元、拍照”，但不知道哪些参数与拍照有关。
2. **参数口径不一致**：不同品牌的写法不同，横向比较成本高。
3. **模型会编**：通用大模型能聊，但价格、参数、口碑经常说得像真的，实际没有数据依据。

项目的回答方式是：把“理解”和“判断”拆开。需求理解可以用模型，商品事实、筛选和排序必须由本地数据与规则完成。

### 1.2 做什么，不做什么

| 做 | 不做 |
|---|---|
| 自然语言 → 结构化需求 | 支付、订单、购物车、物流 |
| 预算内筛选与超预算提示 | 实时价格、库存、销量、真实评价 |
| 可解释的匹配评分 | 全网比价或平台爬虫 |
| 同品类 2–5 件横向比较 | 跨品类“性价比”比较 |
| 知识库问答与只读 Agent | 让模型执行 SQL 或修改数据 |
| 报告快照与 Markdown/CSV 导出 | 多租户、细粒度权限、生产级鉴权 |

### 1.3 为什么只有两个品类

商品库只保留笔记本电脑和手机各 10 件。这是有意的收缩：这两个品类的参数可以横向比较，20 条数据也能逐条说明来源。摊到十个品类、每类两三条，参数可比性和解释力都会垮掉。用户提到表外品类（平板、相机、冰箱等）时，系统明确回答“暂不支持”，而不是跨品类乱推。

## 2. 技术栈与总体架构

### 2.1 技术栈

| 层 | 选型 | 用途与理由 |
|---|---|---|
| 界面 | Streamlit | 单进程、无前后端联调，适合演示与快速迭代 |
| 业务 | 纯 Python | 不依赖 Streamlit，可直接单测；未来可搬进 FastAPI |
| 数据 | SQLite | 零运维、单文件、事务可靠；适合单实例演示 |
| 校验 | pydantic | 模型字段、需求对象、工具参数共用一套声明 |
| 表格 | pandas | **只用于界面渲染**（比较表、管理页切片表） |
| 模型 | httpx | 标准 HTTP 直连，换服务商只改 base_url |
| 向量 | numpy | 百级切片的暴力余弦检索，毫秒级，无需外部向量库 |

运行时实际安装版本（本机复核）：Streamlit 1.51.0、pandas 2.3.3、pydantic 2.12.4、httpx 0.28.1、numpy 2.3.5。

### 2.2 运行时拓扑

```text
浏览器
  │ HTTPS
  ▼
Streamlit 进程 ── 页面脚本每次交互从头重跑
  │
  ├── src/ui/           页面、组件、主题、会话状态
  │
  ├── src/              业务模块（无 Streamlit 依赖）
  │     ├── demand_parser / scoring / recommender / comparison
  │     ├── report_service / settings / catalog_meta
  │     ├── ai_service / ai_enhance
  │     ├── knowledge/  corpus → chunking → BM25 / vector
  │     └── agent/      registry → tools → runner
  │
  ├── storage/products.db   商品、价格、分类/品牌元数据
  ├── storage/zhigou.db     账号、历史、收藏、偏好、向量
  └── data/knowledge/*.md   知识语料（可 diff、可回滚）
        │
        └── 可选外部服务：对话模型、Embedding 服务
```

### 2.3 分层与依赖方向

| 位置 | 职责 | 依赖 Streamlit |
|---|---|---|
| `app.py` | 页面配置、登录入口、导航、数据加载、异常兜底 | 是 |
| `src/ui/` | 页面、组件、主题、会话状态 | 是 |
| `src/*.py` | 解析、评分、筛选、比较、报告、AI、存储 | 否 |
| `src/knowledge/` | 语料、切片、BM25、向量库、检索调度 | 否 |
| `src/agent/` | 工具注册、参数校验、编排循环、轨迹 | 否 |
| `data/`、`scripts/`、`tests/` | 种子数据、数据脚本、自动化测试 | 否 |

依赖规则只有一条：**业务层不 import Streamlit**。因此 `pytest` 能直接调用评分、筛选和检索，不必启动界面；`app.py` 也不写业务规则，只做编排。

### 2.5 一次分析的完整调用链

```text
用户输入（自然语言 + 可选结构化控件）
  │
  ├─ 空输入 / 不支持的品类 ──► 直接拒绝并说明
  │
  ▼
parse_demand() 或 parse_demand_with_ai()
  │     失败 → 回退规则解析，并在界面说明
  ▼
merge_demand()  结构化控件覆盖 / 补齐 / 列表取并集
  │
  ├─ 缺类别或预算 ──► 定向追问，不进入筛选
  │
  ▼
settings.apply_preferences()   只补空缺，不覆盖当次输入
  │
  ▼
recommend()
  │  可见性过滤 → 类别/品牌/硬性条件过滤 → 逐件评分 → 预算分组 → 排序
  │
  ├─► Agent（可选）：只读工具编排，生成解释与轨迹
  ├─► comparison（另一页面）：同品类多商品差异
  └─► build_report()：评分快照 + 待核实项 + 结论
        │
        ▼
database.save_analysis()  按 (user_id, signature) 去重
```

### 2.6 两种运行模式

| 模式 | 触发条件 | 行为 |
|---|---|---|
| 本地演示模式 | 未配置 `ZHIGOU_LLM_API_KEY` | 解析、评分、筛选、比较、报告全部可用；AI 问答不可用并说明如何配置 |
| AI 增强模式 | 已配置密钥，且个人设置里 AI 开关打开 | 需求解析优先走模型；分析页在有预算内候选时进入 Agent；问答走知识库/商品库 |

判定只有一个出处：`state.ai_enhanced_active()`（个人偏好 + 密钥）。侧栏、分析页、问答页都读它，避免三处口径漂移。

## 3. 八条设计原则

| # | 原则 | 在代码中的落点 | 代价 / 边界 |
|---|---|---|---|
| 1 | **事实与语言分离** | 分数、排序、候选集合由 `scoring`/`recommender` 决定；AI 只写解释 | Agent 最终文本不参与事实校验 |
| 2 | **缺失即缺失** | `Product.missing_fields` 派生；评分的 `excluded`；不补 0 分/平均分 | 有的商品只按部分维度得分 |
| 3 | **结论可追溯** | `DimensionScore.reason`、加减分项、报告快照、来源与核验状态 | 文案与快照存储成本更高 |
| 4 | **降级是常态路径** | 无密钥 → 本地模式；向量失败 → BM25；Agent 失败 → 确定性管道 | 两条路径都要分别测试 |
| 5 | **边界写进入口** | 工具集无写操作；注册表拒绝未注册工具；数据层 `require_admin` | 无法做多步写操作 |
| 6 | **数据最小化** | `users` 表只有 5 列；日志脱敏；数据出境告知 | 无法做用户画像式个性化 |
| 7 | **快照优先** | 报告存 JSON 快照，不按当前数据重算 | 存储增长，不能“实时刷新历史” |
| 8 | **单进程优先** | Streamlit + SQLite，无 HTTP API | 不能水平扩展，不能第三方集成 |

这些原则不是装饰：第 2、4、5 条分别对应“不猜数据”“演示现场断网”“模型不能改库”三个真实风险。

## 4. 数据层

### 4.1 Product 模型

`src/data_loader.py` 的 `Product` 覆盖商品主表字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | str | 主键，如 `LP001` / `PH004` |
| `name` / `brand` / `model` | str | 型号可空（部分品类本来没有型号） |
| `category` | str | 类别键，必须与 `config.CATEGORY_LABELS` 对齐 |
| `price` | float? | 参考价；空值表示“没有价格”，不默认符合预算 |
| `specs` | dict | 参数异构，按品类存不同键 |
| `use_cases` / `pros` / `cons` | list[str] | 场景、优点、缺点 |
| `data_source` / `source_url` | str | 来源说明与原始链接 |
| `data_status` | str | `verified` / `unverified`，默认未核验 |
| `is_active` | bool | 下架商品不参与推荐，但历史仍可读 |
| `image_url` | str | 外链，失败时界面回落品类图标 |
| `entered_by` / `entered_at` | str | 仅界面录入的商品有值 |
| `price_source` / `price_collected_at` | str | 来自价格记录 |

所有业务字段都允许为空。空值代表“数据里没有”，不是“取默认值”。`missing_fields` 是**派生属性**，随字段变化实时计算——存下来的列表会在数据被改动后失效。

### 4.2 加载与容错

```text
products.db 为空？
  ├─ 是 → 导入 data/products.json（仅此一次）
  └─ 否 → 直接读库，不覆盖用户录入
        │
        ▼
逐条转换（宽容）：类型不对 → 安全值；无 id → 整条跳过并记 issue
        │
        ▼
Catalog（商品集合 + 数据集元信息 + 加载问题）
```

单个坏记录不会让整个应用失效：它变成“信息不完整商品”继续参与流程，缺失维度在评分时被排除，界面与导出注明“信息缺失”。

### 4.3 缺失与矛盾是两类问题

| 问题 | 判定 | 表现 |
|---|---|---|
| 字段缺失 | `missing_fields`：必填字段为空 | “信息缺失”，对应评分维度不参与 |
| 记录矛盾 | `consistency.check_product()`：字段都在但互相打架 | “资料存疑”，不排除商品，提醒核实 |

一致性规则只有 4 条，且都经过全量数据零误报校验：

| 规则 | 检查 |
|---|---|
| R1 | `_tier` 类字段取值必须在 1–5 |
| R2 | 价格存在时必须是正数 |
| R3 | 同一条描述不能同时出现在优点和缺点里 |
| R4 | 参数写“不支持独显”，描述却肯定地说支持 |

文本规则做**否定感知**：关键词前 3 个字符内出现“无/不/非/没/未/缺”等否定词时，不算肯定陈述。否则“无独显”这类正确写法会被误判成矛盾。规则宁可漏放，不可误杀——错误标记正常商品比不标记更糟。

### 4.4 数据集现状

| 指标 | 值 |
|---|---:|
| 商品数 | 20 |
| 品类 | 2（笔记本 10 / 手机 10） |
| 品牌 | 13 |
| 参考价区间 | 1499–11199 元 |
| 笔记本价格区间 | 3519–11199 元 |
| 手机价格区间 | 1499–5399 元 |
| 已核验记录 | 0（全部 `unverified`） |
| 含 `source_url` | 20 |

品牌与型号真实存在，价格是按公开资料整理的参考价，不是实时价格；处理器/拍照档位是 1–5 级简化刻度，不是厂商跑分。数据集不含销量、用户评价、库存、保修与售后信息。

### 4.5 价格单独成表

`product_prices` 记录价格、币种、来源说明、采集时间、核验时间与 `is_current`。写入逻辑：

- 价格**变了**才插入新行，并把旧行 `is_current` 置 0；
- 价格没变只更新当前行的来源与采集时间，不制造无意义历史；
- 没有价格就不写价格记录，商品价格视为缺失。

这样“当前价”可取 `is_current=1` 的那条，同时保留价格变更轨迹。它解决的是“价格只是一个无来源、无时效的孤立数值”的问题。

### 4.6 可见性过滤

`catalog_meta.visible_catalog()` 在推荐入口统一摘掉三类商品：

1. 商品自身 `is_active = 0`；
2. 所属分类被停用；
3. 品牌被停用。

它返回**副本**，不改原 `Catalog`：`Catalog` 要如实反映数据里有什么，过滤只影响“谁参与推荐”。历史记录里的引用不受影响——下架不等于删除。

## 5. 需求解析

### 5.1 Demand 模型

| 字段 | 含义 | 空值语义 |
|---|---|---|
| `raw_text` | 用户原文 | 空串 |
| `category` | `laptop` / `phone` | 未指定 |
| `budget` | 总预算（元） | 未设定 |
| `use_cases` | 使用场景 | 未提供 |
| `core_needs` | 核心需求 | 未提供 |
| `compromises` | 可妥协项 | 未说明 |
| `brand_preferences` | 品牌偏好 | 未限定 |
| `hard_constraints` | 硬性条件 | 无 |
| `source` | `structured` / `rule` / `ai` / `merged` | — |

关键字段只有类别与预算：没有类别无法确定候选范围，没有预算无法判断匹配度。缺这两项时只追问缺失项，不进入筛选。

### 5.2 规则解析流水线

```text
原文 → lower
  ├─ _extract_category      关键词命中，表顺序决定优先级（笔记本优先）
  ├─ _extract_budget        见 5.3
  ├─ _match_keywords        用途表、核心需求表
  ├─ _extract_brands        拿数据集里的真实品牌匹配，不硬编码
  ├─ _extract_compromises   “可以重一点”“不介意”等让步标记
  └─ _extract_hard_constraints  只在“必须/一定要”等强制词后 8 字内找
```

“必须 X”只在强制语气词后识别，避免把“我不介意没有降噪”里的“降噪”误判成硬性要求。

### 5.3 预算识别

按优先级依次尝试：

| 优先级 | 模式 | 例子 | 结果 |
|---:|---|---|---|
| 1 | 区间 | `3000-4000` | 取右端 4000（预算上限） |
| 2 | 上下文词 + 数字 | `预算 3000`、`不超过五千` | 3000 / 5000 |
| 3 | 数字 + 货币单位 | `3000 元`、`三千块` | 3000 |
| 4 | 兜底：3–6 位数字且在 100–200000 | `想花 2500` | 2500 |

细节与边界：

- 支持阿拉伯数字和中文数字（十/百/千/万），`两千五百` = 2500；
- **口语省略式拒绝猜测**：`两千五` 可能是 2500，也可能被读成 2005，系统返回“未识别”，交给界面追问；
- `两千零五`、`十五` 仍能正确解析；
- 负数（`-100`、`负100`）抛 `InvalidBudget`，不静默当正数；
- 兜底只认 3–6 位数字，避免把“14 寸”“5.3 蓝牙”当预算；
- 结构化预算字段**只接受阿拉伯数字**，可带“元/块/rmb/人民币”后缀；格式不对报错，而不是当成没填。

### 5.4 词表驱动

用途、核心需求、类别都来自集中词表，且界面控件选项与解析器识别词共用同一组常量：

- 用途：编程、学习、办公、游戏、影音、通勤、视频剪辑、三维渲染、运动、拍照、图书馆、长途、录音、上网等；
- 核心需求：性能、性价比、续航、便携、拍照、静音、耐用、省电、容量、舒适、透气、安全等；
- 场景同义词在评分层归一：`写代码/敲代码/开发 → 编程`，`摄影 → 拍照`，`出差 → 长途`。

不支持的品类单独一张表，并按**字符串长度倒序**匹配：否则“婴儿车”会被“婴儿”截胡，“电动牙刷”会被“牙刷”截胡。命中后返回“暂不支持 X，目前只包含笔记本与手机”，而不是当成没提类别跨品类推荐。

### 5.5 AI 解析

`parse_demand_with_ai()` 要求模型只输出 JSON，字段与规则版一致。模型输出一律当不可信输入，由 `demand_from_payload()` 做白名单清洗：

| 字段 | 清洗规则 |
|---|---|
| `category` | 必须命中 `laptop` / `phone`，否则置空 |
| `budget` | 必须是正数；字符串数字可接受，其余丢弃 |
| `use_cases` / `core_needs` | 必须落在既有词表内，表外词丢弃 |
| `hard_constraints` | 必须落在允许集合内 |
| `brand_preferences` / `compromises` | 自由文本，去重、截断、限量 |

采纳表外词没有意义：下游匹配不上商品数据，只会让用户看到“命中 0/N”的假象。模型失败时回退规则解析，并把失败原因写进界面提示，不静默降级。

### 5.6 结构化与自然语言的合并

`merge_demand()` 的规则：

| 字段类型 | 规则 |
|---|---|
| 标量（类别） | 结构化控件有值则覆盖解析结果 |
| 预算 | 结构化值非 `None` 时优先 |
| 列表（用途/需求/让步/品牌/限制） | 取并集，去重保序，结构化在前 |
| `source` | 变为 `merged` |

用户当次明确填写的条件优先于偏好默认值；`settings.apply_preferences()` 也只补空缺，不覆盖当次输入。

## 6. 评分

### 6.1 总公式

```text
total = Σ(score_i × weight_i) / Σ(weight_i)
```

分母是**实际参与计算**的维度权重和。缺失维度不会补 0 分，而是从分母中剔除后重新归一化。

### 6.2 权重

| 维度 | 笔记本电脑 | 手机 |
|---|---:|---:|
| 预算匹配 `budget_fit` | 0.25 | 0.25 |
| 核心需求匹配 `need_fit` | 0.25 | 0.30 |
| 性能功能适配 `performance_fit` | 0.25 | 0.25 |
| 性价比 `value` | 0.15 | 0.10 |
| 便携性 `portability` | 0.10 | 0.10 |
| 合计 | 1.00 | 1.00 |

手机更看重“需求对得上”，笔记本更看重预算与性能。权重集中在 `src/config.py`，测试断言每个品类权重和为 1。界面新增的分类没有专属权重时使用默认表（预算 0.25、需求 0.35、性能 0.20、性价比 0.20，不含便携），避免新分类总分恒为 0。

### 6.3 归一化

参数先线性映射到 0–100，超出端点截断：

```text
scaled = clamp((value - at_zero) / (at_hundred - at_zero) × 100, 0, 100)
```

区间定义（也是商品维护页的取值校验来源）：

| 品类 | 参数 | 0 分端 | 100 分端 |
|---|---|---:|---:|
| laptop | `cpu_tier` | 1 | 5 |
| laptop | `ram_gb` | 8 | 32 |
| laptop | `battery_h` | 4 | 12 |
| laptop | `weight_kg` | 2.5 | 1.0（越小越好） |
| phone | `chip_tier` | 1 | 5 |
| phone | `camera_tier` | 1 | 5 |
| phone | `battery_mah` | 4000 | 6000 |
| phone | `weight_g` | 230 | 160（越小越好） |

### 6.4 五个维度

**预算匹配**

```text
ratio = price / budget
ratio ≤ 1  → 70 + 30 × ratio        # 用满预算 100，占用越少分越低
ratio > 1  → max(0, 100 − 400 × (ratio − 1))   # 每超 1% 扣 4 分，超 25% 归零
```

预算内从 70 分起步而不是从 0 起步：价格远低于预算通常说明选型没有用足预算，但不等于“更差”。

**核心需求匹配**

由两部分取平均：

1. 使用场景重合度：`|需求场景 ∩ 商品场景| / |需求场景| × 100`；
2. 核心需求里可量化部分的平均分。

可量化信号：

| 核心需求 | 读取参数 |
|---|---|
| 性能 | `cpu_tier` / `chip_tier` / `ram_gb` |
| 续航 | `battery_h` / `battery_mah` |
| 便携 / 轻便 | `weight_kg` / `weight_g` |
| 拍照 | `camera_tier` |

无法量化的需求（如“性价比”）不计入分母，并单独说明“由对应维度衡量”，避免出现“命中 2/3 但其实只评估了 2 项”的误导。

**性能功能适配**：该品类性能参数归一化后的平均值。笔记本看 `cpu_tier` + `ram_gb`，手机看 `chip_tier` + `camera_tier`。

**性价比**：同品类内“性能排位”与“价格排位”之差：

```text
price_rank      = 价格 ≤ 本品价格的商品占比 × 100
capability_rank = 性能 ≤ 本品性能的商品占比 × 100
score = clamp(50 + (capability_rank − price_rank) × 0.8, 0, 100)
```

性能排位明显高于价格排位（性能不错、价格不高）时得分高。它是**同类别相对位置**，不是市场性价比。

**便携性**：重量归一化。`weight_kg` 优先，否则 `weight_g`；没有重量数据则排除该维度。

### 6.5 解释与加减分

- 每个维度返回 `DimensionScore(key, score, weight, reason)`；
- 加分项取分最高的两个维度，扣分项取最低的两个；
- 排序键是 `(-score, key)`，保证并列时 `bonus[0]` 恒为最高分维度；
- 档位：≥85 高度匹配、≥70 较为匹配、≥55 基本可用，其余“匹配度较低”。

### 6.6 实例演算：真我 GT Neo6 SE（PH004）

输入“2000 元以内的手机，主要拍照”，规则解析得到：类别 phone、预算 2000、用途 `[拍照]`、核心需求 `[]`。

| 维度 | 得分 | 依据 |
|---|---:|---|
| 预算匹配 | 98.5 | 1899 / 2000 = 0.9495 → 70 + 30 × 0.9495 |
| 核心需求匹配 | 100.0 | 商品场景含“拍照”，用途命中 1/1 |
| 性能功能适配 | 62.5 | `chip_tier` 4 → 75；`camera_tier` 3 → 50；平均 62.5 |
| 性价比 | 58.0 | 同品类价格/性能排位差 |
| 便携性 | 55.7 | 191g → (230 − 191) / (230 − 160) × 100 |

```text
0.25×98.5 + 0.30×100 + 0.25×62.5 + 0.10×58.0 + 0.10×55.7
= 24.63 + 30.00 + 15.63 + 5.80 + 5.57
= 81.62 → 81.6
```

注意这里“拍照”是通过**用途命中**拿到的 100 分；`camera_tier` 3 只贡献 50 分。若用户写“拍照好/相机好/镜头好”，它会进入核心需求，走 `camera_tier` 路径。同一个词在两条路径上的量纲不同，这是当前实现的细节，也是数据标注（商品 `use_cases`）会影响结果的原因。

### 6.7 同一预算、三种需求

实测（2026-10-27，当前数据）：

| 排名 | 拍照优先 | 续航优先 | 便携优先 |
|---:|---|---|---|
| 1 | 真我 GT Neo6 SE 1899 · 81.6 | iQOO Z9 Turbo 1799 · 81.5 | 荣耀 X70 1599 · 62.2 |
| 2 | iQOO Z9 Turbo 1799 · 51.5 | 红米 Turbo 4 1499 · 80.7 | 真我 GT Neo6 SE 1899 · 60.0 |
| 3 | 红米 Turbo 4 1499 · 50.7 | 真我 GT Neo6 SE 1899 · 77.9 | iQOO Z9 Turbo 1799 · 59.0 |

三组输入预算相同，第一名不同。这不是“榜单不稳定”，而是设计目标：分数衡量的是“与这次需求的匹配度”。

## 7. 筛选、排序与推荐

### 7.1 流程

```text
visible_catalog（下架/停用过滤）
  → 类别过滤
  → 品牌偏好过滤
  → 硬性条件过滤
  → 逐件评分（5 维）
  → 预算内 / 超预算分组
  → 按 (-总分, 价格) 排序
  → 截断展示（预算内 limit，超预算独立上限）
```

### 7.2 各类条件的真实语义

| 条件 | 实现 | 不满足时 |
|---|---|---|
| 类别 | 精确匹配 `catalog.by_category` | 候选为空，给出类别提示 |
| 品牌偏好 | 精确匹配品牌名 | 候选为空，建议放宽品牌；**不悄悄退回全部商品** |
| 硬性条件 | 目前只识别“独显/独立显卡” | 可识别但缺参数 → 判为不满足；不可识别 → 不参与筛选，只记提示 |
| 预算 | **不是硬过滤**：切成预算内/超预算两组 | 超预算商品单列并写明超出金额 |

关于预算需要说明：`README` 和 `requirements` 的表述容易让人以为预算是硬性过滤，实际实现是“分区 + 评分”。这样用户能看到“再加多少钱能买到什么”，同时超预算商品不会混进预算内列表。文档口径与代码行为之间的这处措辞差异，建议后续统一。

### 7.3 截断与真实数量

| 字段 | 含义 |
|---|---|
| `within_budget_total` | 预算内商品真实条数（截断前） |
| `over_budget_total` | 超预算商品真实条数（截断前） |
| `within_budget_hidden` | 预算内未展示条数 |
| `over_budget_hidden` | 超预算未展示条数 |

预算内默认最多 6 条，超预算最多 10 条，两个上限相互独立。界面与报告一律用 `*_total` 报数，不用 `len(list)`——截断后长度不再等于总数。

### 7.4 无结果时的放宽建议

`_build_relaxations()` 只给**具体可执行**的建议，按触发条件生成：

1. 预算低于该品类最低价 → 写出最低价商品与“提高到多少”；
2. 品牌偏好筛空 → 列出该品类可选品牌；
3. 硬性条件组合过严 → 建议逐条去掉定位是哪一条；
4. 类别在数据里不存在 → 列出实际可用类别；
5. 以上都不适用 → 通用建议（提高预算/放宽条件/换类别）。

“没有匹配”不等于“市场上没有合适商品”，报告里会明确这一点。

### 7.5 预算张力提示

如果预算内首选的总分低于某件超预算商品，系统会在说明里写出：

> 预算内首选 X 的匹配评分为 A，低于超预算的 Y（B 分，超出 N 元）。若预算可上浮，后者更贴合你的需求。

这正是产品存在的主要理由之一：用户被预算框住时，最该知道的是“多花多少能买到明显更合适的”。

### 7.6 结果对象

`RecommendationItem` = 商品 + 评分 + 是否预算内 + 超出金额 + 是否设定预算；`RecommendationResult` 额外携带候选数、真实总数、隐藏数、过程说明与放宽建议。`best` 属性预算内优先，没有预算内才退回超预算最优。

## 8. 商品比较

| 约束 | 值 |
|---|---|
| 最少件数 | 2 |
| 最多件数 | 5 |
| 类别 | 必须同一类别（跨类别直接拒绝） |
| 重复 ID | 拒绝 |

比较表行顺序：参考价格 → 品牌 → 核心参数（按品类白名单顺序）→ 适用场景 → 优点 → 缺点 → 预算匹配 → 数据来源。

| 特性 | 实现 |
|---|---|
| 参数白名单 | `comparison.param_keys(category)`，与商品维护页共用 |
| 缺失单元格 | 统一写“信息缺失”，**不用其他商品的值填充** |
| 差异标记 | 每行 `varies = len(set(values)) > 1`，界面据此高亮 |
| 单位 | 内存 GB、存储 GB、屏幕英寸、重量 kg/g、续航小时、电池 mAh |
| 档位 | 显示 `4/5`，标注满分便于理解量纲 |
| 布尔值 | “有/无” |
| 数据质量 | `missing_cells` 统计缺失单元格数，界面提示完整度 |

业务层不导入 pandas；比较结果是普通 dataclass，界面层自己转 DataFrame。这样比较逻辑可以在无 Streamlit、无 pandas 的环境里单测。

## 9. 报告与快照

### 9.1 报告是快照，不是引用

`DecisionReport` 里存的是**当时算出的**分数、排序、价格文案、优缺点、来源、核验状态与存疑说明。打开历史时不按当前商品数据重算。因此商品改价或下架后，旧报告的结论不会悄悄变化。

### 9.2 条件指纹

```text
canonical = {
  category, budget,
  use_cases: sorted(...), core_needs: sorted(...),
  compromises: sorted(...), brand_preferences: sorted(...),
  hard_constraints: sorted(...)
}
signature = sha256(json.dumps(canonical, sort_keys=True))
```

两个刻意的设计：

- **不含原始文本**：措辞不同但条件相同（“预算 4000 买办公本”与“4000 元的学习笔记本”）视为同一组条件；
- **列表先排序**：先说学习还是先说编程不影响指纹。

去重在数据库层按 `(user_id, signature)` 做部分唯一索引；不同用户提交相同条件各存一条。写入时先查、插入冲突再查，覆盖并发窗口。

### 9.3 “需要进一步核实”的内容

只写真实存在的缺口，不写万能免责声明：

1. 缺字段的商品，列出缺了哪些字段；
2. 记录内部矛盾的商品，列出矛盾点；
3. 数据集超过 90 天未更新，提示价格可能变化；
4. 数据集本身不含销量、真实评价、售后与保修；
5. 有超预算商品时提示确认当前实际价格；截断时说明还有多少未列出；
6. 完全没有匹配时说明“是本数据集覆盖不到，不代表市场上没有”。

### 9.4 结论生成

按分支生成，不伪造：

- 无任何结果 → 明确说不给推荐，建议放宽条件；
- 只有超预算候选 → 说明预算内无商品，给出匹配度最高的一件与超出金额；
- 有预算内首选但匹配度低 → 推荐同时提示差距；
- 超预算商品分数更高 → 推荐预算内首选并提示可上浮预算的选项。

### 9.5 导出

| 格式 | 内容 |
|---|---|
| Markdown | 固定八节：需求摘要、筛选条件、推荐商品、超预算候选、放宽建议、过程说明、待核实、最终建议 + 数据说明 |
| CSV | 一行一件商品，18 列：分区、序号、ID、名称、品牌、类别、价格、预算匹配、评分、档位、优缺点、来源、更新时间、存疑、核验状态、型号、价格来源 |

CSV 带 UTF-8 BOM，避免 Excel 打开中文乱码。导出件同样标注“未核验”，因为导出后会脱离界面单独流传。

## 10. 知识库与检索

### 10.1 语料构成

```text
data/knowledge/
├── faq.md              服务级：术语、能力边界、常见问题
└── category/
    ├── laptop.md       笔记本选购指南
    └── phone.md        手机选购指南

商品级条目：不写文件，由商品字段在加载时合成
```

当前共 **23 份文档**（3 份手写 + 20 条商品级），切出 **38 个切片**。语料是纯文本，可 diff、可回滚；数据库只存派生出的向量，不存文档本身。

### 10.2 front-matter 契约

手写文档必须以 `---` 开头，包含 `title`、`type`、`source`、`updated_at`；`type` 只允许 `category` / `service`。缺字段、类型非法或正文为空 → 跳过该文档并记日志，不影响其他文档。

正文开头若有一级标题与 front-matter 的 `title` 同名，会被剥掉，避免索引里多一份重复标题。

### 10.3 商品级条目合成

模板刻意与商品字段**字面一致**，不做转述、不加形容词：

```text
真我 GT Neo6 SE（品牌 真我，类别 手机，参考价 1899 元）。
参数：芯片 骁龙 7+ Gen 3、芯片档位 4、内存 12GB、...
适用场景：游戏、拍照、日常。
优点：...；不足：...
```

参数名用 `config.SPEC_LABELS` 的中文标签，而不是 `ram_gb` 这类键名——用户会用“内存”“续航”提问。这样商品数据更新后，知识库不会出现第二份过期副本。

### 10.4 切片

- 按 `##` 二级标题切小节，第一个标题之前的内容单独成节；
- 单节超过 500 字时按空行继续切，单段超长则硬切；
- 切片 ID 稳定为 `doc_id#序号`；
- 送去向量化的文本 = 标题 + 小节名 + 正文，避免切片脱离文档后只剩半句话。

### 10.5 BM25 实现

纯标准库，不引检索库。中文按**字符二元组**切分（“主动降噪” → 主动/动降/降噪），拉丁字母与数字按整词切分（`16GB`、`K87` 保持整体）。这样既不依赖分词器，也能让“降噪”与“主动降噪”共享检索单元。

```text
idf(t) = ln(1 + (N − df(t) + 0.5) / (df(t) + 0.5))
score(D, Q) = Σ_t idf(t) · f(t,D) · (k1 + 1)
              / (f(t,D) + k1 · (1 − b + b · |D| / avgdl))
k1 = 1.5, b = 0.75
```

标题与正文一起参与切分——“标题往往就是用户在问的东西”。得分为 0 的文档不返回。

### 10.6 三类加权

| 加权 | 系数 | 触发条件 | 目的 |
|---|---:|---|---|
| 文档类型 | product 0.45，category/service 1.0 | 按 `doc_type` | 商品条目字段罗列命中二元组多，压低避免霸榜 |
| 品类 | ×1.6 | 查询点名了某品类 | “笔记本多重适合带出门”优先笔记本指南，避免被键盘/平板文里的字面碰撞顶掉 |
| 品牌 | ×3.0 | 查询点名品牌，且（未点名品类或品类一致） | 品牌词只有两三个字，BM25 天然分低；品类约束防止“华为笔记本”把华为手机顶上来 |

0.45 是实测校准值：0.55/0.50 时“机械键盘选什么轴”会被商品名顶掉选购指南，0.45 及以下通过；取通过值里最高的那个。

### 10.7 阈值与相对截断

```text
最高分 < 3.0                    → 判定为“检索不到”，返回空
cutoff = max(3.0, 最高分 × 0.35) → 只保留与第一名同量级的命中
最多返回 3 条
```

绝对阈值管“有没有”，相对截断管“准不准”。实测（当前语料）：

| 查询 | 最高分 | 第二名 | 最终保留 |
|---|---:|---:|---|
| 笔记本多重适合带出门 | 7.57（笔记本选购指南） | 2.73 | 1 条 |
| 怎么选手机拍照 | 5.06（手机选购指南） | 2.03 | 1 条 |
| 今天天气怎么样 | 2.88（FAQ） | 2.05 | 0 条（低于 3.0） |

### 10.8 片段抽取

整篇资料上千字，不能直接铺给模型。做法：按空行切段，按与查询的二元组重合度排序，取最相关的前 3 段，拼成不超过 600 字的片段；同分保持原文顺序；Markdown 标题降级为粗体。

片段**不在界面展示**，只作为 AI 作答的依据。因此覆盖关键信息比行文连贯更重要——实测只给“命中段 + 相邻段”时，问“笔记本多重适合带出门”拿不到重量分档数字，模型只能回答“资料没覆盖”。

### 10.9 向量检索（可选）

向量库就是一张 SQLite 表 + numpy 余弦检索（下表为字段示意，正式建表语句含 NOT NULL 与默认值）：

```text
knowledge_vectors
  doc_id, slice_id, title, heading, content, doc_type,
  source, updated_at, product_id,
  model, dim, embedding, content_hash, indexed_at
  主键 (doc_id, slice_id)
```

| 机制 | 实现 |
|---|---|
| 增量构建 | 正文哈希 + 模型 + 维度都一致才跳过；否则重建该切片 |
| 陈旧清理 | 当前语料中已不存在的切片从表中删除 |
| 状态统计 | `ready` / `stale` / `missing`，管理页展示 |
| 检索 | 只取与当前模型/维度一致的行，暴力余弦，top-k |
| 阈值 | 余弦 < 0.45 判无结果；相对截断 0.35；最多 3 条 |
| 维度不一致 | 记警告并返回空，不混用不同模型的向量 |

Embedding 调用独立配置（DeepSeek 没有 embeddings 接口），按 10 条一批请求，返回条数与维度都必须匹配，否则整批拒绝。向量混用是静默错误：检索分数会失真但不报错，比直接失败更糟。

### 10.10 检索调度与回退

```text
配置了 Embedding 密钥？
  ├─ 否 → BM25
  └─ 是 → 向量检索
        ├─ 抛领域异常 → BM25 + 说明回退原因
        ├─ 有结果 → 向量结果
        └─ 结果为空（低于阈值）→ 空，**不回退 BM25**
```

最后一条是刻意的：向量判定“语义上确实不相关”时，回退到字面匹配会把“没有资料”变成“碰巧命中几个词”，违背检索意图。未配置、调用失败、没有足够相似结果是三种不同情况，界面分别说明。

### 10.11 检索的能力边界

检索按文本相关性找资料，**不理解数值约束**。问“2000 元以内买什么手机”，BM25 完全可能返回一款远超预算的商品——这不是缺陷，是检索的本性。因此具体预算/商品问题在页面层改走结构化推荐：先解析出预算与品类，再从商品库取候选，让模型在候选范围内组织回答。

> 代码里还保留着 `KNOWLEDGE_PRICE_INTENT_TERMS`（“多少钱/预算/元以内”等词表），但当前没有任何模块引用它。实际生效的是 AI 问答页的 `_has_product_intent()`：有预算或“推荐/买哪/哪款”等意图时转商品推荐。这处未接线的配置属于技术债，见第 19 节。

## 11. AI 层

### 11.1 传输层

`AIService` 只负责“把请求发出去、把响应拿回来、把失败翻译成领域异常”，不写提示词、不做业务映射。

- 使用 `httpx.Client` 直连 `{base_url}/chat/completions`；
- 请求体：`model`、`messages`、`max_tokens`、`temperature=0.2`、`stream=false`；只有传了工具才带 `tools` / `tool_choice`（空列表在部分服务商上会被理解为“不允许调用工具”）；
- 可注入 `httpx.Client`，测试用 `MockTransport` 覆盖超时、鉴权、5xx、空响应；
- 密钥只从配置读取，日志与异常统一过 `redact()`，并把任何形如 `sk-xxx` 的长串替换掉。

### 11.2 失败映射

| 上游情况 | 异常 | 上层行为 |
|---|---|---|
| 未配置密钥 | `AINotConfigured` | 本地模式，界面说明如何配置 |
| 连接/读超时 | `UpstreamTimeout` | 降级规则模式，说明超时秒数 |
| 401 / 403 | `UpstreamAuthError` | 提示密钥无效或过期 |
| 429 | `UpstreamUnavailable` | 提示限流 |
| ≥500 | `UpstreamUnavailable` | 提示服务不可用 |
| 其他 4xx | `UpstreamUnavailable` | 响应体脱敏后记录 |
| 非 JSON / 结构不符 | `UpstreamResponseError` | 回退规则模式 |
| 空正文且无工具调用 | `UpstreamResponseError` | 回退，不把空串当答案 |
| `finish_reason=length` 且正文为空 | `UpstreamResponseError` | 提示推理吃光 token，可调大上限 |

### 11.3 推理模型的 token 陷阱

DeepSeek 的 `deepseek-flash` / `deepseek-v4-pro` 是推理模型，推理过程（`reasoning_content`）也计入 `max_tokens`。上限给小了会出现“正文为空、`finish_reason=length`”。系统把这种情况当失败处理并降级，绝不把空字符串当有效结果往下传。`reasoning_content` 本身刻意不返回：它是模型内部推理，可能复述提示词。

### 11.4 JSON 输出与提取

模型经常把 JSON 包在代码块里或前后加一句话。`extract_json_object()` 依次尝试：

1. 整段就是 JSON；
2. Markdown 代码块（json 围栏）里的 JSON；
3. 第一个括号平衡的 `{...}`。

三种都不成返回 `None`，由调用方报错降级。**只去包裹，不做“尽力修复”**——把残缺 JSON 修补成能用的结构，等于把格式错误掩盖成数据错误。

### 11.5 五类提示词任务

| 任务 | 输入 | 输出 | 关键约束 |
|---|---|---|---|
| 需求解析 | 用户原文 + 可选品牌清单 | JSON → `Demand` | 只提取明确说过的话；表外词丢弃 |
| 推荐解读 | 需求 + 候选商品 + 维度得分 | `{overview, per_product}` | 只解释、不重排；不提销量/口碑/保修；不编价格 |
| 知识问答 | 问题 + 最多 3 条片段 | `{answer, used_fragment_indexes}` | 只依据片段；不出现“资料/知识库”字样；不给具体价格 |
| 商品问答 | 问题 + 片段 + 商品候选 | `{answer}` | 必须从候选里选 2–3 款；写清参考价与匹配理由 |
| 通用知识 | 问题 | 纯文本 | 必须声明“基于通用知识”；不给具体价格/型号/排他结论 |

每个任务都有字数上限（60 字/条、200–250 字整段）和禁令清单，目的是让输出可校验、可展示，而不是写得漂亮。

### 11.6 四类事实校验

**（1）价格**

正则抓“3299 元”“¥3,299”，用“前面不是数字或逗号”做边界，避免把“3,299”从逗号后切断只抓到 299。允许集是本次数据里真实存在的价格并集：

- 解读：候选商品价格 ∪ 用户预算；
- 知识问答：片段原文里出现的价格；
- 商品问答：候选价格 ∪ 片段价格 ∪ 用户问题里的价格。

对不上就说明模型在编，丢弃整条文本。

**（2）参数数值**

只校验“数字 + 明确单位”，裸数字（序号、年份、评分）不纳入，避免大量误杀。

单位族：质量（克/千克/kg）、时间（小时/时/h）、存储（GB/TB）、电池（mAh）、长度（英寸/寸）、小长度（毫米/mm）。同族先换算再比较。

```text
tolerance = max(0.05, |known| × 0.02, 小数取整半径)
小数取整半径 = 0.5 × 10^(−小数位数) × 单位换算倍数
```

2% 相对容差吸收四舍五入，但挡得住量级错误；小数断言额外允许按写法精度取整（1.36 → 1.4 不算编造），整数断言不适用——否则 `1TB` 会被当成区间 [0.5, 1.5] TB，放过把 512GB 说成 1TB 的错误。

**（3）排他性/绝对化结论**

固定词表：销量第一、口碑最好、全网最低、历史最低价、遥遥领先、行业第一、好评率等。共同点是它们断言的比较维度在数据集里根本不存在。

刻意不收“排名第一”“同类第一”：系统确实会排序，“在本次推荐里排第一”是真的，收进来会误杀正确解读。宁可漏放，不可误杀。

**（4）存疑属性**

商品被标记“资料存疑”时，解读不能就**被标记的那几个属性**下结论。属性 → 关键词由 `SPEC_LABELS` 推导，剥掉“档位/等级”后缀（模型会说“处理器”，不会说“处理器档位”）。只拦被标记属性，不牵连同一商品的其他正常属性。

### 11.7 校验覆盖矩阵（重要）

不同路径的校验范围不同，不能把一条路径的检查套到所有 AI 输出上：

| 路径 | 价格 | 参数数值 | 排他结论 | 存疑属性 | 失败处理 |
|---|:---:|:---:|:---:|:---:|---|
| 知识问答 | ✓ | ✗ | ✓ | ✗ | 抛异常，整条不展示 |
| 商品问答 | ✓ | ✗ | ✗ | ✗ | 抛异常，整条不展示 |
| 通用知识 | ✗ | ✗ | ✗ | ✗ | 界面标注“未引用知识库” |
| 推荐解读（评测路径） | ✓ | ✓ | ✓ | ✓ | 丢弃该条解读，保留规则结果 |
| Agent 最终文本 | ✗ | ✗ | ✗ | ✗ | 工具参数两层校验；页面提示“以工具返回数据为准” |

`explain_recommendations()`（四类全校验）当前只被评测脚本与测试调用，分析页在 Agent 上线后**不再调用它**。原因是两者都在生成自然语言解释，同时跑会出现两段口径不同的“为什么推荐”。这是当前实现的真实边界：Agent 路径的最终说明文本没有走完整事实校验，比赛材料里不能把它说成“已经杜绝所有编造”。

### 11.8 数据出境告知

启用 AI 前，界面会说明会发送什么：

- 需求原文（填了才发）；
- 筛选条件；
- 候选商品的名称、价格、参数与优缺点。

不会发送收藏、历史记录、身份或设备信息。密钥不写进源码，`.env` 不入库；日志只记异常类型与消息。

## 12. Agent 编排

### 12.1 循环

```text
用户问题 + 工具声明
        │
        ▼
  模型（tool_choice=auto）
        ├─ 请求工具 → 校验 → 执行 → 结果回灌 → 回到模型
        └─ 直接作答 → 结束
```

三个终止条件：模型给出最终回答、达到 5 轮上限、上游异常。前两个是设计内终止；上游异常由页面边界统一捕获，降级到确定性管道。

### 12.2 四个只读工具

| 工具 | 参数 | 语义校验 | 底层 |
|---|---|---|---|
| `search_products` | `category`、`budget_min/max`、`use_cases`、`core_needs`、`limit`(1–10) | 类别存在；预算为正；min ≤ max | `recommender.recommend` |
| `get_product_detail` | `product_id` | ID 真实存在 | `catalog.get` |
| `compare_products` | `product_ids`(2–5)、`focus` | 数量、去重、同类别、ID 存在 | `comparison.compare` |
| `search_knowledge` | `query`、`limit`(1–5) | query 非空；知识库可用 | `knowledge.retrieval` |

工具是业务函数的薄封装，不重复实现逻辑，因此不存在“Agent 算出来的和界面算出来的不一样”。

### 12.3 两层校验与“不纠正”哲学

1. **形状层**：pydantic 校验类型、必填、取值范围；工具声明用的 JSON Schema 由同一个模型派生，不会出现“声明说可选、校验说必填”的漂移。
2. **语义层**：工具自己校验“这个值在我们的数据里存在吗”。

模型把品类写成“笔记本”而不是 `laptop` 时直接拒绝，返回可用类别；不替它猜。自动纠正会掩盖“模型没按 schema 给值”的事实，而那恰恰是校验在起作用的证据。被拒绝的调用同样进入轨迹。

### 12.4 结果与轨迹

`ToolResult` 分三态：

| 状态 | 含义 | 轨迹展示 |
|---|---|---|
| `ok` | 成功 | 成功 |
| `rejected` | 参数没按 schema 给 | 参数被拒 |
| `error` | 工具执行本身出错 | 执行出错 |

分开的理由：前者说明校验在拦，后者说明代码有问题；混成一个颜色，看轨迹的人分不清该改提示词还是改代码。

`TraceStep` 记录轮次、工具名、参数、状态、摘要（120 字）。结果回灌给模型的 JSON 上限 4000 字符，超出截断并注明。轨迹里只有真实发生过的调用，没有模型的思考文字。

### 12.5 失败语义

| 情况 | 结果 |
|---|---|
| 模型请求未注册的工具 | `rejected`，告诉它有哪些可用工具 |
| 参数不合法 | `rejected`，压缩成中文原因回灌，让它下一轮改 |
| 工具内部异常 | `error`，记日志，不中断整轮编排 |
| 达到轮次上限 | `degraded=True`，返回降级原因，页面改用规则结果 |
| 上游超时/鉴权失败 | 异常抛到页面边界，统一提示并保留规则结果 |

Agent 失败不影响筛选、评分、排序和报告——基础功能不依赖模型。

## 13. 存储

### 13.1 两个数据库文件

| 文件 | 表 | 理由 |
|---|---|---|
| `storage/products.db` | `products`、`product_prices`、`dataset_meta`、`category_meta`、`brand_meta` | 外部录入的数据 |
| `storage/zhigou.db` | `users`、`analysis_history`、`favorites`、`user_preferences`、`preference_template`、`knowledge_vectors` | 程序产生的记录 |

分开不是洁癖：共用一个文件时，文件损坏会让商品与历史同时读不出来。分开后故障局部化——历史坏了仍能分析，商品库坏了历史仍可查看。两者写入节奏、备份需求、损坏后果都不同。

### 13.2 表结构摘要

| 表 | 主键 / 关键列 | 说明 |
|---|---|---|
| `users` | `username` | role、is_active、password_hash、created_at；无邮箱/手机号/姓名 |
| `analysis_history` | `id` 自增 | 快照 JSON、signature、user_id（可空=遗留）、top_product/top_score |
| `favorites` | `(user_id, product_id)` | 旧形态是单列主键，会导致全站只能有一人收藏同一商品，老库走重建迁移 |
| `user_preferences` | `user_id` | 偏好 JSON |
| `preference_template` | `id=1` | 单用户时期 settings.json 的收编结果，作为新用户默认值 |
| `products` | `product_id` | specs/use_cases/pros/cons 存 JSON 文本；按品类异构，拆 EAV 收益为零 |
| `product_prices` | `id` 自增 | 当前价 + 历史价，`ON DELETE CASCADE`（需逐连接开 `PRAGMA foreign_keys`） |
| `dataset_meta` | `key` | 免责声明、档位说明等数据集级信息 |
| `category_meta` / `brand_meta` | 键 | 展示名、排序、启停；不是全集，全集仍是 `config.CATEGORY_LABELS` |
| `knowledge_vectors` | `(doc_id, slice_id)` | 向量 JSON、内容哈希、模型、维度 |

### 13.3 迁移策略

- 建表用 `CREATE TABLE IF NOT EXISTS`，对已存在的表是空操作；
- 补列与建索引分开：老库没有 `user_id` 列时，先补列再建索引，否则 `CREATE INDEX` 会以 `no such column` 把升级卡死；
- 需要改主键的表（favorites）走“建新表 → 搬数据 → 删旧 → 改名”；
- 升级前先体检库形状，必要时备份为 `.bak`。

### 13.4 用户隔离与删除

- 历史、收藏、偏好都带 `user_id`；
- 历史查询按 `user_id` 过滤，管理员可看全站；
- 删除账号前统计并展示影响范围，删除时级联删除该用户的历史、收藏、偏好；
- 不能删除自己；不能删除最后一个可用管理员（`LastAdminProtected`，与 `PermissionDenied` 分开：那不是“你没权限”，是“谁来做都不行”）。

## 14. 账号与权限

### 14.1 密码

```text
pbkdf2_sha256$600000$<salt_hex>$<hash_hex>
```

- 标准库 `hashlib.pbkdf2_hmac`，600,000 次迭代，16 字节随机盐；
- 算法与迭代次数写进凭据串，校验时从串里读参数；日后调参不会让已有密码失效；
- `hmac.compare_digest` 定长比较；
- 用户名不存在与密码错误共用一句话；账号停用继承同一文案，真实原因只进 `detail` 日志。

密码规则只要求长度 ≥ 8，不强制大小写/特殊字符——更严的规则通常只会把人推向 `Password1!`。

### 14.2 权限的三道关

1. 导航层：`admin_only` 决定侧栏是否显示；
2. 页面入口：`require_admin(user)`；
3. 领域层：管理员写操作（改角色、重置密码、停用/删除账号、商品与分类元数据）在函数入口再次校验。

第 3 道才是权限本身。只隐藏按钮不构成权限：页面函数会互相调用，`session_state` 也能被脚本改写。

### 14.3 会话

- 登录态只放 `session_state`，不写 Cookie；刷新页面需要重新登录；
- 登录成功后每轮查一次库，账号被停用/删除则立即登出；
- 登出清空**整个** session_state，而不只是用户键——否则下一个账号会看到上一个用户的推荐结果与报告。

## 15. 界面架构

### 15.1 Streamlit 的重跑模型

每次交互都会从头重跑整个脚本。项目用三层机制应对：

| 机制 | 作用 |
|---|---|
| `session_state` | 分析结果只由“点分析”写入，渲染永远只读 |
| 跨页请求键 | 控件实例化后不能改它绑定的键；发起方只记请求，接收方在控件创建前消费 |
| 控件镜像 | 侧栏 `rerun()` 会中断正文渲染，导致控件键被清；把值另存到普通会话键，下次恢复 |

### 15.2 缓存键

| 缓存 | 键 | 目的 |
|---|---|---|
| 商品数据集 | 商品库路径 + 文件 mtime | 数据脚本写库后，下一次渲染自动加载新数据 |
| 知识索引 | 语料目录 + 所有 `.md` 的 mtime 最大值 + 商品库 mtime | 改语料或改商品都能触发重建 |
| 启动引导 | 无（`cache_resource`） | 只跑一次：收编旧设置、创建初始管理员 |

目录自身的 mtime 只在增删文件时变，改内容不变，所以要把目录下所有 `.md` 的 mtime 一并取最大值。

### 15.3 页面清单

| 页面 | 功能 |
|---|---|
| 登录 / 注册 | 入口；未登录时**只渲染登录页并立即返回**，不触发任何数据查询 |
| 首页 | 自然语言输入 + 示例，跳转分析 |
| 智能分析 | 需求解析、筛选、评分、Agent、报告导出；核心页面 |
| 商品比较 | 2–5 件同品类对比 |
| AI 问答 | 知识库 / 商品库 / 通用知识三路作答 |
| 历史记录 | 自己的分析快照与收藏 |
| 个人设置 | AI 开关、价格取向、显示偏好 |
| 关于 | 评分口径、数据来源、使用边界 |
| 商品维护（管理员） | 商品、价格、分类、品牌 |
| 知识库管理（管理员） | 文档、切片、重建索引 |
| 全站概览 / 用户管理（管理员） | 全部记录、角色、重置密码、停用、删除 |

### 15.4 视觉层

- `theme.py` 提供颜色、字体、阴影等设计令牌与基础样式；
- `backend_theme.py` 是登录后的后台视觉层，只在登录后注入；
- `components.py` 提供页面头、卡片、提示条、统计块等组合件；
- `icons.py` 内联 SVG 图标，避免额外图标依赖。

样式依赖 Streamlit 的部分内部 DOM 结构，升级 Streamlit 时需要跑界面回归。这是已知耦合。

### 15.5 异常兜底

`app.py` 是唯一的异常出口：

- 数据加载失败 → 中文提示 + 排查路径，页面停在这里；
- 页面内领域异常 → `to_user_message()`；
- 其他异常 → 记日志 + 兜底文案，绝不把堆栈冒到界面。

因此“不向用户暴露堆栈”这件事只需在一个地方保证。

## 18. 性能与复杂度

| 操作 | 复杂度 | 当前规模下的实际表现 |
|---|---|---|
| 单件评分 | O(维度数 + 同品类商品数) | 20 件商品、5 维，毫秒级 |
| 全量评分 | O(n × d) | 20 件商品，几乎无感 |
| 性价比排位 | 每品类 O(n²)，n=10 | 可忽略 |
| BM25 建索引 | O(文档数 × 平均词数) | 百级文档，毫秒级 |
| BM25 查询 | O(N × 查询词数) | 38 切片，毫秒级 |
| 向量检索 | O(N × 维度)，numpy 矩阵乘 | 百级切片，毫秒级 |
| 报告生成/导出 | O(候选数) | 纯字符串拼接 |
| AI 调用 | 网络延迟主导 | 单次 1–60 秒，有超时 |

真正的性能瓶颈是模型调用，不是本地计算。因此系统把 AI 全部放在可选路径上，并在超时/失败时快速降级。

缓存策略避免每次交互重建索引：商品库 mtime 变才重载商品，语料或商品 mtime 变才重建 BM25。`max_entries=4`，旧版本缓存没有复用价值。

## 19. 已知限制与技术债

### 19.1 数据

- 只有 20 件商品、2 个品类，覆盖不了真实长尾需求；
- 所有记录 `unverified`，价格不是实时价，参数是简化刻度；
- 不接入电商平台，没有库存、销量、真实评价、保修与售后；
- 图片是外链，可能失效（界面回落类别图标）。

### 19.2 算法

- 评分是**需求匹配度**，不是商品好坏、口碑或销量；
- “拍照”在用途与核心需求两条路径上的量纲不同，商品 `use_cases` 标注会显著影响得分；
- 预算实际是软约束（分区），与部分文档“硬性过滤”的措辞不一致；
- 品牌偏好按硬条件处理，不命中时直接筛空，依赖放宽建议兜底；
- 硬性条件目前只识别“独显/独立显卡”，其他条件只提示不筛选。

### 19.3 工程

- SQLite 单写者，没有 WAL 配置，不适合多实例并发写；
- 没有 HTTP API，第三方无法直接集成；
- Streamlit 单体，页面状态依赖 `session_state` 与内部 DOM 结构；
- 账号体系是演示级：无登录限流、无会话过期、无找回密码、无二次验证；
- Cloud 文件系统临时，休眠/重部署可能重置账号、历史与收藏；
- `Dockerfile` 未在本机实际构建。

### 19.4 AI 与校验

- Agent 最终说明文本没有走四类事实校验，只有工具参数两层校验；
- 商品问答只校验价格，商品名与推荐理由主要靠提示词约束；
- 通用知识回答不做事实校验，只做来源标注；
- `explain_recommendations()` 保留但运行时不再调用，四类全校验只覆盖评测路径；
- `KNOWLEDGE_PRICE_INTENT_TERMS` 已定义但未接线，实际由页面级商品意图判断替代；
- AI 解析允许的硬性条件里仍有“静音/降噪/无线/热插拔”，这些条件在商品库收缩后已无对应参数，会被推荐层当作“无法识别”跳过。

### 19.5 评测

- 41 条用例是自建自评，样本有限，偏向已有能力；
- 任务完成率、证据支持率未测量；
- 未做真实用户研究与多人并发测试；
- 全绿只能说明“没有退步”，不能证明真实场景有效。

## 20. 演进路线

按“先补数据和评测，再谈规模和形态”的顺序：

1. **接入授权商品数据源**：补价格采集时间与来源，减少“未核验”比例；
2. **数据库升级**：换 PostgreSQL/MySQL，补迁移、备份与并发写；
3. **评测扩容**：增加真实用户任务、扩大标注样本、补任务完成率与证据支持率；
4. **按需拆 API**：保留现有业务模块，套 FastAPI，不动评分与检索；
5. **数据与评测稳定后再扩品类**：每个品类都需要权重、档位、指南与足够型号。

不建议先做大规模前端重写：当前瓶颈在数据质量与评测，不在页面数量。
