# 技术架构

## 1. 系统边界

智购参谋是一个单进程的 Streamlit 应用。用户通过浏览器访问，应用在服务端完成需求解析、商品筛选、评分排序、知识检索和报告生成。

当前版本没有独立的前后端接口，也没有接入电商平台。商品数据、知识文档和评测用例都在仓库内维护，运行时写入本地 SQLite。

```text
浏览器
  │
  ▼
Streamlit 页面（src/ui）
  │  直接函数调用
  ▼
业务模块（src/）
  ├── 需求解析 / 评分 / 推荐 / 比较 / 报告
  ├── 知识库检索
  ├── Agent 工具编排
  ├── 账号与权限
  └── 商品与历史存储
        │
        ├── storage/products.db
        ├── storage/zhigou.db
        └── data/products.json（种子数据）
```

选择 Streamlit 单体不是因为它适合所有场景，而是因为当前目标是比赛演示和快速迭代：单进程启动、没有跨服务联调、现场网络不稳定时仍能运行核心功能。业务代码集中在 `src/`，不依赖 Streamlit，未来拆成 FastAPI 服务时可以复用。

## 2. 分层与模块

| 位置 | 职责 | 依赖 Streamlit |
|---|---|---|
| `app.py` | 页面配置、登录入口、导航、数据加载、异常兜底 | 是 |
| `src/ui/` | 页面、组件、主题、会话状态 | 是 |
| `src/config.py` | 路径、环境变量、评分权重、标签 | 否 |
| `src/demand_parser.py` | 自然语言 → `Demand` | 否 |
| `src/scoring.py` | 单商品多维度评分 | 否 |
| `src/recommender.py` | 筛选、排序、超预算处理、放宽建议 | 否 |
| `src/comparison.py` | 同品类商品比较 | 否 |
| `src/report_service.py` | 决策报告组装、Markdown/CSV 导出 | 否 |
| `src/ai_service.py` | OpenAI 兼容接口调用、超时和错误映射 | 否 |
| `src/ai_enhance.py` | 提示词、结构化输出清洗、结果校验、问答 | 否 |
| `src/knowledge/` | 语料加载、切分、BM25、向量检索、知识管理 | 否 |
| `src/agent/` | 工具注册表、参数校验、编排循环、执行轨迹 | 否 |
| `src/database.py` | SQLite 读写：账号、历史、收藏、偏好 | 否 |
| `src/product_store.py` | 商品库读写、种子导入、价格记录 | 否 |
| `src/auth.py` / `src/accounts.py` | 密码派生、角色判定、注册登录、初始管理员 | 否 |

`app.py` 不写业务规则。这样测试可以直接导入业务函数，不需要启动界面；页面出错时也只在边界处统一捕获，不让堆栈冒到用户面前。

## 3. 一次分析的调用链

```text
用户输入
  │
  ├─ 结构化表单 ──┐
  └─ 自然语言 ────┤
                  ▼
          demand_parser.parse()
                  │
                  ▼
              Demand
   品类 / 预算 / 用途 / 核心需求
   品牌偏好 / 硬性条件 / 可妥协项
                  │
                  ▼
          recommender.recommend()
     硬性过滤 → 逐件评分 → 排序 → 超预算分组
                  │
                  ├─ scoring：预算、需求、性能、性价比、便携
                  ├─ comparison：多商品差异
                  └─ report_service：报告与导出
                  │
                  ▼
          AI 增强（可选）
     需求解析 / 推荐解释 / Agent 工具调用
                  │
                  ▼
          database.save()：JSON 快照
```

需求解析有两条路径：本地规则和模型解析。两条路径都输出同一个 `Demand` 类型，上层不关心当前用的是哪一种。模型解析失败时回到规则解析，不把空结果当成成功。

## 4. 评分与排序

### 4.1 计算方式

总分是各维度得分乘以品类权重后的和：

```text
total = Σ(score_i × weight_i)
```

权重配置在 `src/config.py` 的 `SCORING_WEIGHTS` 中，每个品类的权重和为 1。当前使用五个维度：

- 预算匹配；
- 核心需求匹配；
- 性能功能适配；
- 性价比；
- 便携性。

不同品类的权重不同。例如手机更看重核心需求匹配，笔记本把预算和性能的权重留得更高。具体数值以配置文件为准，不写死在页面里。

### 4.2 几个不能省的规则

- **先过滤，再排序。** 预算和品类是硬约束，不能因为某件商品在其他维度得分高就跳过预算。
- **超预算商品单独展示。** 它们仍然有价值，但必须写明超出金额，不能伪装成预算内结果。
- **缺失维度不计分。** 没有数据时排除该维度并注明原因，不补 0 分或平均分。
- **评分不是商品好坏。** 同一件商品在“拍照优先”和“便携优先”下得分不同，这是设计目标，不是数据不稳定。
- **AI 不参与计算。** 模型只生成解释，不改变分数、排序或候选集合。

### 4.3 数据缺失与矛盾

商品记录允许字段为空。加载时会记录缺失字段，评分时排除对应维度；界面和导出报告都会显示“信息缺失”。

如果同一件商品的参数之间存在明显矛盾，例如重量字段和描述不一致，系统会标记“资料存疑”。标记不会把商品直接排除，也不会把数据问题算成商品缺点，但会提醒用户核实。

## 5. 知识库与检索

### 5.1 语料构成

```text
data/knowledge/
├── faq.md                    服务级：术语、能力边界、常见问题
└── category/
    ├── laptop.md             笔记本选购指南
    └── phone.md              手机选购指南
```

商品级条目在建立索引时由商品字段合成，不单独维护 20 份商品介绍。这样商品数据更新后，知识库不会出现另一份过期副本。

每份手写文档带有标题、类型、品类、来源和更新时间等元数据。文档按标题和段落切分，切片 ID 保持稳定，重复建索引不会重复写入。

### 5.2 两种检索模式

系统优先使用向量检索：

1. 配置了 `ZHIGOU_EMBEDDING_API_KEY` 时，把查询和切片转成向量，按余弦相似度检索；
2. 检索结果经过最低相似度和相对截断，单次最多返回 3 条；
3. 未配置密钥、调用失败、没有足够相似结果时，回退到 BM25。

BM25 使用中文二元组和拉丁词切分，不依赖分词器。它对语料规模敏感，因此阈值按完整语料校准，不能拿小样本的分数直接套用。

两种模式都返回同一组 `Passage` 对象，上层不需要知道当前走的是哪条路径。界面会显示本次使用的是“语义检索”还是“BM25 关键词检索”，并在向量服务失败时说明回退原因。

### 5.3 回答策略

- 有可靠资料：依据资料回答，价格和排他性结论仍要校验；
- 资料不足：使用 AI 通用知识补答，界面明确标注“未引用知识库”；
- 具体商品或预算：先从商品库取候选，再让模型在候选范围内推荐；
- 未配置模型：说明如何配置，不展示半成品；
- 上游失败：说明失败原因并建议重试，不把空内容当答案。

## 6. Agent 编排

AI 增强模式下，复杂问题可以进入 Agent 循环。模型根据问题选择工具，读取结果后继续，直到给出回答或达到轮次上限。

### 6.1 工具集

| 工具 | 能力 | 底层实现 |
|---|---|---|
| `search_products` | 按预算、品类、用途筛选 | `recommender` |
| `get_product_detail` | 按商品 ID 读取详情 | `data_loader` |
| `compare_products` | 同品类多商品比较 | `comparison` |
| `search_knowledge` | 检索知识库 | `knowledge.search` |

工具全部只读。没有修改商品、写数据库、执行 SQL 或对外发起请求的工具，因此“模型执行任意 SQL”不是靠提示词禁止，而是根本没有这个入口。

### 6.2 参数校验

每次调用经过两层：

1. pydantic 校验类型、必填字段和取值范围；
2. 工具自身校验业务语义，例如品类必须存在、商品 ID 必须真实、比较商品必须同品类。

模型给错参数时，系统返回错误让它重来，不自动把“笔记本”改成 `laptop`。自动纠正会掩盖模型没有按 schema 输出的事实。

### 6.3 循环与轨迹

- 最多 5 轮；
- 模型给出最终回答、达到轮次上限或上游出错时停止；
- 达到上限视为设计内的终止，返回带降级标记的结果；上游异常由界面统一捕获；
- 轨迹记录工具名、参数、结果摘要和状态，不记录模型的隐藏思考；
- 被拒绝的调用也进入轨迹，方便看出校验是否真的在拦截。

Agent 失败或超时后回到确定性管道。筛选、评分、排序和报告不依赖 Agent，因此基础功能不会因为模型不可用而消失。

## 7. AI 输出校验

不同任务使用不同的校验范围。不能把一条路径的检查直接套到所有 AI 输出上。

| 路径 | 检查内容 | 失败处理 |
|---|---|---|
| 知识问答 | 价格、排他性结论 | 丢弃整条回答 |
| 具体商品问答 | 价格是否来自商品库、检索资料或用户问题 | 丢弃整条回答 |
| 通用知识回答 | 不做事实校验，只做来源标注 | 界面标明“未引用知识库” |
| Agent 最终说明 | 工具参数经过两层校验；最终文本未走四类事实校验 | 页面提示以工具返回数据为准 |
| 独立解释函数（评测使用） | 价格、参数数值、排他性结论、存疑属性 | 丢弃该段解释，保留规则结果 |

具体商品问答中，商品名和推荐理由主要依赖提示词约束，没有完整的实体级校验。当前 AI 分析页的说明主要来自 Agent，Agent 的最终文本也没有走同一组四道校验。这是当前实现的边界，比赛材料里不把它说成“已经杜绝所有编造”。

参数数值使用相对容差吸收四舍五入，但不接受量级错误。裸数字（序号、年份、评分）不纳入检查，避免大量误杀。

规则结果不受影响：AI 文本被丢弃时，评分、排序和报告仍然保留。历史报告只存规则快照，不存 AI 文字，因此模型更换或超时不会改变旧结论。

## 8. 数据存储

系统使用两个 SQLite 文件：

```text
storage/products.db
  products              商品主表
  product_prices        价格记录
  dataset_meta          数据集说明
  category_meta         分类展示名、排序、启停
  brand_meta            品牌字典

storage/zhigou.db
  users                 账号、角色、密码凭据
  analysis_history      分析报告快照
  favorites             收藏
  user_preferences      按账号保存的偏好
  preference_template   单用户时期的偏好模板
  knowledge_vectors     可选的向量索引；未配置时为空
```

商品库和历史库分开，是为了让故障局部化：历史库损坏时仍能分析商品，商品库损坏时历史仍可查看。

报告以 JSON 快照存储，不在打开历史时用当前商品数据重算。这样商品价格或参数更新后，旧报告的结论不会悄悄变化。

SQLite 适合单实例演示。它没有多副本并发写能力，因此 Cloud 部署只跑一个实例；需要长期多用户使用时，应换成 PostgreSQL/MySQL 并补迁移。

## 9. 账号与权限

账号体系是演示级实现：

- 密码使用标准库 PBKDF2 加随机盐派生，数据库不存明文；
- 登录态只放在 Streamlit `session_state`，不写 Cookie，刷新页面需要重新登录；
- 普通用户和管理员两种角色；
- 管理页面在界面上隐藏，同时页面入口和数据层写入口各有一道校验；
- 历史、收藏、偏好按用户名隔离；
- 停用或删除账号后，下一次交互时失效；
- 没有登录限流、会话过期、找回密码和二次验证。

公开演示使用 Streamlit Community Cloud，文件系统是临时的。应用休眠或重新部署后，账号、历史、收藏可能重置。比赛演示可以接受，生产环境不可以。

## 10. 部署

当前有三种方式：

| 方式 | 适用 | 数据持久性 |
|---|---|---|
| Streamlit Community Cloud | 公开演示、快速分享 | 临时；休眠或重部署后可能重置 |
| Docker + Railway/Render + 持久卷 | 长期演示 | 保留 `storage/` |
| 自己的 VPS + Docker + 反向代理 | 可控部署 | 保留 `storage/`，自行备份 |

部署细节见 [DEPLOY.md](../DEPLOY.md)。无论哪种方式，模型密钥都通过环境变量或平台 Secrets 注入，不写进仓库。

## 11. 已知限制

- 没有 HTTP API，第三方系统不能直接集成；
- SQLite 不支持多实例并发写；
- 账号体系不是生产级；
- 商品数据只有 20 条，且全部未逐条核验；
- 不接入电商平台，没有实时价格、库存和销量；
- Streamlit 的部分样式依赖内部 DOM 结构，升级时需要跑回归测试；
- 评测集是项目自建，样本量有限。

这些限制是当前版本的边界，不影响演示核心链路，但不能在比赛材料里省略。

## 12. 后续演进

如果继续开发，优先顺序是：

1. 接入授权的商品数据源，补充价格采集时间和来源；
2. 把 SQLite 换成支持并发的关系数据库，补迁移和备份；
3. 增加真实用户测试，扩大评测集，补充任务完成率和证据支持率；
4. 按需拆出 FastAPI 接口，保留现有业务模块；
5. 在数据规模和评测结果稳定后，再考虑更多品类。

不建议先做大规模前端重写。当前瓶颈在数据质量和评测，不在页面数量。
