## 1. 架构总览

### 1.1 目标架构 📋

```
┌──────────────────────────────────────────────────┐
│            前端展示层：Vue 3 + Vite               │  📋
│  首页 / 智能导购 / 商品列表 / 对比页 / AI 问答     │
└──────────────────────┬───────────────────────────┘
                       │  HTTP API
┌──────────────────────▼───────────────────────────┐
│            后端接口层：FastAPI                    │  📋
│   参数校验（Pydantic）· 业务接口 · 异常处理        │
└──────────────────────┬───────────────────────────┘
                       │
┌──────────────────────▼───────────────────────────┐
│                  业务服务层                       │  ✅
│   商品服务 / 筛选排序 / 比较服务 / 推荐记录        │
└──────────┬────────────────────────┬──────────────┘
           │                        │
┌──────────▼─────────┐   ┌──────────▼──────────────┐
│       MySQL        │   │      AI 服务层           │
│  结构化商品与业务数据 │   │  LLM / RAG / Agent      │
│        📋          │   │  ✅ LLM  📋 RAG/Agent   │
└────────────────────┘   └─────────────────────────┘
```

### 1.2 当前架构 ✅

```
┌──────────────────────────────────────────────────┐
│        Streamlit 界面层  src/ui/                  │
│  theme · icons · state · components · pages(×6)  │
└──────────────────────┬───────────────────────────┘
                       │  直接函数调用
┌──────────────────────▼───────────────────────────┐
│              业务逻辑层  src/                     │
│  需求解析 · 评分 · 推荐 · 比较 · 报告 · 接入       │
│             （不依赖 Streamlit）                  │
└──────────┬────────────────────────┬──────────────┘
           │                        │
┌──────────▼──────────┐   ┌──────────▼──────────────┐
│ storage/products.db │   │      AI 服务层           │
│  商品 · 价格 · 元信息 │   │ ai_service · ai_enhance  │
│ storage/zhigou.db   │   │   httpx → DeepSeek 兼容  │
│  分析历史 · 收藏     │   └─────────────────────────┘
│   （两个 SQLite 库） │
│ data/products.json  │
│  种子数据，仅空库时  │
│  导入一次           │
└─────────────────────┘
```

> **商品库与历史库分成两个文件是刻意的**：共用一个文件时，文件一旦损坏，
> 商品数据与历史会同时读不出来，整个应用直接不可用；分开之后损坏是局部的——
> 历史坏了仍能做分析，商品库坏了历史仍在。

**两图的关系**：当前架构不是「尚未完成的半成品」，而是**演示优先**的主动选择。
业务逻辑全部下沉在 `src/` 且不依赖 Streamlit，因此迁往目标架构时，
**业务模块可以原样搬走**——这是当前架构最重要的设计资产。

## 3. 分层设计 ✅

### 3.1 模块职责

```
app.py                   Streamlit 页面编排、session_state、表单校验反馈
                         + **入口短路**：未登录时只渲染登录页，不加载任何数据
src/config.py            环境变量、常量、路径、评分权重表（唯一权重来源）
src/errors.py            领域异常类型 + 面向用户的中文提示映射
src/auth.py              账号的**纯逻辑**：密码派生与校验、角色判定、require_admin 守卫
src/accounts.py          账号的**动作**：注册、登录校验、初始管理员引导
src/data_loader.py       商品加载与字段校验
src/demand_parser.py     自然语言 → 结构化需求（规则实现 + 可选 AI 实现）
src/scoring.py           单商品多维度打分与加分/扣分项提取（纯函数）
src/recommender.py       预算过滤、候选编排、排序、放宽建议
                         + **可见性过滤的入口**（下架商品、停用分类/品牌）
src/comparison.py        多商品比较表组装
src/catalog_meta.py      分类元数据、品牌字典，以及由它决定的可见性过滤
src/catalog_admin.py     管理员维护商品：界面输入 → 可写库记录的校验与写入
src/ai_service.py        大模型调用封装（httpx），超时/失败降级
src/ai_enhance.py        提示词与结果校验（价格幻觉拦截）
src/database.py          SQLite 读写：账号、历史、收藏、按用户的偏好
src/report_service.py    报告组装与 Markdown/CSV 导出
src/ingest.py            外部数据接入：字段映射、档位折算、写前校验
src/settings.py          用户偏好读写（**按账号存库**）
src/ui/                  界面层（唯一依赖 Streamlit 的地方）
src/ui/disclosure.py     「演示级鉴权边界」与数据口径的**唯一文案来源**
```

**账号为什么拆成 `auth.py` + `accounts.py` 两层**：`auth.py` 不碰数据库，
「密码怎么存、谁能做什么」可以被单元测试直接盯住；`accounts.py` 才把
`auth` 与 `database` 拼成「注册」「登录」这样的动作。合成一层的话，
`auth` 要反向依赖 `database`，与 `database` 对 `auth` 的依赖撞成循环导入。

**登录态存在哪里**：`st.session_state`（见 `src/ui/state.py` 的 `current_user()`）。
不留模块级缓存——Streamlit 每次交互都重跑整个脚本，而模块只加载一次，
把当前用户放进模块变量会跨会话串味。代价是刷新页面要重新登录，
这一点写进了鉴权边界说明里。

### 3.2 分层原则

| 层 | 规则 |
|---|---|
| `app.py` | **只管编排**，不含任何业务规则 |
| `src/`（除 `ui/`） | **不依赖 Streamlit**，可单独 import 与单元测试 |
| `src/ui/` | 唯一依赖 Streamlit 的地方 |
| `src/config.py` | 路径、环境变量、权重、标签的**唯一来源** |

**为什么把评分从推荐里拆出来**：评分是纯函数、最需要单元测试，
而推荐要处理过滤与排序策略——两者变更频率不同。

**这样分层换来了什么**：测试可以直接 import 业务函数，
不需要启动 Streamlit；迁往 FastAPI 时业务模块无需改写。

## 4. 关键设计决策

以下 10 项决策是项目的架构基线。每条都记录了**放弃了什么**——
这比「选择了什么」更能说明架构的边界。

### D1. 单一 Streamlit 应用 + 分层 `src/` 模块，而非前后端分离 ✅

**理由**：第一版优先功能完整与运行稳定。Streamlit 单体省去跨进程通信、
CORS、构建链路，Windows 上 `streamlit run app.py` 即可演示。

**放弃了什么**：前端自由度与接真实 API 的天然边界。
缓解方式是保持 `src/` 内模块边界清晰，后续要拆 FastAPI，业务模块可原样搬走。

**备选**：FastAPI + React 前后端分离——视觉上限更高、更接近真实产品，
但对第一版的交付风险与维护成本明显更大。

### D2. 按职责切分模块，`app.py` 不含业务规则 ✅

见 [3.1 模块职责](#31-模块职责)。

### D3. 数据模型用 pydantic，但加载层容错优先于严格校验 ✅

**选择**：`Product` 用 pydantic 描述；加载时**逐条**校验，
单条失败只降级该条并记录，**不整批失败**。

**理由**：若用严格校验整批拒绝，一条坏数据就会让整个演示全废。

**权衡**：加载返回值需同时表达「商品」与「不完整商品」，
用统一的可选字段模型（必填字段缺失时置 `None` 并挂 `missing_fields`）避免引入第二个类型。

### D4. 评分权重集中在一张表里，按类别分维度 ✅

**选择**：`src/config.py` 定义 `SCORING_WEIGHTS: dict[str, dict[str, float]]`，
键为商品类别，值为「维度 → 权重」，同一类别内权重和为 1.0。

**理由**：权重不散落在多个文件中；不同商品类别可用不同维度和权重。

**权衡**：新增类别需在此表补一行。用一个测试断言
「每个类别的权重和等于 1.0」来防止漏配导致评分失真。

### D5. 大模型调用用 `httpx` 直连，不引入 SDK ✅

**选择**：向可配置的 `base_url` 发 OpenAI 兼容格式的 chat completions 请求。

**理由**：本机已有 `httpx`，不新增运行时依赖；OpenAI 兼容格式覆盖绝大多数
国内外模型服务。改用 SDK 需新增依赖且反而锁死端点兼容性。

**权衡**：失去 SDK 的类型与重试封装，需自己处理超时与响应解析。
缓解方式是把这些都收在 `ai_service.py` 内部，并用 stub 响应验证降级路径。

**默认值的绑定**：代码内置的 `DEFAULT_LLM_BASE_URL` / `DEFAULT_LLM_MODEL`
必须与 `.env.example` 登记值一致。二者漂移时，漏配环境变量的部署会静默打向
另一个服务商——请求失败，但错误信息里看不出「打错了地址」。
`tests/test_config.py` 用断言锁死这层绑定，改一边忘另一边会直接测试失败。

### D6. 需求解析双实现，共用同一个输出类型 ✅

**选择**：`demand_parser.parse(text) -> Demand`。
本地模式走正则/关键词规则；AI 模式走 `ai_service` 返回 JSON 再映射为同一个 `Demand`。
**两条路径产出一致，调用方不区分。**

**理由**：让上层（推荐、报告）完全不感知当前是哪种模式，降级变得无感。

**权衡**：规则解析召回率必然低于模型。缓解方式是规则聚焦
「预算数字 + 类别关键词 + 用途关键词」三类高频信息，
其余字段**留空**并由界面控件补齐——不是猜测填充。

### D7. SQLite 用标准库 `sqlite3`，不用 ORM ✅

**选择**：直接使用标准库，手写建表与查询，报告内容以 JSON 文本列存储。

**理由**：表结构只有两张，ORM 的抽象收益小于学习成本。
报告整段以 JSON 存储是为了满足「再次打开时还原当时结论」，
**避免用当前数据重算**。

**权衡**：手写 SQL 需自己防注入（统一参数化查询）。单机单用户场景并发压力可忽略。

### D8. 异常统一走 `errors.py` 的中文映射 ✅

**选择**：业务层抛领域异常（`DataFileMissing`、`InvalidBudget`、`AINotConfigured`、
`UpstreamTimeout` 等），`app.py` 在边界处捕获并查表取中文文案；
完整堆栈只写日志。

**理由**：不向普通用户暴露完整堆栈，且集中映射避免每个页面各写一遍文案。

**权衡**：比裸抛异常多一层间接。用映射表默认值兜底防止漏配导致白屏。

### D9. Streamlit 样式的克制策略 ✅

**选择**：通过 `.streamlit/config.toml` 的 `[theme]` 设主色、背景、字体，
辅以少量自有 class 的 CSS。**不注入依赖 Streamlit 内部类名的样式。**

**理由**：Streamlit 1.51 的内部类名（`st-emotion-cache-*`）每次发版都可能变，
绑上去等于给升级埋雷。

**权衡**：能改的细节比直接覆盖内部 CSS 少。接受这个限制，
把视觉重点放在卡片、表格、间距这些自己渲染的内容上。

### D10. 权限判定放在数据层入口，界面隐藏只是顺带 ✅

**选择**：三道，缺一不可——

1. `app.py` 的**入口短路**：未登录时不进入任何页面函数、不加载数据
2. 页面函数入口的 `require_admin()`（管理页自己的第一行）
3. **数据层写入口**的守卫：`set_user_role` / `set_user_password` /
   `set_user_active` / `set_category_meta` / `create_product` 等的 `viewer`
   是**必填关键字参数**，不是有默认值的可选参数

**理由**：在 Streamlit 里「隐藏按钮」根本不构成权限——页面函数之间会互相调用，
`session_state` 也能被脚本改写（页面名只是其中的一个字符串，改掉它就能让
应用跳到任何一个页面函数）。只隐藏入口的系统，手动改一下 `session_state`
就能越权。

**为什么 `viewer` 不设默认值**：默认值意味着漏传时静默放行，而那正是要防的
事。必填就会在开发期直接报错。

**测出来的东西**：有一条用例把 `session_state` 里的页面名改成「用户管理」
再渲染，断言拿到「没有执行该操作的权限」；另有一组在数据层直接调管理员
写函数，断言普通用户被拒且**不产生任何写入**。

**放弃了什么**：每个写函数都要多传一个参数，调用处略啰嗦。

## 5. 关键架构原则

| # | 原则 | 状态 | 落实方式 |
|---|---|---|---|
| 1 | 前端不直接连接数据库，也不保存模型 API 密钥 | ✅ | 密钥仅在服务端 `os.environ` |
| 2 | 商品查询和硬性条件筛选优先使用确定性代码 | ✅ | `recommender.py` 先过滤后排序 |
| 3 | 大模型负责理解和解释，**不负责凭空生成商品事实** | ✅ | `find_invented_prices()` 校验 |
| 4 | RAG 与商品数据库通过商品 ID、来源 ID 关联 | 📋 | — |
| 5 | Agent 只能调用明确注册、具参数验证和权限限制的工具 | 📋 | — |
| 6 | **AI 异常时，基础功能仍应可以使用** | ✅ | 四种失败路径均降级 |
| 7 | **界面隐藏不算权限，判定放在数据层入口** | ✅ | 见下 D10 |

> 原则 3 的具体体现：**AI 不参与排序**。评分与排序完全由本地规则完成，
> 模型只生成一段解释文字，且这段文字不写入历史报告——
> 报告保存的是规则算出的快照，不受模型波动影响。

## 6. 数据流

### 6.1 分析流程 ✅

```
用户输入（自然语言 / 结构化控件）
        ↓
   demand_parser.parse()          → Demand（品类/预算/用途/偏好/硬性条件）
        ↓
   recommender.filter()           → 硬性条件过滤（预算、品类）
        ↓
   scoring.score()                → 六维度加权评分（纯函数）
        ↓
   recommender.rank()             → 按匹配度排序（非价格）
        ↓
   report_service.build()         → DecisionReport（含评分构成与加减分项）
        ↓
   ai_enhance.explain()           → 可选：自然语言解读（价格校验后）
        ↓
   database.save()                → SQLite 快照存档
```

### 6.2 关键约束

| 环节 | 约束 |
|---|---|
| 解析 | 拿不准的字段**留空**，由界面追问，不猜测填充 |
| 过滤 | 超预算商品**单独列出**并标注超出金额，不混入正常结果 |
| 过滤 | 超预算列表有**独立**的展示上限，与「预算内推荐条数」互不影响 |
| 过滤 | 展示的条数用**真实总数**；只展示一部分时说明还有多少未列出 |
| 评分 | 数据缺失的维度**排除计算**并注明，不补默认分 |
| 排序 | 按需求匹配度，**不是按价格** |
| 解释 | AI 生成，价格校验失败即整条丢弃 |
| 存档 | 快照式，商品数据更新后不改动历史结论 |

### 6.3 目标态新增环节 📋

```
        ↑ 检索知识依据 ←── Chroma ←── knowledge_documents
        ↑
   Agent 编排：按需选择工具，而非固定顺序
        ↓
   search_products / filter_products / get_product_detail
   compare_products / search_knowledge / save_recommendation
```

Agent 需设置**最大工具调用次数、超时、异常处理和终止条件**，
避免陷入无限循环或不断重复查询。

## 7. 抗幻觉设计 ✅

这是本项目最核心的工程约束：**结构化数据必须由数据库提供，模型不能编造。**

### 7.1 AI 输出的四道校验

解读文本生成后依次过四道检查，**任一失败即丢弃该条、保留规则算出的结果**
（不整段失败）。总述与逐条解读走同一条链。

| # | 检查 | 实现 | 抓的是 |
|---|---|---|---|
| 1 | 价格 | `find_invented_prices()` | 顺口报一个数据里没有的价 |
| 2 | 参数数值 | `find_unsupported_spec_claims()` | 编一个重量、续航或容量 |
| 3 | 排他性结论 | `find_unsupported_claims()` | 「销量第一」「口碑最好」——断言的维度数据集根本没有 |
| 4 | 存疑属性 | `find_flagged_claims()` | 就记录内部矛盾的地方下结论 |

**容差设计**：参数数值用**相对容差**（2%）吸收四舍五入——`1.28 千克` 写成
`1.3 千克` 算对得上；但不容忍量级差异，`512GB` 写成 `1TB` 会被抓出来。
（曾用「按写法精度取半径」的方案，`1TB` 会得到 ±0.5TB 的容差而恰好包住 512GB，已废弃。）

**只查带单位的数值**：裸数字里混着序号、评分和年份，纳入校验会大量误杀。

**取不到数据就不判定**：某单位族在候选商品里完全没有数据时跳过——缺数据不等于编造。

### 7.2 数据侧与展示侧

| 防线 | 实现位置 | 机制 |
|---|---|---|
| 记录自相矛盾 | `consistency.check_product()` | 6 条高精度规则；命中则标「资料存疑」 |
| 存疑不影响评分 | `Product.data_issues` 为派生属性 | 数据质量问题不转嫁成商品劣势 |
| 存疑不排除商品 | `recommender` | 标记只提示核实，商品照常参与筛选与排序 |
| 存疑可追溯 | 卡片 / 比较页 / 报告 / CSV | 悬停看原因，导出保留整列 |
| 缺失即排除 | `scoring` | 无数据维度不计分并注明原因 |
| 排序隔离 | `recommender` + `scoring` | AI 不参与任何计算 |
| 快照存档 | `database` + `report_service` | 报告不含 AI 文字，模型波动不影响历史 |
| 空结果不伪造 | `recommender` | 无匹配时说明并给放宽建议 |
| 不暴露堆栈 | `errors` + `app.py` | 领域异常 → 中文文案，堆栈只进日志 |

> **一致性检测的规则为什么这么少**：一条不准的规则会把正常商品污名化，
> 比不做更糟。6 条规则全部经全量数据实测零误报，且都能识别否定表述——
> 数据里真实存在「无独显」「不可折叠」这类**正确的否定句**，
> 朴素关键词匹配会把它们判成矛盾。

## 8. 知识库层 ✅

### 8.1 在架构中的位置

```
用户提问
    ↓
src/ui/pages/knowledge.py     界面：输入、展示片段与来源
    ↓
src/knowledge/search.py       检索入口：阈值判定 + 片段抽取
    ↓
src/knowledge/index.py        倒排索引 + BM25 打分 + 类型/品类加权
    ↓
src/knowledge/corpus.py       语料加载（手写文档 + 商品级合成）
    ↓
data/knowledge/*.md + 商品数据
```

上层只依赖 `search_knowledge(query, *, index, ...) -> list[Passage]` 与 `Passage`。
**接口稳定是刻意的**（design.md D9）：将来若真要换成向量检索，替换实现即可，
调用方一行不用改。这个「双实现共用接口」的手法项目已有先例——
需求解析的规则实现与 AI 实现共用同一个 `Demand` 类型。

### 8.2 技术路线：不用向量库

| | 方案要求 | 实际采用 | 理由 |
|---|---|---|---|
| 索引 | Embedding + Chroma | **字符二元组 + BM25** | 零新增依赖、完全离线 |
| 切分 | 未指定 | 中文出二元组，拉丁数字出整词 | 不需要分词器就能匹配「降噪」与「主动降噪」 |
| 片段 | 未指定 | 按空行切段、按重合度排序取最相关段 | 整篇上千字，全展示等于没展示 |

**关键约束**：本项目的硬约束是「不配密钥、断网状态下全部功能可演示」。
向量检索需要调 embedding 接口，会把知识问答变成**没网就演示不了**的功能。

### 8.3 三层加权与两道取舍

检索得分 = BM25 原始分 × 类型系数 × 品类系数 × 品牌系数。

| 加权 | 目的 | 值 |
|---|---|---|
| 类型系数 | 通用问题（「怎么选」）命中选购指南，而不是某件具体商品 | 商品级 0.45，品类级/服务级 1.0 |
| 品类系数 | 用户点名了品类时，该品类资料优先 | 1.6 |
| 品牌系数 | 只问品牌（「华为怎么样」）也要有结果 | 3.0 |

**三者都是实测校准出来的，不是拍脑袋**。商品级系数压得太高，通用问题
（「怎么选」）会被同名的商品级条目顶掉、命中不了选购指南；压得太低，
具体商品查询又难命中。0.45 是在固定查询集上通过全部正例后的**最大取值**——
取通过值里最高的，压得比需要的更狠只会让具体商品查询更难命中。

品类加权针对的是语料之间的**无意字面碰撞**：某篇品类指南顺带提到另一个品类的
说法，问那个品类时它会被词频顶上去。

**品牌加权解决的是另一类失败**：品牌词只有两三个字，BM25 天然分低，
不加权会被相关度阈值直接挡掉——而用户点名品牌时想要的恰恰是那个品牌的商品。
它**带品类约束**：问「华为笔记本怎么样」时，加权只作用于笔记本条目，
不会把华为手机一起顶上来。

#### 两道取舍：绝对阈值管「有没有」，相对截断管「准不准」

| 取舍 | 常量 | 作用 |
|---|---|---|
| 绝对阈值 | `KNOWLEDGE_MIN_SCORE` | 判定这次检索**有没有**资料 |
| 相对截断 | `KNOWLEDGE_RELATIVE_CUT`（0.35） | 丢掉「与第一名差一个量级」的命中 |
| 条数上限 | `KNOWLEDGE_MAX_RESULTS`（3） | 单次返回上限 |

只看绝对阈值是不够的：它只能回答「有没有」，回答不了「后面那几条值不值得
交给模型」。实测中第一名 8.57 / 19.20 时，第二三名往往只有 4.13 / 1.26 这种
量级——把弱命中一并喂过去，只会稀释答案质量。相对截断就是针对这一点的：
**只保留与第一名同一量级的命中**。三个值都在 `config` 里，改完要拿固定
查询集重跑一遍基线（见 [testing.md §4.5](testing.md#45-知识检索回归基线-)）。

### 8.4 一条容易误当 bug 的性质

**BM25 的绝对分数随语料规模变化**（idf 依赖文档总数）。同一份资料，
在单文档索引里只得 2.0 分，在完整的生产语料（3 篇品类指南 + 1 篇 FAQ +
20 条商品级条目）里能得数倍于此的分。

因此**相关度阈值必须按真实语料规模校准**，小样本上试出来的值不能用。
已写成断言（`test_absolute_scores_depend_on_corpus_size`）钉住这条性质。

### 8.5 与抗幻觉的关系

知识库是 AI 的**外部依据**，但它不改变抗幻觉的基本立场：

- AI 作答的价格允许集取自**检索片段原文**（而非商品数据）——此处依据是片段
- 排他性结论复用同一张模式表（`find_unsupported_claims`），解读与问答不各写一份
- AI 问答页恒开 AI：未配置密钥时说明怎么配，调用失败时说明并建议重试，**不展示半成品**

## 9. Agent 编排层 ✅

### 9.1 在架构中的位置

```
用户问题
    ↓
src/ui/pages/analysis.py      AI 模式下走编排，否则走确定性管道
    ↓
src/agent/runner.py           编排循环 + 执行轨迹
    ↓
src/agent/registry.py         注册表：校验 → 分发（唯一的模型→业务通道）
    ↓
src/agent/tools.py            四个只读工具
    ↓
recommender / data_loader / comparison / knowledge.search
```

**关键：编排层的产出仍受抗幻觉防线约束。** 工具返回的是结构化数据或知识片段，
与本地模式用的是同一批；最终解释仍过 `ai_enhance` 的四道校验链。

### 9.2 唯一的模型→业务通道

模型只能调用注册表里的东西，且每次调用先过两层校验：

| 层 | 负责 | 拦什么 |
|---|---|---|
| 形状 | pydantic 参数模型 | 类型不对、缺必填、取值越界 |
| 语义 | 工具自己 | 品类不在已知类别内、商品 ID 不存在 |

**声明与校验同源**：OpenAI 的 `tools` 声明由 pydantic 模型的 JSON Schema 派生，
不会出现「声明说可选、校验说必填」的漂移。

**不做模糊纠正**：模型把品类写成「笔记本」而不是 `laptop`，直接拒绝并列出可用
类别，不替它猜。猜测纠正等于替模型圆场。

### 9.3 循环与终止

三个终止条件：模型给出回答 / 达到轮次上限（5） / 上游出错。

**达上限与上游出错的处理不同**：前者返回 `degraded=True` 的结果（那是设计内的
终止，不是异常）；后者原样抛领域异常，由界面在边界处统一捕获——整个项目只有
一处处理上游异常的出口。

### 9.4 执行轨迹

轨迹记录每一步真实发生过的调用：工具名、模型给的参数、结果摘要、状态。

**状态分三种**：`ok` / `rejected`（参数没按 schema 给）/ `error`（工具本身出错）。
分开是因为它们在轨迹里是**不同的信号**——前者说明提示词该改，后者说明代码该改。
混成一个颜色，看轨迹的人就分不清。

**被拒绝的调用同样入轨迹**。这不是失败展示，而是校验真的在拦的证据。

> 方案自己点名过：「这块最容易做成看起来像 Agent、实际只是聊天的形式。」
> 应对就是轨迹里只有真实调用。有一条测试断言「轨迹条数 == 实际调用次数」，
> 防止以后有人往里塞模型的思考文字。

### 9.5 与既有解读功能的分工

Agent 路径下**不再调用** `explain_recommendations`。两者都在生成自然语言解释，
同时跑会出现两段口径不同的说明——用户看到两个「为什么推荐」就砸了可解释性。
宁可少一段，不要两段打架。

## 10. 迁移路径

当前架构 → 目标架构不需要重写。映射关系：

| 当前 | 目标 | 改动量 |
|---|---|---|
| `src/config.py` | `backend/app/core/config.py` | 移动 |

| `src/scoring.py` `src/recommender.py` `src/comparison.py` | `backend/app/services/` | **原样搬走** |
| `src/demand_parser.py` `src/report_service.py` | `backend/app/services/` | 原样搬走 |
| `src/ai_service.py` `src/ai_enhance.py` | `backend/app/ai/llm_service.py` | 移动 |
| — | `backend/app/ai/rag_service.py` | 📋 新增 |
| — | `backend/app/ai/agent_service.py` `tools.py` | 📋 新增 |
| — | `backend/app/api/` | 📋 新增 |
| `src/ui/pages/` | `frontend/src/views/` | 重写 |
| SQLite | MySQL | 表结构见 [database.md](database.md) |

**建议的迁移顺序**：

1. 先补 RAG 与 Agent（**在有界面的情况下验证**，反馈最快）
2. 再抽 FastAPI（业务逻辑此时已稳定，搬家风险最低）
3. 最后重写前端

> ⚠️ 反过来做（先拆 FastAPI + Vue）会消耗数周在不产出新能力的工作上，
> 且在新架构上调试 RAG/Agent 的迭代速度远低于在 Streamlit 上。
