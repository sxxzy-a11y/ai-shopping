# 需求规格说明书

> **智购参谋 —— 基于 RAG 与 Agent 的智能消费决策助手**
> 英文名：SmartBuy AI Assistant

**状态标记**：✅ 已实现 ｜ 🚧 开发中 ｜ 📋 规划中

---

## 1. 项目背景

### 1.1 消费者面临的问题

线上商品种类不断增加，消费者在购物时经常面临以下问题：

| # | 问题 | 具体表现 |
|---|---|---|
| 1 | 商品种类多、参数复杂 | 难以快速找到适合自己的产品 |
| 2 | 参数口径不统一 | 不同品牌的商品参数各有各的说法，横向比较困难 |
| 3 | 需求难以结构化 | 用户的需求往往是自然语言表达的，不容易直接转换成筛选条件 |
| 4 | 大模型不可信 | 通用大模型可能给出缺乏数据依据的推荐，甚至生成错误的价格和参数 |
| 5 | 信息不对称 | 用户往往只能看到商品的宣传信息，难以判断产品是否真正符合自己的需求 |

### 1.2 现有方案的空隙

| 方案类型 | 解决了什么 | 没解决什么 |
|---|---|---|
| 传统电商平台 | 商品展示、搜索、交易 | 不帮你做**决策**，只是把商品摆出来 |
| 通用 AI 聊天工具 | 能理解用户需求 | 不掌握**准确、完整的商品数据**，容易编造价格参数 |
| 商品比价工具 | 价格对比 | 只比价格，不结合**你的使用场景和偏好** |

**本项目要填的正是这个中间地带**：一个既掌握结构化商品数据、
又能理解自然语言需求、还能给出可解释推荐理由的决策系统。

### 1.3 项目不是做什么

项目**不是**给电商平台加一个聊天窗口。区别在于：

- 聊天窗口：用户问什么，模型凭记忆答什么
- 本项目：用户提需求 → 系统在**真实数据结构**上筛选 → 按**明确规则**排序 →
  结合**可追溯的知识**解释 → 全程保留依据

---

## 2. 项目目标

构建一个能完成以下任务的智能消费决策系统：

| # | 目标 | 状态 |
|---|---|---|
| 1 | 理解用户以自然语言表达的消费需求 | ✅ |
| 2 | 将模糊需求转换为明确的预算、用途和筛选条件 | ✅ |
| 3 | 从商品数据库中查找符合条件的候选商品 | ✅ |
| 4 | 通过 RAG 检索商品知识和选购资料 | 📋 |
| 5 | 综合考虑预算、参数、用户偏好和商品优缺点 | ✅ |
| 6 | 调用后端工具完成查询、筛选和比较 | 🚧 |
| 7 | 生成有数据依据的推荐结果，并解释推荐理由 | ✅ |
| 8 | 保留推荐依据和数据来源，降低错误推荐风险 | 🚧 |

---

## 3. 项目范围

首个参赛版本**聚焦消费决策**，不做完整电商交易系统。

| ✅ 纳入本期开发 | ❌ 暂不纳入 |
|---|---|
| AI 自然语言导购 | 完整支付系统 |
| 商品搜索与筛选 | 购物车和订单交易闭环 |
| 商品参数横向对比 | 复杂商家运营后台 |
| RAG 商品知识问答 | 全网实时爬虫系统 |
| Agent 工具调用 | 自动发放优惠券 |
| 可解释的推荐报告 | 大规模多商家入驻 |
| 推荐历史与反馈 | 复杂的用户画像平台 |

**范围裁剪的理由**：完整商城闭环（支付、订单、库存、售后）是**电商**问题，
不是**消费决策**问题。把精力集中在决策链路上，才能把 AI 技术做深而不是做宽。

## 4. 核心用户

| 用户类型 | 特征 | 核心诉求 |
|---|---|---|
| 参数小白 | 对商品参数不熟悉，看不懂规格表 | 用大白话告诉我该买哪个 |
| 预算明确型 | 有明确预算，但不知道如何选择 | 在这个价位里哪个最合适 |
| 选择困难型 | 已经挑出几个候选，决定不了 | 帮我比较，告诉我差在哪 |
| 谨慎研究型 | 希望了解优缺点、使用场景和选购注意事项 | 给我依据，别只给结论 |

## 5. 典型使用场景

### 场景一：自然语言选购 ✅

**用户输入**
> 我想买一款 500 元以内的耳机，主要用于通勤，降噪要好，佩戴要舒服。

**系统处理**：提取预算、使用场景和偏好 → 筛选候选商品 → 检索相关资料 → 给出推荐。

**需求解析结果**

| 字段 | 值 |
|---|---|
| 商品品类 | 耳机 |
| 预算上限 | 500 元（**硬性约束**） |
| 使用场景 | 通勤 |
| 重要偏好 | 降噪效果、佩戴重量（**软性偏好**） |

### 场景二：多商品对比 ✅

**用户输入**
> 帮我比较这三款耳机，重点看降噪、续航、佩戴舒适度和价格。

**系统处理**：提取结构化参数 → 展示对比表 → 标记缺失数据 → 解释不同商品的适用人群。

**约束**：比较限定在同一类别内。先选类别，再从该类别里挑商品，
跨类别混选会被拒绝——衣服和电脑比性价比没有意义。

### 场景三：商品知识问答 📋

**用户输入**
> 主动降噪和被动降噪有什么区别？我通勤应该关注什么？

**系统处理**：从选购知识库中检索相关资料，结合用户场景给出回答和参考来源。

> ⚠️ **依赖 RAG，当前尚未实现。** 系统目前无法回答此类商品知识问题。

### 场景四：多步骤智能决策 🚧

**用户输入**
> 给我推荐三款适合地铁通勤的耳机，预算不超过 500 元，最好续航长、降噪好。

**系统处理**：解析条件 → 查询商品 → 检索知识 → 比较候选项 → 生成推荐报告。

> 🚧 当前由**确定性管道**完成，步骤顺序写死在代码里，尚不是 Agent 自主决策。

## 6. 功能需求

六个功能模块。详细规格见 [`openspec/specs/`](../openspec/specs/)（11 份能力规格，
59 条需求，186 条可测试场景）。

### FR-1 商品中心 🚧

| 编号 | 需求 | 状态 |
|---|---|---|
| FR-1.1 | 按名称、品牌和关键词搜索 | ✅ |
| FR-1.2 | 按价格区间筛选 | ✅ |
| FR-1.3 | 按关键参数筛选 | ✅ |
| FR-1.4 | 查看商品资料来源和更新时间 | ✅ |
| FR-1.5 | 查看商品详情 | 🚧 在推荐卡片与比较页内展开，无独立详情页 |
| FR-1.6 | 商品列表与分类展示 | 📋 无可浏览的商品目录页 |
| FR-1.7 | 独立商品详情页 | 📋 |

**商品详情应展示**：名称、品牌和型号 · 商品图片 · 记录中的价格及其更新时间 ·
关键规格和参数 · 商品介绍 · 适用场景 · 优点与不足 · 数据来源及缺失信息提示。

> **验收要求**：用户输入价格上限后，系统返回的商品必须满足价格筛选条件。
> **没有价格数据的商品不应默认视为符合预算。**

### FR-2 AI 智能导购 ✅

这是项目的核心交互模块。用户不需要先学习商品分类和参数，只需要说出自己的需求。

| 编号 | 需求 | 状态 |
|---|---|---|
| FR-2.1 | 识别商品品类 | ✅ |
| FR-2.2 | 提取预算范围 | ✅ |
| FR-2.3 | 识别使用场景 | ✅ |
| FR-2.4 | 提取重要参数和偏好 | ✅ |
| FR-2.5 | 识别硬性条件与软性偏好 | ✅ |
| FR-2.6 | 判断条件是否足够明确 | ✅ |
| FR-2.7 | 必要时向用户追问（只问缺的那项） | ✅ |
| FR-2.8 | 根据结构化条件检索商品 | ✅ |
| FR-2.9 | 返回候选商品和推荐理由 | ✅ |

> **硬性约束必须优先执行**：对于「500 元以内」这类条件，系统必须先筛选再排序；
> 不能因为某款商品在其他方面表现好，就推荐超过预算的商品。

### FR-3 商品比较 ✅

| 编号 | 需求 | 状态 |
|---|---|---|
| FR-3.1 | 支持 2–5 件商品横向比较 | ✅ |
| FR-3.2 | 限定同一类别内比较 | ✅ |
| FR-3.3 | 对比维度按品类自动适配 | ✅ |
| FR-3.4 | 标记关键差异 | ✅ |
| FR-3.5 | 展示各商品的优势和不足 | ✅ |
| FR-3.6 | 标注数据缺失，不用其他商品的值填充 | ✅ |
| FR-3.7 | 针对不同使用场景给出建议 | 📋 |

> **不能把未知参数当成零，也不能把没有资料证明的特点当成商品优势。**

### FR-4 知识问答（RAG）✅

| 编号 | 需求 | 状态 |
|---|---|---|
| FR-4.1 | 建立三类知识库：商品级、品类级、服务级 | ✅ 商品级由商品字段合成，不写文件 |
| FR-4.2 | 文档切分、索引与检索 | ✅ **字符二元组 + BM25**，非向量化（见下） |
| FR-4.3 | 用户提问时检索相关片段 | ✅ |
| FR-4.4 | 每条知识记录来源、文档类型、关联商品、更新时间 | ✅ front-matter 承载 |
| FR-4.5 | 回答时展示资料来源 | ✅ 标题 · 类型 · 来源 · 更新时间 |
| FR-4.6 | 检索不到可靠证据时明确说明，不生成虚假引用 | ✅ 低于阈值即判定检索不到，不展示任何来源 |
| FR-4.7 | 价格类问题不走检索 | ✅ 改为引导到商品筛选 |

> **FR-4.2 与方案不同**：方案要求 Embedding + Chroma 向量检索，本项目改用
> 字符二元组 + BM25。理由是用向量检索会让知识问答**必须联网**，
> 与「断网也能完整演示」这条硬约束冲突，且需新增两个依赖。
> 取舍与实测数据见 [architecture.md](architecture.md) 与 README 第七章。
>
> 用户询问商品具体参数时，应优先使用对应商品的资料；
> 检索不到可靠证据时，应说明暂时无法确认。

### FR-5 决策记录 ✅

| 编号 | 需求 | 状态 |
|---|---|---|
| FR-5.1 | 保存用户查询条件、候选商品 ID、推荐结果、所用资料来源 | ✅ |
| FR-5.2 | 同一组条件重复提交只存一条 | ✅ |
| FR-5.3 | 报告为快照，商品数据更新后不改动历史结论 | ✅ |
| FR-5.4 | 从列表重新打开当时的完整报告 | ✅ |
| FR-5.5 | 收藏商品 | ✅ |
| FR-5.6 | 用户反馈（`recommendation_feedback`） | 📋 |

> 初期只保存必要的匿名会话记录，不必一开始开发复杂的用户账号体系。

### FR-6 数据管理 🚧

| 编号 | 需求 | 状态 |
|---|---|---|
| FR-6.1 | 导入 CSV 商品文件 | ✅ |
| FR-6.2 | 检查必填字段和数据格式 | ✅ |
| FR-6.3 | 识别重复商品（按 ID，不只依赖名称） | ✅ |
| FR-6.4 | 更新价格和商品参数 | ✅ |
| FR-6.5 | 查看数据来源及更新时间 | ✅ |
| FR-6.6 | 查看导入失败记录 | ✅ |
| FR-6.7 | 图形化的数据管理页 | 📋 |
| FR-6.8 | 重新生成或更新知识库索引 | 📋 |

> 这一模块对参赛作品很重要——它证明系统不是只依赖提示词，
> 而是有实际的数据管理能力。

### FR-7 Agent 工具编排 ✅

| 编号 | 需求 | 状态 |
|---|---|---|
| FR-7.1 | 提供只读工具：商品筛选、商品详情、多商品比较、知识检索 | ✅ 四个 |
| FR-7.2 | 模型自主决定调用哪些工具、按结果继续推进 | ✅ |
| FR-7.3 | 工具参数经过程序化校验（形状 + 语义两层） | ✅ |
| FR-7.4 | 禁止执行模型生成的任意 SQL、禁止越权工具 | ✅ 根本不存在此类工具 |
| FR-7.5 | 设置轮次上限、超时与终止条件 | ✅ 上限 5 轮 |
| FR-7.6 | 记录并展示工具执行轨迹 | ✅ 工具名 · 参数 · 结果摘要 · 状态 |
| FR-7.7 | 编排失败降级回确定性管道，结果不空白 | ✅ |

> **FR-7.1 的只读是硬性的**：工具集里不存在修改商品数据、写数据库或对外
> 发起请求的工具。「禁止执行任意 SQL」在本项目里的实现比「禁止」更彻底。
>
> **参数校验不做模糊纠正**：模型给错就回灌错误让它重来。猜测纠正等于替模型
> 圆场，会掩盖它没按 schema 给值的事实。
>
> 详细设计与边界见 [architecture.md](architecture.md) 与 README 第八章。

## 7. 非功能需求

### NFR-1 可解释性 ✅

每个推荐结果必须展示：为什么推荐 · 哪些方面符合用户需求 · 哪些方面存在不足 ·
哪些信息尚未核验。评分的每个维度得分、权重与计算依据都可展开查看。

### NFR-2 数据可追溯 🚧

| 编号 | 需求 | 状态 |
|---|---|---|
| NFR-2.1 | 每条商品记录有数据来源说明 | ✅ |
| NFR-2.2 | 每条商品记录有更新时间 | ✅ |
| NFR-2.3 | **逐条**原始资料链接（`source_url`） | 📋 |
| NFR-2.4 | 数据核验状态（`data_status`） | 📋 |
| NFR-2.5 | 价格专有时效戳（`price_updated_at`） | 📋 |
| NFR-2.6 | 独立的数据来源表（含许可说明） | 📋 |

> ⚠️ **当前障碍**：112 条商品的 `data_source` 是同一串免责说明，
> `updated_at` 同为一天。「点开推荐依据看到不同来源」目前**演示不出差异**。

### NFR-3 抗幻觉 ✅

大模型**不得**凭空决定价格、规格或库存。

| 防线 | 实现 |
|---|---|
| 价格校验 | `find_invented_prices()` 校验 AI 解读中的每个价格是否来自传入数据 |
| 对不上就丢弃 | 校验失败时整条解读作废，不展示给用户 |
| AI 不参与排序 | 评分与排序完全由本地规则完成 |
| 不写入历史 | 报告保存的是规则算出的快照，不受模型波动影响 |
| 缺数据即排除 | 数据缺失的维度排除计算并注明，不补默认分 |

### NFR-4 可用性降级 ✅

**AI 接口异常时，商品搜索和参数比较等基础功能仍应可以使用。**

不配密钥、模型超时、返回空正文、返回编造价格——四种情况下，
应用都能自动降级到本地规则模式，并明确告知用户当前处于哪种状态。

### NFR-5 密钥安全 ✅

密钥只从环境变量读取 · `.env` 已在 `.gitignore` 中排除 ·
日志与异常信息中的密钥替换为 `sk-****` · 界面只显示脱敏片段 ·
启用 AI 前列出将要发送的数据由用户确认。

## 8. 开发原则

贯穿项目始终的约束：

1. 分阶段开发，每个阶段独立可运行，**不允许一次性生成整个项目**
2. 编写代码前先检查现有目录、文件和环境，**禁止未经确认覆盖已有成果**
3. 复杂功能拆分为独立模块，不把所有代码写进 `main.py`
4. 每个阶段完成后运行相关测试，并说明测试结果
5. 遇到错误时先定位原因，**不通过删除功能或绕过校验来解决问题**
6. 不擅自增加优惠券、完整支付系统、复杂商城交易等本期不需要的功能
7. **不声称未实现或未测试的功能已经完成**
8. 商品价格、参数等结构化数据必须由数据库或经过验证的数据接口提供
9. 知识库缺少证据时应明确说明，不得生成虚假的来源或引用
10. 缺失参数应明确标记，**不得默认其满足条件**
