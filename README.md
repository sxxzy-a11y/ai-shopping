# 智购参谋 · 基于 RAG 与 Agent 的智能消费决策助手

> **SmartBuy AI Assistant** —— 帮你在预算内买到真正适合自己的商品，
> 并且告诉你这个结论**是怎么得出来的**。

它不是聊天机器人，也不是商品列表。它做的是完整的决策链路：

```
听懂需求 → 筛选候选 → 按需求匹配度打分排序 → 多商品横向比较
        → 检索知识依据 → 给出可解释的推荐 → 保存决策记录
```

## 1. 快速开始

### 1.1 环境要求

- **Windows 10/11**（macOS / Linux 同样可用）
- **Python 3.10 或更高**（开发与验证环境为 Python 3.13.9）

```bash
python --version
```

### 1.2 安装依赖

```bash
pip install -r requirements.txt
```

会安装 5 个包：`streamlit`、`pandas`、`pydantic`、`httpx`、`pytest`。

### 1.3 启动应用

```bash
streamlit run app.py
```

浏览器会自动打开 <http://localhost:8501>。如果没自动打开，手动访问该地址即可。

**这一步不需要任何 API 密钥**，应用会以[本地演示模式](#3-两种运行模式)运行，全部功能可用。

**首次启动会创建初始管理员**，账号与密码取自 `ZHIGOU_ADMIN_USERNAME` /
`ZHIGOU_ADMIN_PASSWORD`；没配的话会生成一个随机密码并**在终端打印一次**，
请登录后立即修改（见[附录 G](#附录-g--账号与权限)）。

> ⚠️ **演示时请只绑定本机地址，不要暴露到公网。** 注册是开放的：任何能访问到
> 这个地址的人都能创建账号并进入。账号体系只做到「演示级鉴权」，
> 没有限流、没有会话过期，不该拿它对外提供任何真实服务。

### 1.4 停止应用

在运行它的终端窗口按 `Ctrl + C`。

### 1.5 常用命令

| 目的 | 命令 |
|---|---|
| 跑全部测试 | `pytest` |
| 只跑推荐逻辑 | `pytest tests/test_recommender.py` |
| 只跑端到端验收 | `pytest tests/test_acceptance.py` |
| 验证 AI 通路（**会联网并消耗额度**） | `python -c "from src import ai_service; print(ai_service.probe())"` |
| 生成商品导入模板 | `python scripts/fetch_products.py --write-template data/platform_export.csv` |
| 试跑一次数据导入 | `python scripts/fetch_products.py --source csv --input data/platform_export.csv --dry-run` |
| 换端口启动 | `streamlit run app.py --server.port 8502` |

## 2. 环境变量

把 `.env.example` 复制为 `.env` 后按需填写：

```bash
cp .env.example .env        # Git Bash / macOS / Linux
copy .env.example .env      # Windows CMD
```

### 2.1 大模型（可选）

| 变量 | 默认值 | 说明 |
|---|---|---|
| `ZHIGOU_LLM_API_KEY` | 空 | API 密钥。留空即本地演示模式 |
| `ZHIGOU_LLM_BASE_URL` | `https://api.deepseek.com/v1` | OpenAI 兼容的服务端点 |
| `ZHIGOU_LLM_MODEL` | `deepseek-flash` | 模型名 |
| `ZHIGOU_LLM_TIMEOUT` | `60` | 单次请求超时秒数，超时自动降级 |
| `ZHIGOU_LLM_MAX_TOKENS` | `2000` | 单次回复 token 上限，见下方说明 |

代码内置的默认值与 `.env.example` **保持一致**，并由测试锁死：
改任何一边忘另一边，`pytest` 会直接失败。

本项目用 `httpx` 直连 OpenAI 兼容接口，**换服务商只需要改环境变量**，不用动代码。

> **推理模型的 token 上限要注意**
>
> `deepseek-flash`、`deepseek-v4-pro` 这类推理模型，**推理过程也计入 `max_tokens`**。
> 上限给小了会出现「推理把额度用光、正文为空」的情况。
> 应用会把它当作失败并降级到本地规则模式，不会把空结果当成有效答案。
> 遇到提示「推理过程用尽了 token 额度」时，把 `ZHIGOU_LLM_MAX_TOKENS` 调大即可。

### 2.2 本地路径（通常不用改）

| 变量 | 默认值 |
|---|---|
| `ZHIGOU_PRODUCTS_DB_PATH` | `<项目根>/storage/products.db` |
| `ZHIGOU_DB_PATH` | `<项目根>/storage/zhigou.db` |
| `ZHIGOU_PRODUCTS_PATH` | `<项目根>/data/products.json`（**种子数据**，库为空时才读） |
| `ZHIGOU_SETTINGS_PATH` | `<项目根>/storage/settings.json` |

### 2.3 关于密钥安全

- 密钥**只从环境变量读取**，不写进任何源码文件
- `.env` 已在 `.gitignore` 中排除，不会被提交
- 日志与异常信息里的密钥会被替换成 `sk-****`
- 界面上只显示「已配置」和脱敏片段，不回显明文
- AI 增强的启停在「个人设置」（全局开关，默认开启）；开启时界面常驻说明**将要发送哪些数据**

## 3. 两种运行模式

|  | 本地演示模式 | AI 增强模式 |
|---|---|---|
| 需要密钥 | 不需要 | 需要 |
| 联网 | **完全不联网** | 会调用你配置的模型服务 |
| 需求理解 | 本地规则（预算、类别、用途、核心需求） | 大模型理解，能处理更口语化的表达 |
| 推荐解读 | 只给评分构成与加减分项 | 额外给一段自然语言解读 |
| 计算推荐排序 | 本地规则 | 本地规则（**AI 不参与排序**） |

**默认就是本地演示模式。** 在 `.env` 里填上密钥即自动进入 AI 增强模式，
界面上的 AI 开关需要你手动打开才会真正调用模型。

> **这不是降级方案，而是刻意设计。**
> 比赛现场网络不可靠是常态——本项目的整套核心演示**全程不需要网络**。

## 一、项目定位

### 1.1 项目名称

**智购参谋 —— 基于 RAG 与 Agent 的智能消费决策助手**
英文名：SmartBuy AI Assistant

### 1.2 项目背景

线上商品种类不断增加，消费者在购物时经常面临这些问题：

- 商品种类多、参数复杂，难以快速找到适合自己的产品
- 不同品牌的商品参数不统一，横向比较困难
- 用户的需求往往是自然语言表达的，不容易直接转换成筛选条件
- 通用大模型可能给出缺乏数据依据的推荐，甚至生成错误的价格和参数
- 用户往往只能看到商品的宣传信息，难以判断产品是否真正符合自己的需求

传统电商平台主要解决商品展示、搜索和交易问题；普通 AI 聊天工具虽然能理解
用户需求，却不一定掌握准确、完整的商品数据。本项目要填的正是这个中间地带。

### 1.3 项目目标

项目不是给电商平台加一个聊天窗口，而是构建一个能完成以下任务的决策系统：

1. 理解用户以自然语言表达的消费需求
2. 将模糊需求转换为明确的预算、用途和筛选条件
3. 从商品数据库中查找符合条件的候选商品
4. 通过 RAG 检索商品知识和选购资料
5. 综合考虑预算、参数、用户偏好和商品优缺点
6. 调用后端工具完成查询、筛选和比较
7. 生成有数据依据的推荐结果，并解释推荐理由
8. 保留推荐依据和数据来源，降低错误推荐风险

### 1.4 项目范围

首个参赛版本**聚焦消费决策**，不做完整电商交易系统。

| ✅ 纳入本期开发 | ❌ 暂不纳入 |
|---|---|
| AI 自然语言导购 | 完整支付系统 |
| 商品搜索与筛选 | 购物车和订单交易闭环 |
| 商品参数横向对比 | 复杂商家运营后台 |
| RAG 商品知识问答 | 全网实时爬虫系统 |
| Agent 工具调用 | 自动发放优惠券 |
| 可解释的推荐报告 | 大规模多商家入驻 |
| 推荐历史与反馈 | 复杂的用户画像平台 |

## 二、核心用户与使用场景

### 2.1 目标用户

| 用户类型 | 特征 | 核心诉求 |
|---|---|---|
| 参数小白 | 对商品参数不熟悉，看不懂规格表 | 用大白话告诉我该买哪个 |
| 预算明确型 | 有明确预算，但不知道如何选择 | 在这个价位里哪个最合适 |
| 选择困难型 | 已经挑出几个候选，决定不了 | 帮我比较，告诉我差在哪 |
| 谨慎研究型 | 希望了解优缺点、使用场景和选购注意事项 | 给我依据，别只给结论 |

### 2.2 典型使用场景

| 场景 | 用户输入 | 系统处理 | 状态 |
|---|---|---|---|
| **自然语言选购** | 「我想买一款 5000 元以内的笔记本，主要用来编程，续航要好，要轻一点」 | 提取预算、使用场景和偏好，筛选候选，检索资料，给出推荐 | ✅ |
| **多商品对比** | 「帮我比较这三款手机，重点看芯片、续航、拍照和价格」 | 提取结构化参数，展示对比表，标记缺失数据，解释适用人群 | ✅ |
| **AI 商品知识问答** | 「笔记本多重适合带出门？编程该看什么参数？」 | 从知识库检索资料并由 AI 组织成回答；**只展示回答，不展示片段与来源** | ✅ |
| **多步骤智能决策** | 「给我推荐三款适合编程的笔记本电脑，预算不超过 6000 元」 | 解析条件 → 查询商品 → 检索知识 → 比较候选项 → 生成推荐报告 | 🚧 |

> 🚧 说明：当前「多步骤决策」由**确定性管道**完成（解析 → 筛选 → 评分 → 解释），
> **AI 增强模式下**已可自主决策：见[第八章](#八agent-智能决策-)。
> 本地模式仍走确定性管道——那是断网时的保障。

### 2.3 需求解析示例

用户说：「想买一台办公用的笔记本，最好轻一点，续航强，5000 元以内」

| 字段 | 解析结果 |
|---|---|
| 商品品类 | 笔记本电脑 |
| 预算上限 | 5000 元（**硬性约束**） |
| 使用场景 | 办公 |
| 重要偏好 | 便携性、续航（**软性偏好**） |

> 对于「500 元以内」这种硬性条件，系统**必须先筛选，再进行推荐排序**；
> 不能因为某款商品在其他方面表现好，就推荐超过预算的商品。

### 3.1 商品中心 🚧

| 能力 | 状态 | 说明 |
|---|---|---|
| 按名称、品牌和关键词搜索 | ✅ | 需求解析层支持品牌偏好与关键词识别 |
| 按价格区间筛选 | ✅ | 硬性条件优先过滤 |
| 按关键参数筛选 | ✅ | 评分维度按品类自适应 |
| 查看商品详情 | 🚧 | 在推荐卡片与比较页内展开，**无独立详情页** |
| 查看数据来源和更新时间 | ✅ | 界面与导出报告都会展示 |
| 商品缩略图 | ✅ | 有图片时显示实物图；缺图或图片加载失败时**回落成类别图标**，不出现破图 |
| 暂不支持的品类提示 | ✅ | 提到冰箱、平板、耳机这类表外品类时，明确回复只支持笔记本电脑、手机 |
| 商品列表与分类展示 | 📋 | **无可浏览的商品目录页**，首页是需求驱动入口 |

**验收要求**：用户输入价格上限后，返回的商品必须满足价格筛选条件。
**没有价格数据的商品不应默认视为符合预算。**

### 3.2 AI 智能导购 ✅

项目的核心交互模块。用户不需要先学习商品分类和参数，只需说出自己的需求。

系统需要完成：

1. 识别商品品类
2. 提取预算范围
3. 识别使用场景
4. 提取重要参数和偏好
5. 识别硬性条件与软性偏好
6. 判断条件是否足够明确
7. 必要时向用户追问
8. 根据结构化条件检索商品
9. 返回候选商品和推荐理由

需求解析示例见 [2.3](#23-需求解析示例)。实现落点：`src/demand_parser.py`（594 行）。

### 3.3 商品比较 ✅

在同一类别内选 2–5 件商品横向对比：先选类别，再从该类别里挑
（衣服和电脑比性价比没有意义，跨类别混选会被拒绝）。

对比维度**按品类自动决定**——笔记本比处理器和重量，手机比芯片和影像。结果包含：

- 参数对比表
- 关键差异标记
- 各商品的优势和不足
- 用户需求匹配程度
- 数据缺失提示

> **不能把未知参数当成零，也不能把没有资料证明的特点当成商品优势。**
> 缺失数据一律标注为「信息缺失」，不用其他商品的值填充。

### 3.4 AI 问答（RAG）✅

输入商品知识类问题，系统从知识库检索资料，再由 AI 组织成回答；**检索片段与来源不在界面展示**，只作为作答依据（回答只依据片段，价格与排他性结论有强制校验兜底）。
该页恒开 AI——未配置密钥时说明如何配置，作答失败时说明并建议重试，不展示半成品。
价格与参数类问题会被引导到商品筛选，不走问答——检索按文本相关性找资料，不理解数值约束。

## 五、商品数据方案

### 5.1 数据的存放与获取

| 数据类型 | 存放位置 | 获取方式 | 状态 |
|---|---|---|---|
| 商品型号、价格、参数 | **SQLite 商品数据库** `storage/products.db` | 手动核实录入、导入 CSV/JSON | ✅ 已落地 |
| 官方产品说明、选购知识 | 知识文档 `data/knowledge/` 及检索索引 | 整理官方公开资料 | ✅ 已落地 |
| 数据来源、核实时间 | 商品记录（`products`）**及价格记录**（`product_prices`） | 录入时一并保存 | ✅ 机制就绪，**当前数据如实标为未核验** |
| 推荐评分和筛选条件 | 推荐逻辑及推荐历史 `storage/zhigou.db` | 程序计算并记录 | ✅ 已落地 |

**商品库与历史库是两个文件，这是有意的。** 共用一个文件时，文件一旦损坏，
商品数据与历史会同时读不出来，整个应用直接不可用；分开之后损坏是局部的——
历史坏了仍能做分析，商品库坏了历史仍在。

> ⚠️ **「机制就绪」不等于「来源核验过了」。** 第三行的字段与流程都已建好，
> 当前 20 条全部带 `source_url`。字段仍可空——取不到来源时留空，如实表达
> 「没找到来源」，而不是补一个打不开的链接。核验状态一律为**未核验**。
> 它会如实显示在界面与导出结果里，不会因为「字段有了」就标成已核实。

**当前数据状态**：20 条商品的 `data_source` 统一为
「公开资料整理 · 参数经简化，价格非实时」，`data_status` 一律为 **unverified（未核验）**。
价格是参考价、不是实时价，会随促销波动——这些口径都会如实显示，不冒充实时数据。

### 5.2 数据来源的优先级

按以下优先级准备数据：

| 优先级 | 来源 | 状态 |
|---|---|---|
| 1 | 公开或授权的数据集（许可范围明确，记录来源与许可条件） | 📋 |
| 2 | 厂商公开产品资料（官网、官方说明书，保留原始来源链接） | ✅ 当前数据：按公开资料整理 |
| 3 | 人工整理的样例数据（必须明确标注，不得伪装成实时价格） | — |
| 4 | 后续扩展授权 API（需要价格或库存更新时接入） | 🚧 通道已建 |

> 商品图片、产品介绍和用户评价也要考虑版权、使用条款及个人信息保护。
> 公开可访问不代表可以不受限制地批量抓取和使用。

**当前数据状态**：20 条商品均为第 2 类，按公开资料整理——
`data_source` 统一为「公开资料整理 · 参数经简化，价格非实时」，
`data_status` 一律为未核验；20 条全部带 `source_url`。
品牌与型号真实可查，但价格是参考价、参数经简化，不等于厂商实时数据。
逐条来源已可演示，见[第十四章创新点二](#创新点二rag-与结构化商品数据协同-)。

### 5.3 数据量规划

| 阶段 | 商品数量建议 | 状态 |
|---|---:|---|
| 接口开发 | 20–30 款 | ✅ 当前 30 款 |
| AI 功能开发 | 50–100 款 | 🚧 当前 30 款 |
| 比赛演示 | 100–300 款 | 🚧 当前 30 款 |
| 扩展阶段 | 1,000 款以上 | 📋 |

首期选一个品类更容易保证数据质量。即使有 300 款商品，如果大量商品缺失价格、
型号或关键参数，推荐效果仍然会很差。

**品类收缩后**，数据集定为两个品类、每类 10 款、共 20 条真实机型——
宁可少而准，也不凑数——品类只保留能凑齐 10 款**真实机型**的笔记本电脑与手机，
键盘与耳机因品类聚焦先后移除。
当前 2 个品类的分布见[附录 A](#附录-a--商品品类)。

## 七、AI 问答（RAG）

> **状态：✅ 已实现** —— 变更 `add-knowledge-base` 交付。
> **技术路线与方案不同**：不用 Chroma、不用 embedding 接口，
> 见 7.2 的理由。

### 7.1 知识库构成

```
data/knowledge/
├── faq.md                    服务级：术语解释、系统能力与数据限制
└── category/<品类>.md        品类级：2 份选购指南（笔记本 / 手机）

商品级条目                      由商品字段在构建索引时合成，不写文件
```

语料共 **3 篇**（2 篇品类选购指南 + 1 篇 FAQ）；键盘与耳机指南随品类移除。
索引文档总数 = 3 篇语料 + 20 条商品级条目。

每份手写文档带 front-matter：`title` / `type` / `category` / `source` / `updated_at`，
对应需求要求的「来源、文档类型、关联商品 ID、更新时间」。

**商品级为什么不写文件**：同一事实只保留一处来源。写 30 份介绍文档意味着
改一处忘另一处的失同步几乎必然发生——而抗幻觉防线里的矛盾检测，
盯的正是这类问题。合成则商品数据改了知识库自动跟着变。

### 7.2 检索方式：字符二元组 + BM25（**不引入向量库**）

| | 方案要求的做法 | 本项目实际做法 |
|---|---|---|
| 索引 | Embedding + Chroma 向量检索 | 字符二元组 + BM25，**纯标准库** |
| 依赖 | 新增 Chroma、LangChain | **零新增**，仍是原有 5 个 |
| 联网 | 调 embedding 接口，**必须联网** | **完全离线** |

**为什么改**：用向量检索等于把知识问答变成「没网就演示不了」的功能，
而本项目最大的保障恰恰是**断网也能完整演示**。中文按字切二元组是 CJK 检索的
标准做法，不需要分词器；语料规模在百条量级，BM25 足够。

**实测效果**（固定查询集回归基线，8 正例 + 4 反例）：

| 查询 | 排第一的文档 | 类型 |
|---|---|---|
| 处理器档位是什么意思 | 常见问题 | 服务级 |
| 笔记本多重适合带出门 | 笔记本选购指南 | 品类级 |
| 手机拍照怎么选 | 手机选购指南 | 品类级 |
| 苹果 iPhone 16 怎么样 | 苹果 iPhone 16 | 商品级 |
| **今天天气怎么样** | **无结果** | — |

**按文档类型加权**：商品级条目系数 0.45（实测校准）。不压一压的话，
商品名里的字面命中会顶掉选购指南——问「笔记本买什么好」会答成某款具体笔记本。

**按品牌加权**：查询点名了商品库中的品牌（「华为怎么样」）时，该品牌的商品条目
额外加权（系数 3.0）；同时点名品类时只作用于该品类——问「华为笔记本」不会把
华为手机顶上来。品牌词短、BM25 天然分低，不加权这类宽问题会被阈值挡掉。

**按品类加权**：查询点名了某个品类时该品类资料额外加权。这条针对语料之间的
**无意字面碰撞**——一篇品类指南里可能提到另一种品类，于是问后一个品类时
它会被词频顶上去。

### 7.4 检索与回答策略

1. 判断问题属于商品参数、选购知识还是消费决策
2. 涉及明确的价格或参数，**先查询数据库**
3. 需要解释概念或了解商品特点，再进行知识检索
4. 将检索内容与用户问题交给大模型，要求**只依据片段**组织回答
5. 片段不足以回答时直接说明，不用常识补全
6. 回答**只在界面上以回答形式呈现**（不展示片段与来源）；有问题请以资料为准再核

> 检索侧有两道取舍：**绝对阈值**判「有没有资料」，**相对截断**（`KNOWLEDGE_RELATIVE_CUT`，0.35）判「准不准」——
> 得分远低于第一名的弱命中会被丢掉，单次最多返回 3 条。实测一名 19.2 分时后面跟着 1.x 的命中，
> 一并喂给模型只会稀释答案。

> 用户问「为什么推荐这款笔记本？」时，系统应当能指出该商品的已记录价格、
> 重量和降噪功能，以及知识库中支持其适用场景的资料，
> 而不是只给出「综合性能优秀」这样的空泛描述。

### 7.5 检索质量基线 ✅

固定查询集写在 `tests/test_knowledge_search.py`，**8 条正例 + 4 条反例**，
每次跑 `pytest` 都会验证。正例不只要求「命中」，还要求**排第一的是正确的那一类**
文档（术语问题→服务级，通用选购→品类级，具体商品→商品级）。

覆盖的四类风险：

| 风险 | 对应的断言 |
|---|---|
| 找不到正确资料 | 8 条正例必须命中 |
| 通用问题被答成具体商品 | 正例限定「排第一的文档类型」 |
| 不相关问题错误引用资料 | 4 条反例必须返回空 |
| 缺少资料时不说明 | 反例覆盖语料外问题 |

**这套基线也是「效果评测」子项目的雏形**——调语料、改系数或阈值之后，
跑一遍就知道是变好了还是变坏了，而不是凭感觉。

## 八、Agent 智能决策 ✅

> **状态：✅ 已实现** —— 变更 `add-agent-orchestration` 交付。
> AI 增强模式下走编排；本地模式与编排失败时走既有的确定性管道。

### 8.1 它补的是哪一块

现有分析链路是确定性管道，步骤顺序写死。它能答「预算 X 用途 Y 推荐哪几件」，
但答不了**需要分步探索的复合问题**：

> 「预算 5000，主要用来编程，帮我看看这几款的续航差别大不大，
> 另外笔记本一般多重适合带出门？」

这句话里同时有商品筛选、参数对比、知识查询三类诉求，且第二步依赖第一步的结果。

**Agent 不是替代品，是补充。** 两条路径并存：

| | 确定性管道 | Agent 编排 |
|---|---|---|
| 适用 | 条件明确的标准选购 | 需要分步探索的复合问题 |
| 何时走 | 本地模式 / AI 不可用 / 编排失败 | AI 增强模式下 |
| 产出 | 评分、排序、可解释报告 | 同上 **+ 执行轨迹** |

### 8.2 四个工具，全部只读

| 工具 | 用途 | 复用的实现 |
|---|---|---|
| `search_products` | 按预算、类别、用途筛选商品 | `recommender` |
| `get_product_detail` | 按商品 ID 取完整信息 | `data_loader` |
| `compare_products` | 横向比较多件商品 | `comparison` |
| `search_knowledge` | 检索选购资料 | `knowledge.search` |

**没有任何能修改数据、写库或对外发起请求的工具。** 「禁止模型执行任意 SQL」
在本项目里的答案比「禁止」更彻底——根本没有能执行 SQL 的工具。

### 8.3 参数校验分两层，且不做模糊纠正

1. **形状层**（pydantic）：类型、必填、取值域
2. **语义层**（工具自己）：品类必须在已知类别内、商品 ID 必须真实存在

模型给错参数时**回灌错误让它重来，不替它猜**。猜测纠正等于替模型圆场，
会掩盖它没按 schema 给值的事实——而那恰恰是「校验在起作用」的可见证据。

### 8.4 执行轨迹：真实调用，不是思考过程

智能分析页展示 AI 的执行过程：每一步的**工具名、模型给的参数、结果摘要、状态**。

被参数校验**拒绝的调用同样入轨迹**，并标成醒目状态。那不是失败展示，
而是校验真的在拦的证据。

> 方案自己点过名：「这块最容易做成看起来像 Agent、实际只是聊天的形式。」
> 应对就是——轨迹里只有真实发生过的调用，没有模型的思考文字。
> 有一条测试专门断言「轨迹条数 == 实际调用次数」，防止以后有人往里塞字数。

### 8.5 受控的循环

- **轮次上限 5**：够覆盖「筛选 → 详情 → 比较 → 查资料 → 作答」这条最长路径，
  同时防住模型陷入循环与单次分析耗时失控
- **失败即降级**：上游出错、超时、超轮次都降级回确定性管道，
  筛选、评分、排序、报告一个不少
- 最终解释仍过 `ai_enhance` 的四道校验链

### 13.2 推荐效果评估 ✅

**已建成**：评测集 [`data/evaluation/cases.json`](data/evaluation/cases.json)（41 条，2.0 版）、
评测脚本 [`scripts/evaluate.py`](scripts/evaluate.py)、报告

> 评测集随数据同步升到 **2.0**：引用旧商品 ID 的用例全部按新数据集重算，

> 版本号升了，**不做跨版本比较**——口径变了，比出来的差值没有意义。

```bash
python scripts/evaluate.py            # 跑一遍，输出报告
python scripts/evaluate.py --only 知识检索
```

**指标分两类，刻意不合成总分**——把人工指标折进一个「综合得分」会让读者以为
那是测量结果，而它其实是主观判断的加权。

| 自动计算（分母写在报告里） | 需人工复核 |
|---|---|
| 需求理解准确率 · 硬性条件满足率 · 检索质量 · 幻觉场景通过率 · 推荐相关性 | 任务完成率 · 证据支持率 |

> ⚠️ **这是自评。** 评测集由本项目自行构造并标注，天然偏向系统已有的能力。
> 它的用途是「在明确定义的口径下达到什么水平」，**不是行业基准**。
> 每条用例的构造依据记录在它的 `origin` 字段里。



> **单元测试回答的是「代码对不对」，不是「推荐准不准」——这两件事需要分开证明。**
> 959 条单元测试之外，另有一份人工标注的评测集负责回答后者（当前 41 条用例）。

评测集按下列口径标注，由人工给出合理的预期条件和评价标准：

| 指标 | 定义 |
|---|---|
| **硬性条件满足率** | 推荐结果中符合全部硬性条件的商品占比 |
| **推荐相关性** | 人工判断商品与用户需求是否相关 |
| **证据支持率** | 推荐理由中能由商品资料或知识库支持的事实占比 |
| **检索质量** | 相关知识能否被检索到，引用是否准确 |
| **任务完成率** | 用户能否通过系统完成预定的选购任务 |

> 先明确分母、统计口径和人工标注方法，再报告实际测得的结果。
> **不要在没有运行测试的情况下预先宣称准确率达到 95% 或其他数值。**

### 13.3 抗幻觉设计 ✅

**AI 输出的四道校验**——解读生成后依次检查，任一失败即丢弃该条、保留规则结果：

| # | 检查 | 实现 | 抓的是 |
|---|---|---|---|
| 1 | 价格 | `find_invented_prices()` | 顺口报一个数据里没有的价 |
| 2 | 参数数值 | `find_unsupported_spec_claims()` | 编一个重量、续航或容量 |
| 3 | 排他性结论 | `find_unsupported_claims()` | 「销量第一」「口碑最好」 |
| 4 | 存疑属性 | `find_flagged_claims()` | 就记录内部矛盾的地方下结论 |

**数据侧与展示侧**：

| 防线 | 实现位置 | 机制 |
|---|---|---|
| 记录自相矛盾 | `consistency.check_product()` | 6 条高精度规则，命中标「资料存疑」 |
| 存疑不影响评分 | `Product.data_issues`（派生属性） | 数据质量问题不转嫁成商品劣势 |
| 存疑不排除商品 | `recommender` | 标记只提示核实，照常参与筛选与排序 |
| 排序隔离 | `recommender` + `scoring` | AI 不参与任何计算 |
| 快照存档 | `database` + `report_service` | 报告不含 AI 文字，模型波动不影响历史 |
| 缺失即排除 | `scoring` | 无数据维度不计分并注明原因 |
| 空结果不伪造 | `recommender` | 无匹配时说明并给放宽建议 |

**需要专门测试的幻觉场景**：

| # | 场景 | 状态 |
|---|---|---|
| 1 | 用户询问数据库中不存在的商品 | ✅ |
| 2 | 商品缺少某个参数 | ✅ |
| 3 | 用户预算低于所有候选商品的价格 | ✅ |
| 4 | 知识库检索不到相关资料 | 📋（待 `add-knowledge-base`） |

## 附录 B · 数据说明

**品牌与型号真实存在**，能在网上搜到——但本项目的数据是**按公开资料整理的
参考版本**，不是厂商实时数据，也不代表厂商官方口径：

## 附录 C · 已知限制

**架构方面**

- 当前为 Streamlit 单体，无 HTTP API 层，无法被第三方系统集成
- 存储为 SQLite 本地文件，无并发写入设计，不支持多实例部署
- 无账号体系与多用户隔离，数据保存在本机

**数据方面**

- 20 条商品**按公开资料整理**，不接入任何电商平台，
  不提供实时价格、库存、销量或真实评价
- **来源虽已逐条标注，核验状态仍一律为「未核验」**：20 条全部有 `source_url`。
  字段仍可空——取不到来源时如实留空，不编一个链接顶上。
  **「字段有了」不等于「来源核验过了」**
- 只有 2 个品类、每类 10 条，用户真实需求命中率可能偏低
- 超预算候选最多展示 10 件（`MAX_OVER_BUDGET_SHOWN`）；超出部分不会静默丢弃，
  界面会说明还有多少件未列出
- **效果评测是自评**：评测集由本项目构造并标注，偏向系统已有能力，
  不能当作第三方基准；其中「任务完成率」「证据支持率」两项需人工复核，尚无结论

**功能方面**

- 📋 Agent 工具调用尚未实现，决策步骤顺序固定，不能按需求动态编排
- 中文数字识别**按位书写**（`三千`、`两千五百`），也支持写在货币单位前（`三千元`）；
  口语省略式（`两千五` 表示 2500）**识别不了，会追问**——
  它字面上与「两千零五」只差一个「零」，猜错会给出偏窄的预算并静默筛选，所以宁可不猜
- 需求解析只覆盖预算、类别、用途、核心需求这类高置信字段，拿不准的一律留空
- 商品图片为**外链**，随时可能失效；有图时显示缩略图，缺图或加载失败时回落成
  类别图标，不出现破图。图片不是必填字段，缺图商品照常入库、照常参与筛选评分
- 用户提到表外品类（冰箱、平板、键盘、耳机、沙发……）时，系统只明确回复「不支持」，
  不会给出该类商品的推荐——因为数据里确实没有

**技术方面**

- 深色侧栏依赖 Streamlit 的 `[data-testid="stSidebar"]` 选择器
  （Streamlit 没有官方 API 改侧栏底色）。已锁定版本并加了断言测试，
  升级 Streamlit 把它改坏时测试会失败，而不是悄悄退化成浅色
- `st.pills` 的多选模式可用，单选模式在 Streamlit 的测试框架 `AppTest` 下
  会报错（浏览器里正常），因此「价格取向」使用了 `st.radio`

## 附录 D · 常见问题

**Q：页面报「商品数据文件不存在」怎么办？**

确认 `data/products.json` 存在，且是合法的 JSON。
你也可以用 `ZHIGOU_PRODUCTS_PATH` 环境变量指向别处。

**Q：报「历史记录读取失败」怎么办？**

`storage/zhigou.db` 可能损坏了。历史与收藏功能会不可用，但**分析功能不受影响**。
想恢复的话，删掉这个文件重启应用，会自动新建一个空库。

**Q：填了预算却提示「格式不正确」？**

结构化预算输入框只接受阿拉伯数字（`3000`、`3000 元` 都可以）。
`三千块` 这类中文数字在自然语言输入框里能识别，在数字框里不行，
因为那是你明确填写的字段，格式不对应该提示而不是猜。

**Q：AI 开关点了没反应？**

没配 `ZHIGOU_LLM_API_KEY` 时开关不会出现。
配了密钥后需要重启应用才会生效（环境变量在启动时读取）。

**Q：提示「推理过程用尽了 token 额度」？**

推理模型的推理过程也计入 `max_tokens`。把 `ZHIGOU_LLM_MAX_TOKENS` 调到
4000 或更高再试。这不影响本地演示模式的任何功能。

**Q：端口 8501 被占用？**

```bash
streamlit run app.py --server.port 8502
```

## 附录 G · 账号与权限

### G.1 两种角色

| 角色 | 能做什么 |
|---|---|
| **普通用户** | 使用全部功能页：分析、比较、问答、历史、收藏、个人设置。**只看得到自己的**历史、收藏与偏好 |
| **管理员** | 普通用户的全部能力，外加三个管理页：用户管理、全站概览、商品维护 |

**注册开放，但注册得到的账号一律是普通用户。** 管理员权限只能由管理员授予——
系统里没有「第一个注册的人自动成为管理员」这种规则。

### G.2 初始管理员

首次启动时，账号表为空则自动创建初始管理员：

- 账号密码取自 `ZHIGOU_ADMIN_USERNAME` / `ZHIGOU_ADMIN_PASSWORD`
- 未配置时生成随机密码，**在终端打印一次**，提示立即修改
- 配置的密码太短或用户名不合规时，系统会换成随机密码 / 退回默认账号名，
  并说明原因——**不静默放行**

### G.3 密码怎么存

标准库 `hashlib.pbkdf2_hmac` + 随机盐，存储格式
`pbkdf2_sha256$<迭代次数>$<盐>$<哈希>`，**不开新依赖**。

算法与迭代次数**写在凭据串里**，所以日后调参数不会让已有密码失效——
校验时从串里读，而不是读代码里的常量。实测 60 万次派生约 93 毫秒，
保持在这个量级：慢是它的作用。

界面上永远看不到明文：写入口只收明文、内部派生，所以列里不可能出现明文。

### G.4 数据按用户隔离

历史记录、收藏、个人偏好都归属到具体账号：

- 历史列表只列**本人**的记录；按记录标识读别人的记录会被拒绝
- 同一件商品可以被多个用户分别收藏，互不影响
- 偏好按账号存，一个用户的设置**不会**影响另一个用户的分析结果
- 条件去重也按用户：两个用户提交完全相同的条件**各存一条**

> 单用户时期留下的记录与收藏**标为无归属**，只对管理员可见。系统没有把它们
> 划给任何账号——那样等于编造归属。

### G.5 鉴权边界（**这不是生产级方案**）

本系统的账号体系是**演示级鉴权**，用于展示角色与数据隔离。它**不具备**：

- 没有会话过期机制：登录状态一直有效，直到登出或关闭页面
- 没有登录限流：连续尝试密码不会被拦住
- 没有找回密码：忘了密码只能由管理员重置
- 没有 CSRF 防护
- 刷新浏览器页面后需要重新登录——凭据只存在会话状态里，不写 Cookie、
  不放网址，所以也没法被复制分享出去

所以：**演示时只绑定本机，不要暴露到公网。**

同一份说明在**登录页与项目说明页**都能看到（`src/ui/disclosure.py` 是唯一来源）。

### G.6 管理员维护分类与品牌

商品维护页分**商品 / 分类 / 品牌**三块：

- **商品**：改名称、型号、品牌、图片地址、详情（亮点/不足/适用场景）、参数与价格，
  可上下架。**界面录入的商品一律标为未核验**，并记录录入者——
  是谁填的不等于核实过；改一件既有商品也不会把它的来源说明改写成「界面录入」。
- **分类**：改展示名、排序、启用/停用。**分类的键集合不可增删**——新增一个分类
  要同时配评分权重、参数档位与知识指南，那是改代码与语料的工作量。
- **品牌**：品牌字典**随商品库自动同步**，管理员改展示名、排序与启用状态。
  在字典里登记一个商品库里没有的品牌，**不会**让需求解析认识它——
  解析仍以商品数据为准。

**停用不等于删除。** 停用一个分类或品牌，该分类/品牌下的商品不再出现在搜索与
推荐中，但商品记录一行没动、历史记录里的引用也仍然可读，随时可以恢复。
下架一件商品同理。

### G.7 明确不做的：库存

商品模型里**没有库存字段**，本项目管理端也不提供库存维护。

原因是这个应用做的是**选品推荐**，不做交易与履约。「上下架」已经表达了
「是否在售」；再叠一个数量，就必须定义「上架但缺货」「有货但下架」这类组合
的语义，收益不抵复杂度。若将来确实要做，那是一个独立变更。
