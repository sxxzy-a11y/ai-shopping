## Context

商品数据现在放在 `data/products.json`（105KB，112 条），由 `data_loader.load_catalog()`
读取。SQLite 已经在用（`storage/zhigou.db`），但只存分析历史与收藏。

`load_catalog` 是全项目的**数据入口**——评分、推荐、比较、报告、知识库的商品级
条目、评测脚本，全都经过它。这决定了这次迁移的风险点在哪里。

现有数据的一个事实必须先摆出来：

| 字段 | 现状 |
|---|---|
| `data_source` | 112 条**同一串**：「演示数据 · 本项目自行构造…」 |
| `updated_at` | 112 条**同一天**：2026-10-01 |
| `model` | 不存在 |
| 价格 | 商品表上的一个孤立数值，无来源、无时效 |

也就是说：**这 112 条没有任何真实来源可填**。它们全是本项目自造的。

## Goals / Non-Goals

**Goals:**

1. 商品数据存进 SQLite，成为运行时唯一数据源
2. 补齐型号、逐条来源、核验状态；价格单独成记录并能追溯来源与时间
3. **不破坏开箱即用**：克隆下来直接能跑，不需要前置命令
4. 把改动的影响面压到最小——`load_catalog()` 的签名与返回类型不变

**Non-Goals:**

- **不伪造数据来源**。字段与流程建好，当前数据如实留空并标注未核验
- 不把 `specs` 拆成 EAV 参数表（见 D5）
- 不做爬虫、不做定时同步
- 不引入 ORM（沿用设计基线 D7：手写 SQL + 参数化查询）
- 不改评分、排序、比较、报告的算法

## Decisions

### D1. SQLite 是唯一运行时数据源，JSON 降级为种子数据

**选择**：`products` / `product_prices` 两张表进 `storage/zhigou.db`；
`data/products.json` 不再被运行时读取，只作为**种子数据**在空库时导入一次。

**理由**：两个数据源必然漂移——这正是本项目反复在避免的问题（商品级知识条目
之所以由商品字段合成、不写文件，就是为了这个）。JSON 保留为种子而不是删掉，
是为了保住「克隆下来直接能跑」。

**放弃了什么**：`data/products.json` 不再是「可直接编辑的数据契约」，
改数据要走脚本或 SQL。对比赛演示来说可接受——数据更新本来就有 `ingest` 通道。

### D2. 空库首启动自动导入种子

**选择**：`load_catalog()` 发现库里没有商品记录时，从 `data/products.json` 导入一次。

**理由**：这是**开箱即用**与**单一数据源**之间的唯一可行折中。
没有它，用户克隆后必须先跑一个迁移脚本才能启动——那会破坏项目一直守着的
「streamlit run app.py 就能演示」。

**边界**：
- 只在**库为空**时导入，库里已有数据一律不覆盖（用户的录入永远优先）
- 种子文件不存在且库为空 → 给出明确中文提示，走既有的 `DataFileMissing` 出口
- 导入失败不静默：抛出领域异常，由 `app.py` 在边界处转成中文提示

**放弃了什么**：首启动会比之前慢一点（112 条插入，毫秒级，可忽略）。

### D3. `load_catalog()` 的签名与返回类型**不变**

**选择**：只换内部实现，`Catalog` 与 `Product` 的结构保持兼容；新增字段给默认值。

**理由**：这是把影响面压到最小的关键。`load_catalog` 被评分、推荐、比较、报告、
知识库、评测脚本、以及**几乎所有测试**经过。只要它对外不变，这些调用方一行不用改。

新增字段（`model` / `source_url` / `data_status`）全部**带默认值**，
既有的构造代码（大量测试夹具直接 `Product(id=...)`）照常工作。

**放弃了什么**：`Product` 里会同时存在「从数据库来的字段」与「派生字段」，
结构上不如重新设计干净。但搬迁期保持兼容比结构纯粹更重要。

### D4. 价格单独成表，商品上的价格是派生值

**选择**：`product_prices` 表存价格、币种、来源、采集时间、核验状态、是否当前；
`Product.price` 由**当前有效的那条记录**派生。

**理由**：价格是最需要核实的字段，而它现在是一个无来源、无时效的孤立数值。
单独成表之后：
- 价格能带来源与采集时间（需求直接要求）
- 重新录入变成「新增一条记录并把旧的标为非当前」，历史不丢
- 没有价格记录时 `Product.price` 为 `None`，系统按「信息缺失」处理——
  与既有行为一致（`scoring` 已有「无数据维度排除计算」的处理）

**放弃了什么**：读一条商品要关联一次价格表。112 条的规模下无所谓。

### D5. `specs` / `use_cases` / `pros` / `cons` 保持 JSON 列，不拆 EAV

**选择**：这几项以 JSON 文本存在 `products` 表里，读出时解析。

**理由**：**这次变更是关于「数据在哪、来源是谁」，不是关于「参数怎么规范化」。**
`specs` 的键按品类异构（笔记本有 `cpu_tier`，服饰有 `comfort_tier`），
拆成 EAV 需要三张表加一次重组，而消费方（`scoring`）本来就是按 dict 读的，
拆完还得拼回去——纯粹为了形式上的「规范」，没有任何实际收益。

**如果要按参数做 SQL 级筛选**，那才是该拆的信号。当前筛选在 Python 里做，
且候选集只有百条量级。到时另开变更。

### D6. 型号可空，按名称派生一部分

**选择**：`model` 允许为空。名称里能可靠派生出型号的（约 59 条，主要是电子品类）
派生出来；其余留空。

**理由**：服装、家具、运动、个护、母婴这五类**本来就没有型号概念**——
给一件 T 恤编一个「型号」是造数据。可空字段如实表达「这个信息不存在」，
比填一个占位文本诚实得多。

**派生规则**：品牌名之后、去掉尾部品类词的部分。规则要保守——
拿不准就留空，宁可少派生也不造错。

### D7. 缓存键改用数据库文件的 mtime

**选择**：`state._load_cached` 的缓存键从「JSON 路径 + mtime」改为「数据库路径 + mtime」。

**理由**：数据源变了，缓存键就得跟着变，否则改了库里的数据应用看不到。
沿用同一手法（mtime 进键），行为一致。

**注意**：SQLite 写入后文件 mtime 会更新，所以 `ingest` 写库之后应用仍能自动看到
新数据——与之前「数据刷新免重启」的体验一致。

### D8. 迁移脚本独立于常规导入

**选择**：`scripts/migrate_products.py` 负责把现有 JSON 一次性导入；
`ingest` 的写盘目标改为数据库，但它管的是**后续的数据接入**。

**理由**：两件事的触发时机不同——一个是历史数据搬迁（跑一次），
一个是日常数据更新（反复跑）。混在一起会让 `ingest` 的职责含糊。

**重复执行安全**：迁移脚本按商品 ID 幂等，重复跑只更新不重复插入。

## Risks / Trade-offs

**[改动面大，`load_catalog` 是全项目入口]** → D3 保持签名不变；新增字段全部带默认值。
先跑通「读取路径」，再改「写入路径」，每一步跑全量测试。

**[现有测试夹具大量构造 JSON 文件]** → 提供测试专用的建库助手（临时库 + 写入若干商品），
把夹具迁移成本降到最低。`ZHIGOU_PRODUCTS_PATH` 的含义需要重新界定——
它现在指的是种子文件，测试若仍指它，会走「空库 + 种子」那条路。

**[开箱即用被破坏]** → D2 的自动种子就是为它设计的；写测试覆盖「空库首启」
与「种子文件缺失」两条路径。

**[数据来源字段被误解为「已经有了真实来源」]** → 在 README、数据库文档与
评测报告三处明确写：字段与流程已就绪，**当前数据仍是自造且未核验**。
这条比技术实现更需要盯住——它决定别人怎么理解这个项目的成熟度。

**[价格派生引入新的空值路径]** → `scoring` 已有「无价格则排除预算维度」的处理；
补测试断言「没有价格记录的商品不被当成符合预算」。

## Migration Plan

1. 建表 + 仓储层（`products` / `product_prices`），独立可测
2. 迁移脚本：JSON → SQLite，跑一次并核对条数与字段
3. `load_catalog` 改为读库，**保持签名不变**；跑全量测试
4. 空库自动种子导入 + 相应测试
5. `ingest` 写盘目标改为数据库
6. 界面展示核验状态与来源
7. 文档同步（README 商品数据方案换成那张表并标状态）

**回滚**：`data/products.json` 全程保留不删，`load_catalog` 切回读 JSON 即可回到现状。

## Open Questions

1. **`specs` 要不要拆 EAV**——见 D5，当前不做。若将来需要 SQL 级参数筛选再说。
2. **价格历史要不要展示**——表结构支持，但界面暂时只展示当前价格。
   要展示走势的话是另一个变更。
3. **核验状态怎么流转**——当前只有「已核验 / 未核验」两态，谁在什么时候改，
   没有流程约定。演示项目里由录入者手动设置即可。
