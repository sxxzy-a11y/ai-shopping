## 3. 会话校验（顺带堵上的既有口子）

- [x] 3.1 `accounts.still_valid(user) -> bool`：查库确认账号**仍存在且启用**
      （库读不出来时按「仍然有效」处理：那是「读不到」而不是「账号无效」，
      把所有人踢出去只会让一个只读故障升级成用不了应用）
- [x] 3.2 `app.py`：渲染前校验一次；失效则 `state.sign_out()` +
      提示「你的账号已被停用或删除，请重新登录」+ 回登录页（design D4）
- [x] 3.3 单测：`still_valid` 对「账号不存在 / 已停用 / 正常」三种情形各返回正确结果
- [x] 3.4 界面用例：账号被停用后，其会话下一次交互回到登录页
- [x] 3.5 界面用例：账号被删除后，其会话下一次交互回到登录页
- [x] 3.6 检查开销：校验**每轮渲染只跑一次**，不要塞进 `current_user()` 里
      （后者一次渲染被调用多次）

**这一条改动把测试夹具打红了一轮**（21 条界面用例）：夹具只往 `session_state`
里塞一个用户对象，而库里从来没有那个账号——会话校验正确地把它当成「幽灵账号」
踢了出去。修的是夹具（`_run()` 里先建号），不是守卫。顺带发现那几条
「损坏的库不该让应用停摆」的用例会先把库弄坏再启动，所以夹具里的建号要容错跳过——
否则夹具自己把用例搞挂了。
