## Context

删除的**后端一半已经在了**：`database.delete_analysis()` 写好了、有归属校验、有测试，
但没有任何页面调它。缺的是界面，以及账号删除这件事本身。

而账号删除**被规格禁止**。`add-login-and-user-roles` 当时把它列成 Open Question，
最后选了「只停用不删除」，理由写在 design 里：

> 删除会让历史记录的归属悬空……要么级联删历史（丢用户数据），要么留一堆指向空用户的记录（更乱）。

这次用户明确要求删除，于是那个两难必须正面回答，而不是继续绕。

用户已确认的三点范围：

1. **删除账号 = 级联删除**该账号的历史、收藏与偏好
2. **删除记录 = 硬删**（不做软删/回收站）
3. **禁删自己**，并且顺手补上「每轮渲染校验会话账号」——因为 `require_admin(viewer)`
   只看会话里那个对象的角色，不查库，被停用/被删的账号在它自己刷新之前仍能操作

现有的约束：

| 来源 | 约束 |
|---|---|
| `user-auth`「管理员维护用户」 | 明写「SHALL NOT 能够删除账号」——本变更要改的就是它 |
| 项目原则 | 破坏性操作要让破坏性**可见**，不能悄悄发生 |
| `history-store`「数据最小化与隐私」 | 账号标识只存内部用户名；删除是删自己的数据，不涉新采集 |
| 技术约束 | 零新增依赖；SQLite 维持现状 |

## Goals / Non-Goals

**Goals:**

1. 三个删除入口可用：历史记录页、全站概览、用户管理
2. 删除账号连数据一起清干净，**不留无主记录**
3. 破坏性在动手前就看得见（「将一并删掉 N 条历史与 M 条收藏」）
4. 三条边界真的挡得住：不能删自己、不能删掉最后一个可用管理员、不能删别人的记录
5. 账号一旦失效（停用或删除），其会话**不迟于下一次交互**就失效

**Non-Goals:**

- 不做回收站 / 软删除（用户明确要硬删）
- 不做批量删除
- 不做「删除前把数据转给另一个账号」
- 不改商品与分类的「停用/下架」语义——它们**依然不是删除**

## Decisions

### D1. 级联删除写在一个事务里，用四条 DELETE，不用外键级联

**选择**：`delete_user()` 在一个 `with connection:` 事务里依次删
`analysis_history` → `favorites` → `user_preferences` → `users`。

**理由**：

- 那三张表的 `user_id` **都没有被 `FOREIGN KEY` 约束住**（它们是普通 TEXT 列）。
  要享受 `ON DELETE CASCADE`，得先给它们加上外键约束——而 SQLite 改不了已有表的约束，
  只能重建表。为了让库替我们删，去重建三张表，代价远大于写四条 DELETE
- 一个事务是硬要求：删了历史却没删掉账号（或反过来）会留下**半删状态**——
  账号没了但数据还在，或者数据没了账号还在。这类中间态最难排查

**放弃了什么**：外键约束本来还能防住「手写 SQL 造出悬空 user_id」，我们没用上。
靠的是所有删除都走这一个入口。

### D2. 删除前先统计，把破坏性写在确认处

**选择**：`count_user_data(username)` 返回该账号的历史与收藏条数；确认文案写成
「将一并删除 `demo` 的 3 条历史与 2 条收藏，**不可恢复**」。

**理由**：用户选了硬删，所以这一句就是唯一的「缓冲」。只说「确定删除吗」等于没提醒；
把**具体多少条**摆出来，删的人才知道自己在删什么。这也符合项目一贯立场：
不做没有信息量的免责套话。

### D3. 禁删自己，并复用既有的最后管理员守卫

**选择**：

- `viewer.username == username` → 直接拒绝（界面上自己那一行**不渲染**删除入口）
- 删掉最后一个**可用**管理员 → 复用 `_guard_last_admin()`（停用的管理员不算可用）

**理由**：删掉自己之后，那个会话里的用户对象还在内存里，而守卫只看这个对象——
于是「已被删除的管理员仍能操作」会有一个窗口。D4 虽然堵住了这个窗口，
但**禁止删自己**仍是更简单的一层：自己把自己删掉这个操作本身就没有正当用途，
而它带来的第一个后果是「你立刻被踢出去」，用户会以为系统坏了。

**界面上不给灰按钮**：灰掉会让人以为是权限不够，而实际是「这条规则对谁都一样」。
所以自己那一行直接不渲染入口，并写明原因。

### D4. 每轮渲染校验一次会话账号

**选择**：`accounts.still_valid(user)` 查库确认账号**仍存在且启用**；`app.py` 在渲染前调一次，
失效就 `sign_out()` 回登录页，并提示「你的账号已被停用或删除」。

**理由**：这是本变更顺带堵的一个既有口子。`require_admin(viewer)` 只判断角色，
`current_user()` 只读会话——两者都不查库。所以：

- 停用一个正在使用的账号，它的会话**照样能进管理页**，直到刷新才被拦
- 删除一个账号，问题一样——而删除是这次新增的能力，等于把口子放大了

**位置与开销**：放在 `app.py` 里**每轮渲染调一次**，不是塞进 `current_user()` 里——
后者在一次渲染中被调用很多次，塞进去就是很多次查询。一次本地 SQLite 查询是毫秒级。

**放弃了什么**：如果账号在两次交互之间被删，**下一次交互**才会失效
（这正是 spec 里写「不迟于下一次交互」而不是「立即」的原因）。要做到真正即时，
得引入会话版本号或轮询，那是另一个量级的事，与演示级鉴权的定位不符。

### D5. 二次确认用「勾选确认 + 按钮」，不用模态框

**选择**：删除按钮上方一个 `st.checkbox("我确认删除…")`，未勾选时按钮不生效；
勾选后才真正执行。

**理由**：

- Streamlit 1.51 有 `st.dialog` 模态框，但**在无头测试里不好断言**——
  本项目的界面回归全靠 `AppTest`，选一个测不了的形式等于这块没有回归保护
- 勾选框同样能防手滑，而且它是「让用户明确说出自己在做什么」，
  比「再点一次」更能拦住误操作

**放弃了什么**：模态框更醒目。用**文案**补：确认框的文字里带具体条数（D2）。

### D6. 全站概览里，无归属的遗留记录**也允许删除**

**选择**：管理员在全站概览里可以删掉任何记录，包括那 12 条无归属的遗留记录。

**理由**：它们在界面上只对管理员可见（普通用户永远看不到），除了管理员没人能处理它们。
禁止删除等于让这几条**永久占着位置且无法清理**——而它们恰恰是最没有价值的那些
（不知道是谁做的、什么时候做的）。管理员看得到、又删不掉，是最差的一种组合。

### D7. 规格上怎么写这次推翻

**选择**：把 `user-auth`「管理员维护用户」整条**改写**（MODIFIED），
而不是删掉重写（REMOVED + ADDED）：

- 需求文本里「SHALL NOT 能够删除账号——删除会让已有历史记录失去归属」这一句，
  改成「SHALL 能够删除账号，且 SHALL 一并删除其历史、收藏与偏好」，
  并补「SHALL NOT 删除自己」
- 场景「不能删号」**换成**三个新场景：级联删除、不能删自己、不能删掉最后一个管理员

**理由**：删掉整条再新增会把「停用/启用、改角色、重置密码」那些仍然有效的场景一起洗掉——
这与本项目踩过的坑同源（旧 delta 覆盖了新规格）。MODIFIED 是整体替换，
所以替换文本要**基于线上现文本**逐句改，而不是凭记忆重写。

## Risks / Trade-offs

| 风险 | 处理 |
|---|---|
| 硬删不可恢复，误点即永久丢失 | 二次确认 + 确认文案带具体条数；不做回收站是用户的选择，写进文档 |
| 删除账号把他人的历史一并删掉（该账号自己的记录） | 那是**他自己的**数据，且确认文案报出条数；不做跨账号牵连 |
| 事务中断留下半删状态 | 一个事务，失败整体回滚；补一条「中途失败」的测试 |
| 每轮多一次库查询 | 一次本地 SQLite 查询（毫秒级），且只在已登录路径上跑 |
| 被删账号的用户名可以被重新注册 | **可以，且新账号不会继承旧数据**（数据已级联删除）。这是干净的语义，写进文档 |
| 推翻一条已归档的规格需求 | delta 里写明原因（原先的顾虑是「归属悬空」，本次用级联删除正面回答，而不是绕开） |

## Open Questions

1. **删除记录后，历史里「已经导出过的 Markdown/CSV」怎么办？** 管不了，也不该管——
   导出物一旦离开应用就与它无关了。文档里说明这一点即可。
2. **要不要给删除留审计痕迹？** 本变更不做（项目一贯：不做全站操作流水）。
   若将来需要，那是独立变更。
