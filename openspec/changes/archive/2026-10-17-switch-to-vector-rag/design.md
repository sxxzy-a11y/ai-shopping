## Context

知识库目前是 23 条文档（2 篇手写指南 + FAQ + 20 条商品合成条目），检索用 bigram + BM25，零依赖、离线可用。参考项目展示了 Embedding 检索（切片向量化、模型/维度/状态、相似度检索台），用户要求对齐这一形态并授权解除离线与零依赖约束。

现有可复用设施：

| 设施 | 用途 |
|---|---|
| `src/knowledge/corpus.py` | 文档模型与语料加载（含商品级合成） |
| `src/knowledge/search.py` | `search_knowledge()` 统一入口与 `Passage` 输出 |
| `src/ai_service.py` | httpx 直连 OpenAI 兼容端点的先例：超时、错误翻译、脱敏 |
| `src/ui/state.py` | 索引缓存与检索入口 |
| `app.py` `NavItem(admin_only=True)` | 管理员专属页面的可见性机制 |
| SQLite + `src/database.py` | 本地持久化与错误翻译先例 |

## Goals / Non-Goals

**Goals:**

1. 语义检索可用：换一种说法也能命中知识切片
2. 管理端可见：切片、向量状态、模型/维度、检索调试
3. 索引可增量重建，模型/维度变更能识别过期
4. 服务不可用时回退关键词检索，不阻断问答
5. 现有测试继续全绿；原有 AI 问答行为不回归

**Non-Goals:**

- 不引入 Chroma / LangChain / 独立向量服务
- 不做多轮对话、不做重排模型（rerank）
- 不做知识文档的在线编辑器（语料仍是文件，管理页只读 + 索引操作）
- 不改评分、推荐、报告链路

## Decisions

### D1. Embedding 走 OpenAI 兼容 `/embeddings`，独立配置

**选择**：新增 `ZHIGOU_EMBEDDING_API_KEY` / `_BASE_URL` / `_MODEL` / `_DIM`。示例默认 `https://dashscope.aliyuncs.com/compatible-mode/v1` + `text-embedding-v4` + 1024 维（与参考项目一致），也可指向 SiliconFlow、OpenAI 等兼容服务。

**理由**：DeepSeek（当前对话模型服务商）**没有 embeddings 接口**，不能复用现有模型密钥；OpenAI 兼容协议是事实标准，配置化后不锁定厂商。`_DIM` 用于校验返回向量长度，防止「换了模型但旧向量还在库里」。

**放弃了什么**：开箱即用（需要用户自备 embedding 服务与密钥）。未配置时回退关键词检索，不算不可用。

### D2. 向量存 SQLite，不引入 Chroma

**选择**：`knowledge_vectors` 表存储切片文本、向量（JSON）、模型、维度、内容哈希、状态；检索用 numpy 余弦（`pandas` 已依赖 numpy，显式登记即可）。

**理由**：语料规模百级，暴力余弦毫秒级；少一个外部服务就少一类现场故障（Chroma 的持久化目录、版本兼容、Windows 安装）。「向量库」的本质是存向量 + 近邻检索，这两件事 SQLite + numpy 都做得到。接口（`VectorStore.search`）与 Chroma 对齐，未来可替换。

**放弃了什么**：大规模（十万级以上）检索性能与 ANN 索引。当前与可预见的比赛规模用不上。

### D3. 切片：按 Markdown 标题分段，超长再按段落切

**选择**：切片优先在 `##` 标题处分段；单段超 500 字按空行继续切；切片内容前缀带上文档标题与小节标题（帮助 embedding 理解上下文）。切片 ID 稳定为 `doc_id#序号`。

**理由**：知识文档本身就是按小节写的，按语义边界切比定长滑窗更可解释；带标题前缀显著改善「只说半句话」的切片。

### D4. 索引状态 = 内容哈希 + 模型 + 维度

**选择**：每条切片记录 `content_hash`、`model`、`dim`。生成时三者任一不匹配即重建该切片；检索只使用与当前配置一致的切片。文档删除或切片数减少时清理陈旧行。

**理由**：向量与文本必须同源。只比较内容会漏掉「换模型」；只比较模型会漏掉「改语料」。

### D5. 检索调度：向量优先，失败回退关键词

**选择**：新增 `src/knowledge/retrieval.py` 的 `retrieve()`：

1. Embedding 已配置且存在可用向量 → 语义检索（余弦阈值 + 相对截断 + 条数上限）
2. 否则 / 调用失败 → BM25（现有实现）
3. 返回结果同时带回 `mode`（`vector` / `keyword`），界面如实标注

**理由**：向量服务是最容易挂的一环（配额、网络、密钥）。回退让问答永远有输出，且用户知道当前依据哪条路径。

**取舍**：两种模式的结果可能不一致（这是预期的：一个按语义、一个按字面）。

### D6. 管理页只做「看 + 建索引 + 调检索」

**选择**：知识库管理页包含概览统计、切片表、生成全部向量、检索调试台；**不做**文档编辑器（语料仍是 markdown 文件，走 git）。

**理由**：编辑器的复杂度（校验、版本、权限）与比赛演示价值不成比例；语料在文件里天然可 diff、可回滚。页面核心价值是「让向量化过程可见、可操作、可验证」。

## Risks / Trade-offs

**[Embedding 调用失败或配额不足]** → 管理页显示失败条数与原因；问答侧回退 BM25 并标注。
**[首次生成较慢、按量计费]** → 页面显示待生成数量；支持增量，未变化切片不重复计费。
**[换模型后旧向量被静默使用]** → 检索按当前模型+维度过滤，旧向量显示为「过期」并提示重建。
**[numpy 依赖]** → 已随 pandas 存在，requirements 显式声明并锁下限。
**[用户以为「有向量=一定更准」]** → 检索调试台同时可见分数；固定查询集回归仍保留（向量模式单独一组基线）。
