## Context

应用现在没有「谁」的概念：`analysis_history` 与 `favorites` 都是全局表，
个人偏好存在一个全局的 `storage/settings.json` 里。所有页面直接进，
没有入口拦截。

这个假设已经在数据层留下了会出错的地方（见 proposal 的两张表），
所以本变更不是「加个登录页」那么轻——**它先得把单用户的数据模型改成多用户的**，
登录只是这件事的表层。

现有的约束：

| 来源 | 约束 |
|---|---|
| 项目原则 | **零新增依赖**（streamlit / pandas / pydantic / httpx / pytest，仅此） |
| `history-store` 规格 | 「数据最小化与隐私」明确要求记录**不含用户身份信息**——与本变更直接冲突 |
| 项目原则 | 不得把未核实的数据说成已核实（这条要延伸到「管理员录入的商品」上） |
| 技术栈 | Streamlit 单体应用，没有后端服务层，页面函数即服务端代码 |

用户已确认的范围：

1. 管理员**包含商品库在线编辑**
2. 账号**开放自助注册**
3. 商品维护**包含分类与品牌**，且分类走**轻量**路线——管理元数据，**不**做成可增删的分类表
4. **不做库存**（商品模型里没有这个字段，也不新增）
5. 商品维护要能改**图片与详情**

另有一条来自现有代码的硬约束值得先摆出来：**分类键被 5 处断言钉死了**——

| 断言 | 位置 | 含义 |
|---|---|---|
| 权重表键集合 == 分类键集合 | `test_recommender.py:119` | 新增/删除分类必须同步改权重 |
| 每个分类键都有商品 | `test_acceptance.py:412` | 空分类会让断言失败 |
| 每个分类键都有知识指南 | `test_knowledge_corpus.py:272` | 新增分类要配一篇语料 |
| `DEFAULT_CATEGORY_MAP` 值集合 == 分类键集合 | `test_config.py:190` | 导入别名要与分类同步 |
| 解析器认识的类别 == 分类键集合 | `test_demand_parser.py:277` | 同上 |

**这五条正是「轻量」路线的依据**：分类一旦能随便增删，这五处会同时失效。
所以分类元数据只能是**读取时叠加的一层**，键集合仍由 `config.CATEGORY_LABELS` 定义。

## Goals / Non-Goals

**Goals:**

1. 有登录、有注册、有两种角色，未登录不得进入任何功能页
2. 历史、收藏、个人偏好**按用户隔离**，且修掉签名去重的串号隐患
3. 普通用户**无法**通过任何路径读到他人数据或进入管理员页
4. 管理员能管用户、看全站概览、在界面里维护商品数据——含**分类与品牌**
5. 老库能平滑升级，用户已有的 12 条历史不丢
6. 分类与品牌的元数据维护**不得破坏**上面那 5 条既有断言

**Non-Goals:**

- **不做生产级鉴权**：不做会话过期、登录限流、找回密码、CSRF 防护、邮箱验证、二次验证
- 不做第三方登录（OAuth）
- 不做多租户 / 组织 / 权限细分（只有两种角色，不做细粒度授权）
- **不做库存**：商品模型里没有库存字段，也不新增。本应用是选品推荐、不做交易履约；
  「上下架」已经表达了「是否在售」，叠一个数量字段就要额外定义
  「上架但缺货」「有货但下架」的组合语义，收益不抵复杂度
- **不做自定义分类**：界面不提供新增/删除分类键。允许新增就得同时录入评分权重、
  参数档位与知识指南，否则新分类在推荐与知识问答里是半残的
- **不做品牌别名**（见 Open Question 1：字典先只存规范名与展示名，不做别名映射）
- 不做商品数据的批量导入界面（那仍是 `scripts/fetch_products.py` 的职责）
- 不做操作审计日志（只记录商品录入者，不做全站操作流水）

## Decisions

### D1. 密码用标准库 `pbkdf2_hmac`，并且把参数写进哈希串

**选择**：`hashlib.pbkdf2_hmac("sha256", password, salt, 600_000)`，随机 16 字节盐，
存储格式 `pbkdf2_sha256$600000$<盐hex>$<哈希hex>`。

**理由**：

- 项目一贯零新增依赖。`passlib` / `bcrypt` 都能用，但为了一次登录引入一个依赖不划算，
  而 `pbkdf2_hmac` 是标准库、是 NIST 认可的算法
- **参数写进哈希串**是关键：将来嫌慢想降迭代次数，老密码仍能验证——
  校验时从串里读参数，而不是读一个全局常量。参数写死在代码里的话，
  调参就等于让所有人的密码失效

**放弃了什么**：迭代 60 万次意味着每次登录约 0.2–0.4 秒。这是刻意的成本——
慢正是它的作用。若实测在演示机上超过 0.5 秒，降到 20 万并在哈希串里如实记录。

### D2. 会话只放在 `st.session_state`，刷新即需重新登录

**选择**：不用 cookie，不用 URL 令牌。登录成功后在 `st.session_state` 里记当前用户；
刷新页面就回到登录页。

**理由**：

- Streamlit 没有官方 cookie API。要「刷新不掉登录」只有两条路：
  引第三方组件（违反零依赖），或者把令牌放进 URL query param——
  后者会让凭据出现在浏览器历史、代理日志和用户能随手复制粘贴的地址栏里，
  用**可分享的凭据**换一点便利，方向反了
- 演示场景里，刷新后重新登录是可以接受的代价

**放弃了什么**：刷新体验。这一点必须写进「演示级鉴权边界」文档——
它正是「演示级」的具体含义之一，不能只写一句「仅供演示」含糊过去。

### D3. 权限判定必须在数据层入口再判一次，界面隐藏不算权限

**选择**：`src/auth.py` 提供 `require_admin(user)` 之类的守卫，所有管理员操作
**在真正读写的那个函数入口**再检查一次；侧边栏按角色隐藏入口只是锦上添花。

**理由**：在 Streamlit 里「隐藏按钮」根本不构成权限——
页面函数之间会互相调用，`st.session_state` 也能被脚本改写。
只隐藏入口的系统，只要有人手动跳转页面函数就能越权。守卫放在数据层入口，
「能不能做这件事」就只有一处判断。

这条直接对应测试里的「越权访问」用例：普通用户不得进入管理员页、不得读到他人记录。

### D4. 历史去重加上用户维度，并顺手修掉串号

**选择**：

- 唯一索引从 `(signature)` 改为 `(user_id, signature)`，仍用部分索引
  （`WHERE signature IS NOT NULL AND user_id IS NOT NULL`）
- 去重查询加上 `AND user_id = ?`

**理由**：这是本变更最要紧的一处修复。现状下李四提交与张三相同的条件，
`save_analysis` 会把张三的记录 ID 返回给李四，**不报错、不崩溃，
只是把别人的报告当成自己的给出去**。

**顺带得到一个好性质**：SQLite 的 UNIQUE 索引把 NULL 视为互不相等，
所以遗留记录（`user_id` 为 NULL）既不会互相冲突，也不会挡住新用户的同名签名。
去重查询带上 `user_id` 之后也自然查不到它们——遗留记录就此退出去重体系，
这正是想要的。

### D5. `favorites` 主键改 `(user_id, product_id)`，用「建新表→搬→改名」迁移

**选择**：SQLite 不支持 `ALTER TABLE` 改主键，所以迁移是三步：
建 `favorites_new` → `INSERT INTO favorites_new SELECT ...` → `DROP` 原表 → `RENAME`。

**理由**：当前库里 `favorites` 是空的（实测），所以这次搬迁没有行要保。
但迁移代码**仍要按有行的情形写**——别人的机器上可能有收藏，
而「我这里没有」不是可以少写一段迁移的理由。

**遗留收藏的归属**：如果有行，`user_id` 置空，仅管理员可见。
与历史记录的处理一致——**不编造归属**。

### D6. 个人偏好从全局 JSON 迁进数据库，按用户存

**选择**：新增按用户存的偏好记录；`storage/settings.json` 退役。

**理由**：偏好里是「价格优先还是性能优先」「默认关注哪些核心需求」这类东西，
留着全局一份的话，李四的分析会被张三的偏好影响——这已经不是「功能缺失」，
是**一个人的设置作用在另一个人身上**。

**迁移方式**：首次启动时若发现 `settings.json` 存在，
把它作为**所有新用户的初始偏好模板**写入，然后把文件改名为 `settings.json.bak`。
不把它「归给初始管理员」——那份偏好是单用户时期那个使用者设的，
我们不知道是谁，编个归属不如让它成为默认值，既不丢数据也不撒谎。

### D7. 管理员录入的商品一律标为未核验，并记下是谁录的

**选择**：界面新增的商品 `data_status` 固定为 `unverified`，
`data_source` 自动填「管理员界面录入 · 未核验」，
并在商品表上记录 `entered_by` / `entered_at`。

**理由**：这是项目一贯立场在多用户下的延伸——**「是谁填的」不等于「核实过」**。
管理员能录入，不代表他逐条对照过来源。界面上要显式提示这一点，
免得录入者默认自己填的数据会被标成可信。

**价格的修改走既有的价格记录机制**：改价会新增一条 `product_prices` 记录、
旧记录标记为非当前。这是既有设计顺带给的好处——管理员改价不会抹掉价格历史。

### D8. 注册开放，但只能注册普通用户

**选择**：注册页任何人都能用，注册得到的账号角色固定为普通用户，
角色字段不接受客户端输入。用户名唯一、密码长度至少 8 位。不要邮箱字段。

**理由**：

- 管理员权限只能由管理员授予。**绝不允许「第一个注册的人自动成为管理员」**——
  那等于把管理员挂在谁手快上
- 不要邮箱是因为不做邮箱验证：收集一个永远不验证的邮箱，只是白拿用户信息，
  与「数据最小化」的原则冲突

**初始管理员**：用户表为空时自动创建，取自 `ZHIGOU_ADMIN_USERNAME` /
`ZHIGOU_ADMIN_PASSWORD`；未配置则生成随机密码并在控制台打印一次。

### D9. 分类元数据是「叠加层」，分类键集合仍然在 `config`

**选择**：新建 `category_meta` 表，主键 `category_key`，字段是
`display_label`（可空，空则用 `config.CATEGORY_LABELS` 的名字）、`sort_order`、
`is_active`、`updated_by`、`updated_at`。读取时：

- **全集**永远是 `config.CATEGORY_LABELS` 的键——界面列分类就是遍历它
- 表里的元数据只做**覆盖**：有行就用行的展示名与排序，没行就用默认
- 表里出现 `config` 不认识的键，**忽略并记一条警告**，不把它当新分类

**理由**：

- 新增一个分类不是「填个名字」：要配评分权重（`SCORING_WEIGHTS`）、参数档位
  （`_SPEC_RANGES` 等一整套）、还要写一篇知识指南。这是**代码 + 语料**的工作量，
  做成界面按钮只会让系统进入「配置不完整」的状态——那时推荐会缺权重、问答会缺资料，
  而且不报错，只是结果变差
- 反过来，展示名、排序、启停是纯运营数据，改它们**不触碰任何一条断言**。
  把这两类东西分开，是这个设计唯一重要的一点

**放弃了什么**：管理员不能自己加品类，只能改既有三类的元数据。这是有意的，
但**必须在界面上写明**——否则管理员会把它当成 bug 反复试。
分类页要直接显示「新增分类需要改配置与语料，请在代码中完成」的提示。

### D10. 停用分类/品牌是**读取时过滤**，不是改写商品行

**选择**：停用一个分类或品牌，**不修改任何商品记录**。读取商品的路径
（搜索、推荐、筛选器的候选值）叠加一个条件：该商品的 `category` 与 `brand`
在元数据里都是启用的。恢复 = 把那一行改回启用。

**理由**：改写商品行有三个坏结果：

1. 恢复时无法区分「管理员当初手工下架的」与「因分类停用而被下架的」——
   `is_active` 一个字段会承担两种原因，取关分类时要么误上架、要么漏恢复
2. 元数据操作本该是可逆的，写商品行就把它变成了一次不可逆的数据改写
3. 与既有的上下架功能语义混在一起，以后没人说得清某件商品为什么不可见

**与既有「下架」的关系**：两者**可见性后果相同**（不出现在搜索结果与推荐中，
历史记录里的引用仍可读），但**原因分开存**。可以复用的是同一条「不可见」的判定，
不是同一份状态。

**一处必须小心的实现细节**：这个过滤**不得进入 `Catalog` 的类别推导
（`present_categories`）**。`test_acceptance.py:412` 断言
`present_categories() == set(config.CATEGORY_LABELS)`——过滤一旦下沉到那里，
停用一个分类就会直接把这 3 个测试打红。过滤只叠加在**推荐/搜索/筛选候选**这一层，
`Catalog` 照旧如实反映数据里有什么。

**放弃了什么**：同一条「商品是否可见」的规则存在两个来源（商品自身的上下架状态、
分类与品牌的启用状态）。代价是判定要合在两处做；换来的是两者能各自回退、
不会互相污染。

### D11. 品牌字典随商品**自动同步**，且不反向约束需求解析

**选择**：`brand_meta` 表，主键 `brand_name`（与商品里的写法完全一致），
字段 `display_name`、`sort_order`、`is_active`、`entered_by`、`entered_at`。
同步规则：应用启动时与每次商品写入后，把商品库中出现的品牌 upsert 进字典——
已存在则**只保留其元数据不动**，不存在则补一行启用的。

商品录入时：品牌候选来自字典中启用的品牌；校验要求品牌能在字典中找到——
而自动 upsert 保证既有商品永远合法，不会出现「老数据通不过新校验」。

**理由**：

- `Catalog.brands` 现在是从商品推导的，注释里写得很清楚：
  「**不靠硬编码品牌清单**，数据文件里加了新品牌，解析器就自动认识」
  （`data_loader.py:187-193`）。这是一条既有性质，**本变更不得把它换成读字典**
- 若字典成为解析的品牌来源，就要求字典永远与商品同步——漏同步一次，
  商品的品牌就解析不出来了。让**商品仍是事实来源**、字典只管元数据与候选集，
  两边就不会打架：字典少了会自动补，字典多了不会改变商品的解析结果
- 品牌停用走 D10 的同一条派生过滤

**放弃了什么**：

- 不能靠字典「隐藏」数据里存在的品牌——停用只是可见性过滤，不是删除
- 在字典里登记一个商品里没有的品牌，**不会**让解析器认识它。界面上要说明这一点，
  免得管理员登记完发现「分析里还是识别不出这个品牌」

### D12. 「详情」用既有字段承载，**不新增 `description`**

**选择**：商品维护页的「详情」= 名称、型号、亮点（`pros`）、不足（`cons`）、
适用场景（`use_cases`）；参数另由 `specs` 承担。**不新增自由文本的描述字段**。

**理由**：

- 加一个 `description` 等于把结构化的 pros / cons 用自然语言再抄一遍。
  两份说法迟早不一致，而**不一致时无法判断哪份是对的**——项目一贯反对同一事实存两处
- 新增字段要牵动 `data_loader` 的 `REQUIRED_FIELDS` 与 `missing_fields`、
  `ingest` 的字段别名与校验、`product_store` 的读写、商品卡片与比较表的渲染——
  五处，全都为了一个「把已有内容再写一遍」的字段
- 商品卡片与比较表现在已经把这些字段拼成了「详情」。缺的**不是字段，是可编辑**

**放弃了什么**：没有一段可以自由散文的商品介绍。若将来确实需要
（比如要放一段营销文案），应当作为独立变更讨论，并在那时明确它与 pros/cons 的分工，
而不是顺手塞进本变更。

## Risks / Trade-offs

| 风险 | 处理 |
|---|---|
| 刷新即掉登录，演示时尴尬 | 接受，并写进「演示级鉴权边界」文档——它正是「演示级」的具体含义 |
| 无 CSRF / 无限流 / 开放注册，暴露到公网等于敞开 | 文档明确要求**只绑定本机地址**进行演示；`README` 与部署说明两处都写 |
| pbkdf2 60 万次在演示机上太慢 | 实测一次登录耗时；超过 0.5 秒就降到 20 万，哈希串里如实记录参数，老密码不受影响 |
| 老库迁移改表失败，把用户历史弄丢 | 迁移前复制 `.bak`；迁移在单个事务里完成；失败则不写库、按只读降级并给中文提示 |
| 管理员编辑商品把数据改坏（档位越界、字段矛盾） | 写入前复用既有的 `ingest.validate_products` 与 `consistency` 检查，不合格不放行 |
| 只隐藏入口导致越权 | 见 D3：判定放在数据层入口，并补越权测试 |
| 删除用户会让历史记录的归属悬空 | 管理员**只能停用、不能删除**用户（这也是 Open Question 之一） |
| 管理员把「停用分类」当成「删除分类」，找不到恢复入口 | 分类页显式列出停用项与「恢复」操作，文案写明：停用 = 不再出现在推荐与筛选里，**数据没有删** |
| 元数据表里出现 `config` 已不认识的分类键（如以后某类被下线） | 读取时忽略该行并记警告；补一条测试：表里有陌生键不影响分类列表 |
| 品牌字典与商品库跑偏（字典缺已有品牌，导致编辑商品时选不到） | 启动与每次商品写入后自动 upsert（D11）；补测试：造一件带新品牌的商品，断言字典自动补齐且解析仍认识它 |
| 「详情」被顺手做成一坨自由文本，与 pros/cons 说法打架 | D12 明确不新增 `description`；若确要实现，走独立变更 |

## Migration Plan

启动时按顺序执行，任一步失败即中止并回退：

1. **备份**：`storage/zhigou.db` → `zhigou.db.bak-<日期>`（产品库结构不变，不备份）
2. **建表**：`users`；`analysis_history` 加 `user_id` 列
3. **重建 `favorites`**：建新表 → 搬数据 → 删旧表 → 改名（见 D5）
4. **重建签名索引**：删 `idx_history_signature`，按 `(user_id, signature)` 重建
5. **偏好迁移**：`settings.json` → 默认偏好模板 + 文件改名 `.bak`（见 D6）
6. **初始管理员**：用户表为空则按 D8 创建
7. **建元数据表**：`category_meta` / `brand_meta`（D9、D11）。
   分类元数据**只按 `config.CATEGORY_LABELS` 的键建行**，不为不存在的分类造行
8. **品牌字典首次同步**：把 `products` 里已出现的品牌 upsert 进 `brand_meta`（D11）。
   这一步是幂等的，每次启动都会跑，所以漏做也不会出错

第 7、8 步都只建新表、不碰既有表，失败不会影响前面几步的成果。

**回滚**：把 `.bak` 复制回原名。因为迁移不触碰 `products.db`，商品数据不受影响。
元数据表即使留在库里也无害（应用读不到就走默认行为）。

## Open Questions

1. **管理员能否删除用户？** 建议只停用不删除——删了之后历史记录的归属就没有对象了，
   要么级联删历史（丢用户数据），要么留一堆指向空用户的记录（更乱）。
   倾向「停用」，但这条要确认。
2. **全站分析概览要不要图表？** 建议先只做列表 + 计数，
   图表等有了真实使用数据再加。避免为演示造一个没有信息量的饼图。
3. **演示时是否需要预置几个样例账号？** 自助注册已经够用，
   但如果演示脚本里要展示「两个用户各看各的历史」，预置账号会省事。
4. **品牌要不要支持别名？** 本变更先不做（Non-Goal）：字典只存规范名与展示名。
   若数据里把同一品牌写成「华为」和「HUAWEI」两种写法，字典里就是两个品牌，
   停用其一不会影响另一个。真要合并得引入别名表，那是独立的一件事——
   而且在那之前，更该先统一商品数据里的写法。
5. **停用分类时，知识问答还要不要回答该分类的问题？** 倾向**仍然回答**：
   停用是「不再推荐」，不是「不承认这个品类存在」，而知识语料也还在。
   但这样一来，界面上「支持的品类」会少一类，问答却仍能答，需要看一次实际观感再定。
