## Why

**整个应用现在建立在「只有一个使用者」的假设上。** 历史记录与收藏都是全局共享的，
数据库里没有任何「这是谁做的」的概念。演示时没法体现「不同角色看到不同的东西」，
而这恰恰是很多评审会问的第一个问题。

更要紧的是：这个假设已经在数据层埋了两处隐患，**一加多用户就会立刻暴露**——
它们不是「功能缺失」，是「会出错」。

| 位置 | 现状 | 多用户后会发生什么 |
|---|---|---|
| `favorites` 表 | `product_id` 是主键 | 全站只能有一个人收藏某件商品。第二个人点收藏是**覆盖**第一个人那条 |
| `idx_history_signature` | **全局唯一**索引 + 去重查询 `WHERE signature = ?` | 李四提交与张三完全相同的条件时，`save_analysis` 直接把**张三那条记录的 ID** 返回给李四——李四打开历史，看到的是张三的报告 |

第二条尤其危险：它不报错、不崩溃，只是**悄悄把别人的数据当成自己的给出去**。
这是本变更必须先处理的根因。

## What Changes

- **登录与注册**：未登录时停在登录页；开放**自助注册**，注册得到的账号一律是普通用户，
  角色不可自选。密码用标准库 `hashlib.pbkdf2_hmac` 加盐哈希——**不引入任何新依赖**
- **初始管理员**：用户表为空时自动创建，账号密码取自
  `ZHIGOU_ADMIN_USERNAME` / `ZHIGOU_ADMIN_PASSWORD`；未配置则生成随机密码并
  **在控制台打印一次**，提示立即修改。绝不允许「第一个注册的人自动成为管理员」——
  那等于把管理员权限挂在谁手快上
- **两种角色**：管理员 / 普通用户。角色决定侧边栏可见的页面与可执行的操作
- **历史与收藏按用户隔离**：
  - `analysis_history` 增加归属用户；去重查询与唯一索引一并加上用户维度，
    修掉上面那处串号隐患
  - `favorites` 主键改为 `(user_id, product_id)`
  - 单用户时期遗留的 12 条历史标为**无归属**（`user_id` 为空），仅管理员可见。
    不把它们「划归」给初始管理员——那是编造归属，宁可如实标成遗留数据
- **管理员页面三块**：
  1. **用户管理**：新建、改角色、重置密码、停用
  2. **全站分析概览**：谁在什么时候分析了什么、共多少条
  3. **商品维护页**：分三个分页——**商品**、**分类**、**品牌**（见下）
- **商品维护页 · 商品分页**：新增/修改商品的**信息、价格、图片、详情、参数**，以及上下架。
  其中
  - **信息**：名称、型号、品牌、适用场景
  - **价格**：走既有的价格记录机制，改价新增一条记录、旧价仍可追溯
  - **图片**：图片地址（外链）。写入前校验是 `http(s)` 链接，空白串按「没有图片」处理；
    展示时沿用既有的回落到类别图标
  - **详情**：亮点（pros）、不足（cons）、适用场景（use_cases）。**不为此新增
    `description` 字段**——理由见 design D12
  - **参数**：按该分类的既有参数键与档位填写，写入前复用 `ingest.validate_products`
    与 `consistency` 检查，档位越界或字段自相矛盾一律拒绝
  - **新增的商品一律标为未核验**，并记录「由哪个管理员录入、何时录入」——
    界面维护的数据不因为「是管理员填的」就自动变成已核实
- **商品维护页 · 分类分页**：维护每个分类的**展示名、排序、启用/停用**。
  分类的**键集合不可增删**——评分权重、参数档位、知识指南都绑在键上，
  新增一个分类是代码变更而不是界面操作（见 design D9）
- **商品维护页 · 品牌分页**：维护品牌字典的**展示名、排序、启用/停用**。
  字典随商品库自动同步（商品里出现的品牌必然在字典中），并作为录入商品时的候选与校验集。
  品牌字典**不反过来约束**需求解析——解析仍以商品数据里出现的品牌为准，
  保住既有的「数据里加了新品牌，解析器就自动认识」这条性质（见 design D11）
- **个人设置随用户走**：`storage/settings.json` 那份全局偏好改存数据库、按用户隔离。
  否则李四的分析会被张三的偏好影响
- **不做的**：
  - **不做生产级鉴权**：没有会话过期、没有登录限流、没有找回密码、没有 CSRF 防护、
    没有邮箱验证。文档里一律称为「演示级鉴权」，**不得写成「安全的用户系统」**
  - **不做第三方登录**（OAuth 等）
  - **不做多租户/组织**：只有两种角色
  - **不做库存**：商品模型里没有库存字段，本变更也不新增（用户已明确不要）。
    本应用是**选品推荐**，不做交易与履约；「上下架」已经表达了「是否在售」，
    再叠一个数量就必然要定「上架但缺货」「有货但下架」这类组合的规则，
    收益不抵复杂度。若将来要做，那是一个独立变更
  - **不做自定义分类**：界面上不能新增或删除分类键（见上）。允许新增分类，
    就得同时录入评分权重、参数档位与知识指南，否则新分类在推荐与知识问答里是半残的——
    那已经不是「维护元数据」，而是改配置与语料
  - **不做商品数据的批量导入界面**：那是命令行脚本 `scripts/fetch_products.py` 的事

- **BREAKING**：`history-store` 的「数据最小化与隐私」需求明确写着
  「记录字段……不包含……用户身份信息」。**本变更与它直接冲突**——按用户隔离历史，
  就必然要在记录里存用户身份。该需求需改写为「只存本应用内部的账号标识，
  仍不采集设备标识、地理位置等额外信息」。
- **BREAKING**：开放注册意味着**任何能访问该地址的人都能创建账号并进入**。
  这是产品决定，但必须写进文档：演示环境应只绑定本机地址，不要暴露到公网。

## Capabilities

### New Capabilities

- `user-auth`: 账号与登录本身——用户模型、密码存储与校验、注册、登录/登出、
  两种角色的权限模型、初始管理员引导，以及「未登录不得访问任何功能页」这条边界

### Modified Capabilities

- `history-store`: 分析记录与收藏从全局共享改为**按用户隔离**；去重规则加上用户维度；
  个人偏好从全局文件改为按用户存储；「数据最小化与隐私」需求相应改写
- `product-catalog`: 新增「管理员可在界面维护商品数据」需求——含新增商品的
  溯源标注规则、核验状态默认值、录入者记录，以及可维护的字段范围
  （信息/价格/图片/详情/参数）；新增**分类元数据**与**品牌字典**两块需求——
  两者都是**在既有固定键集合之上叠加元数据**，不含新增/删除分类键的能力
- `web-ui`: 页面构成增加登录页、注册页、管理员页（用户管理 / 全站概览 / 商品维护）；
  未登录时的访问边界；侧边栏按角色显示；商品维护页分为商品 / 分类 / 品牌三块

**代码**

|---|---|
| `src/auth.py`（新） | 用户模型、密码哈希与校验、注册、登录状态、角色判定、初始管理员引导 |
| `src/database.py` | 用户表；历史/收藏/偏好表加用户维度；去重查询与唯一索引加用户维度；老库迁移 |

| `src/catalog_meta.py`（新） | 分类元数据与品牌字典的读写、排序、启停判定，以及对商品可见性的派生过滤（见 design D10） |
| `app.py` | 未登录时短路到登录页；按角色决定侧边栏 |
| `src/ui/pages/*.py` | 取历史/收藏/偏好的地方传入当前用户 |
| `src/settings.py` | 偏好从 JSON 文件改为按用户存库（含一次性迁移） |
| `src/product_store.py` | 供管理员编辑使用的写入入口与校验 |
| `src/config.py` | **不改**——分类键、评分权重、参数档位仍集中在这里。分类元数据是叠加层，不搬走这些（见 design D9） |
| `src/recommender.py` / `src/product_store.py` | 读取商品时叠加「分类与品牌均未停用」的过滤（见 design D10） |

**测试**

现有 83 条 `test_app` 与 16 条 `test_acceptance` 都是直接进应用的，需要补
「已登录」夹具（且要区分管理员/普通用户）；`test_database` 里历史与收藏的用例
需要带上用户维度。另外四类必须有专门的测试：**老库迁移**（单用户库 → 多用户库）、
**越权访问**（普通用户不得进入管理员页、不得读到他人记录）、
**密码存储**（不得明文、同一密码两次哈希结果不同）、
**分类与品牌的固定键不变式**（见下）。

**分类元数据与品牌字典不能破坏的既有不变式**（现有 5 处断言把分类键钉住了，
`tests/test_acceptance.py` / `test_recommender.py` / `test_config.py` /
`test_knowledge_corpus.py`）：

- 权重表的键集合 == 分类键集合（`test_recommender.py:119`）
- 每个分类键都必须有商品（`test_acceptance.py:412`）
- 每个分类键都必须有知识指南（`test_knowledge_corpus.py:272`）
- `ingest.DEFAULT_CATEGORY_MAP` 的值集合 == 分类键集合（`test_config.py:190`）

**这四条在本变更后必须仍然成立**——所以分类元数据只能是**读取时的叠加**，
不能是「分类从 config 搬进数据库」。要补一组测试明确钉住这一点：
**停用一个分类不得改变 `config.CATEGORY_LABELS`，也不得让上述四条断言失败**。
