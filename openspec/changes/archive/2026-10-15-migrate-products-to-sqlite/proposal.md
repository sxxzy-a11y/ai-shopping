## Why

用户给出了一张商品数据的目标形态，它比现状更完整：

| 数据类型 | 存放位置 | 获取方式 |
|---|---|---|
| 商品型号、价格、参数 | SQLite 商品数据库 | 手动核实录入、导入 CSV/JSON |
| 官方产品说明、选购知识 | 本地知识文档及 RAG 索引 | 整理官方公开资料 |
| 数据来源、核实时间 | 商品记录及价格记录 | 录入时一并保存 |
| 推荐评分和筛选条件 | 推荐逻辑及推荐历史 | 程序计算并记录 |

第二行已经做到（`data/knowledge/` + RAG，上一阶段交付）。第四行也做到了
（评分由程序算，条件与结果落 `analysis_history`）。**第一行与第三行没有。**

现状与目标的差距：

| 目标 | 现状 |
|---|---|
| 商品存在**数据库**里 | 商品在 `data/products.json`；SQLite 只存历史与收藏 |
| 记录**型号** | 没有 `model` 字段 |
| 逐条的**数据来源** | `data_source` 112 条同一串，不是逐条来源 |
| **核实时间** | 只有 `updated_at`，112 条同一天，无核实状态 |
| **价格记录** | 没有独立的价格记录：无来源、无时效戳、无历史 |

这直接卡住「创新点二」的展示动作——**「点击推荐依据，可以看到商品参数来源和数据
更新时间」**，而当前 112 条共用一个来源串、共用一天时间戳，点开看不出任何差异。

## What Changes

- **商品数据落到 SQLite，成为运行时唯一数据源**
  - 新增 `products` 表与 `product_prices` 表
  - `data/products.json` 从「运行时数据源」降级为**种子数据**：首次启动空库时导入一次
  - 保住「开箱即用」——克隆下来直接 `streamlit run app.py` 仍能跑，不需要先建库

- **商品记录补齐字段**
  - `model`（型号）：**可空**。名称里能派生出的（约 59 条）派生，其余为空——
    服饰家具这类品类本来就没有型号概念，硬造是编数据
  - `source_url`、`data_status`：逐条来源与核验状态

- **新增价格记录**
  - 每条商品有一条**当前价格记录**，含价格、币种、来源、采集时间、核验状态
  - 商品上的价格变为**从当前记录派生**，不再是一个孤零零的数字

- **README 等文档同步**：商品数据方案一节换上这张表并如实标注状态；
  数据库设计、目录结构、技术栈相应更新

- **不做的**：**不伪造数据来源**。现有 112 条全是本项目自造，
  没有任何真实来源可填——`source_url` 留空、`data_status` 如实标为
  「演示数据 · 未核实」。字段与流程建好，等接入真实数据时自然填上。
  也不做爬虫、不引入 ORM、不改评分与排序逻辑。

## 一个必须说清楚的前提

**加字段不会凭空造出数据来源。** 做完这个变更后：

- 数据库结构支持逐条溯源 ✅
- 导入流程会保存来源与核实时间 ✅
- **但当前这 112 条的来源依然是「本项目自行构造」**，`source_url` 是空的

所以「点开源码看来源」仍然演示不出多来源的差异——除非接入真实数据。
这一条会在 README 与评测报告里如实标注，不因为「字段有了」就说成做到了。

## Capabilities

### New Capabilities

无。本变更不引入新能力，只是把商品数据从文件搬到数据库并补齐溯源字段。

### Modified Capabilities

- `product-catalog`: 新增三条需求——「商品数据持久化在数据库中」、「商品记录的来源与核验状态」、「价格记录」。
  三条都归这里：价格记录也是**商品数据**，不是分析历史，放 `history-store` 是错位。
  既有需求不改——新增字段都可空，不改动 `商品数据结构与必填字段` 的字段清单。

## Impact

**新增文件**

| 路径 | 内容 |
|---|---|
| `scripts/migrate_products.py` | 把现有 JSON 导入 SQLite 的一次性迁移脚本 |
| `tests/test_product_store.py` | 商品仓储层的读写、种子导入、价格记录 |

**修改文件**

| 路径 | 改动 |
|---|---|
| `src/database.py` | 新增 `products` / `product_prices` 表与读写函数 |
| `src/data_loader.py` | `load_catalog` 改从数据库读；Product 增加新字段 |
| `src/ingest.py` | 写盘目标由 JSON 改为数据库；保留字段校验与去重 |
| `src/config.py` | 增加数据库形式的商品数据访问入口 |
| `src/ui/state.py` | 缓存键改用数据库文件 mtime |
| `src/ui/pages/settings.py`、`about.py` | 展示的数据路径改为数据库 |
| `README.md` | 商品数据方案一节换成这张表并标状态；数据库设计、目录结构、技术栈同步 |
| `docs/database.md`、`docs/architecture.md` | 表结构与数据流更新 |

**依赖**

无新增。`sqlite3` 是标准库。

**测试**

- `tests/test_product_store.py`：建表、种子导入、读写、价格记录、去重
- `tests/test_data_loader.py`：改为从数据库读取后的加载与容错
- `tests/test_ingest.py`：写盘目标变化后的校验与合并
- 现有测试大量依赖 `ZHIGOU_PRODUCTS_PATH` 指向 JSON —— 需要一并改为指向数据库

**风险**

- **改动面大**：`load_catalog` 是全项目的数据入口，几乎所有测试都经过它。
  缓解：保持 `load_catalog()` 的签名与返回类型不变，只换实现——
  调用方无感，这是把影响面压到最小的关键。
- **开箱即用的保障可能被破坏**：种子导入若失败，第一次运行就没数据。
  缓解：导入失败时给出明确提示并保留原有错误出口；写测试覆盖「空库首启」。
- **现有测试夹具大量构造 JSON 文件**：它们会一起失效。
  缓解：提供测试专用的建库助手，把夹具迁移成本降到最低。
