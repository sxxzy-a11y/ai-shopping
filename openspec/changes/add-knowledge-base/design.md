## Context

项目当前的决策链路是完整的：需求解析 → 硬性筛选 → 多维评分 → 排序 → 可解释报告。它能回答「**哪件商品更适合你**」，但答不了「**主动降噪和被动降噪有什么区别**」这类问题——后者不需要商品数据，需要的是选购资料。这是知识库要补的位置。

现有约束：

| 来源 | 约束 |
|---|---|
| `requirements.txt` | 运行时依赖只有 5 个：streamlit / pandas / pydantic / httpx / pytest |
| 项目设计基线 D5 | 不引入不必要的依赖，用已装的能力解决问题 |
| 项目设计基线 D6 | 同一能力可做双实现（本地规则 + AI），共用同一输出类型，调用方不区分 |
| 本地演示模式 | **不配密钥、不联网即可完整演示**——这是比赛现场的最大保障 |
| `ai-enhancement` 规格 | 降级路径必须是「告知 + 保留可用功能」，不得崩溃或返回半成品 |

`ai-enhancement` 规格里已有一条「AI 输出不得编造事实」，但 AI 当时没有外部资料可依据。接入知识库后，这条约束需要扩展到「回答只能依据检索到的片段」。

## Goals / Non-Goals

**Goals:**

1. 系统能回答商品知识类问题，并展示来源
2. 保持**零新增依赖**与**离线可用**——RAG 不能变成「没网就演示不了」的功能
3. 检索不到时诚实说明，不返回弱相关结果、不编造来源
4. 明确价格与参数不通过检索回答
5. 为后续 Agent 提供 `search_knowledge` 工具所需的检索接口

**Non-Goals:**

- 不引入 Chroma / LangChain / embedding 接口或任何新依赖
- 不做 PDF / Word / 图片文档的解析，语料只接受纯文本与 Markdown
- 不做多轮对话记忆与追问改写
- 不做文档自动抓取或定时同步
- 不把价格、库存等动态数据放进知识库
- 不改动评分、排序与推荐逻辑

## Decisions

### D1. 中文检索用字符二元组 + BM25，不引入分词器与向量库

**选择**：中文按**字符二元组（bigram）**切分，拉丁字母与数字按整词切分；用 BM25 打分；全部用标准库实现。

**理由**：中文分词需要词典或模型（jieba 等均为新增依赖），而**按字切二元组是 CJK 检索的标准做法**——不需要理解词边界，就能让「降噪」「主动降噪」共享 `降噪` 这个二元组。BM25 是纯算术，几十行可写完。

**已实测验证**（112 条商品合成的商品文档 + 3 份示例知识文档，共 115 条）：

| 查询 | 结果 | 判定 |
|---|---|---|
| 主动降噪和被动降噪有什么区别 | `faq:anc` **61.68**，第二名 22.31 | ✅ 正确且区分度大 |
| 笔记本多重适合带出门 | `category:laptop` 10.32 排第一 | ✅ |
| 编程用什么电脑 | `category:laptop` 排第一 | ✅ |
| 今天天气怎么样 | **无任何结果** | ✅ 语料外问题自然拒绝 |

**放弃了什么**：放弃语义匹配。问「通勤戴的会不会夹头」这种不含「耳机」字样的问法，bigram 检索命中率低。缓解方式是品类级文档在写作时就覆盖口语化问法（「久戴胀耳」「夹头」这类词显式写进指南），把召回问题前移到**语料写作**而不是检索算法。

**备选**：Chroma + embedding——视觉上更贴合 GPT 方案的措辞，但需要新增依赖、需要联网调接口、可能产生费用，且会把 RAG 变成离线不可用的功能。项目现有最大的保障就是「不联网也能完整演示」，不值得为措辞牺牲它。项目设计基线 D6 已有「双实现共用接口」的先例，若将来确实需要向量检索，可在同一接口下替换实现，上层不动。

### D2. 文档类型加权，解决「通用问题答成具体商品」

**选择**：检索得分乘以文档类型系数——品类级与服务级为 1.0，商品级为 **0.55**（初值，据固定查询集调优）。

**理由**：原型暴露了这个问题——查询「通勤戴的耳机怎么选」时，某款具体商品（`product:HP003`，8.62 分）排在了耳机选购指南（3.94 分）之前。原因是商品合成文档里同时出现「通勤」「耳机」「降噪」等多个二元组，命中数天然高于指南。但用户问「怎么选」要的是**方法论**，不是某款商品。

**为什么用静态系数而不是意图识别**：识别「用户问的是通用问题还是具体商品」需要额外的分类逻辑，而静态系数简单、可预测、可调。具体商品名的查询依然会赢——因为商品名本身是强命中，0.55 的系数不足以抵消。

**放弃了什么**：通用问题与具体商品问题的分界不完全精确。用固定查询集建立回归基线来守住这条线。

### D3. 相关度阈值决定「有没有资料」

**选择**：检索最高分低于 `KNOWLEDGE_MIN_SCORE` 时判定为检索不到，返回空结果并说明。

**理由**：不设阈值会把弱相关结果当答案返回，这正是要避免的「拿半个答案冒充答案」。原型里「今天天气怎么样」返回空是因为语料中完全没有 `天气` 这个二元组；但「这款耳机会夹头吗」会命中 `耳机` 得到低分——需要阈值兜住这类情况。

**取舍**：阈值定高了会把「明明有资料」判成找不到，定低了会返回噪声。因此阈值是 `config` 常量，可调，并用固定查询集（正例 + 语料外反例）建立回归基线。

### D4. 商品级知识由商品数据合成，不单独维护文档

**选择**：不写 112 份商品介绍文档。构建索引时，从每件商品的 `name / brand / price / specs / use_cases / pros / cons` 合成一条知识条目。

**理由**：写 112 份独立文档意味着同一事实存两处——改一处忘另一处的失同步几乎必然发生（`harden-ai-enhancement` 变更设计的矛盾检测正是为了抓这类问题）。合成则**只有一个事实来源**，商品数据改了知识库自动跟着变。

**放弃了什么**：合成文本读起来是字段罗列，不如手写介绍自然。对检索而言这影响不大——检索靠的是术语命中，不是行文流畅度。

### D5. 语料用 Markdown + YAML front-matter

**选择**：

```markdown
---
title: 耳机选购指南
type: category
category: headphone
source: 本项目整理
updated_at: 2026-10-15
---

正文……
```

**理由**：Markdown 是人可读、可手写的格式，不需要额外的编辑器；front-matter 承载规格要求的「来源、文档类型、更新时间」元数据。解析器只需处理 `---` 分隔的头部，标准库足够。

**放弃了什么**：没有用 JSON/YAML 存结构化文档——正文是散文，塞进 JSON 会难以书写和维护。

### D6. 本地模式不做生成，只展示原文片段

**选择**：本地演示模式下，问答页直接展示检索到的资料原文与来源，**不生成任何答复文本**。AI 增强模式下才由模型基于片段组织回答。

**理由**：本地模式没有模型可用，任何「回答」都只能是对片段的机械拼接——那不如直接给原文，用户自己读。这也符合项目一贯的诚实立场：**没把握就不替用户写答案**。

**放弃了什么**：本地模式下的体验不如对话式回答自然。但这是可辩护的取舍，且写进规格后成为明确的预期行为。

### D7. 索引在内存中构建，沿用现有缓存模式

**选择**：语料规模约 120 条，启动或首次访问时在内存构建索引；缓存键包含知识语料目录与商品数据文件的修改时间，**改动语料后无需重启**。

**理由**：项目已有一个同类先例——数据集缓存以「路径 + mtime」为键（commit `bd840dc`「数据刷新免重启」）。复用同一模式，行为一致，且无需持久化索引文件（不必处理索引与语料的版本一致性问题）。

**放弃了什么**：每次进程重启都要重建索引。语料规模下耗时在毫秒级，可以忽略。若语料增长到数千条再考虑持久化。

### D8. 价格与参数问题走引导，不走检索

**选择**：问答页对含价格意图（`元`、`价位`、`预算`、`多少钱`、`便宜`）或参数意图的提问，不给检索结论，而是引导到智能分析页。

**理由**：原型里「500 元以内降噪耳机」返回了一款 2499 元的商品——**这不是 bug，是 RAG 的本性**：它按文本相关性找资料，不理解数值约束。用检索结果回答价格问题必然出错。GPT 方案也明确要求「价格和关键参数优先查询 MySQL，RAG 主要负责语义知识检索」。

**放弃了什么**：问答页不能直接回答「X 多少钱」，用户要多点一次跳转。这个不便换来了不会给出错误价格的保证。

### D9. 检索接口按「将来可换实现」设计

**选择**：对外只暴露 `search_knowledge(query, *, limit) -> list[Passage]`，`Passage` 携带正文、来源、类型、更新时间。上层（页面、AI 层、将来的 Agent 工具）只依赖这个接口。

**理由**：项目设计基线 D6 已有先例（需求解析的规则实现与 AI 实现共用同一输出类型）。接口稳定后，若将来要接向量检索，替换实现即可，调用方不动。同时也让 `search_knowledge` 成为 Agent 工具的天然落点。

## Risks / Trade-offs

**[bigram 检索召回不足，口语化提问找不到资料]** → 把召回问题前移到语料写作：品类级指南中显式写入常见口语说法（「夹头」「胀耳」「闷」），而不是只写规范术语。同时用固定查询集做回归，覆盖典型问法。

**[阈值调不好]** → 阈值与文档类型系数都放 `config.py`，可调不需改代码；建立固定查询集回归基线（正例必须命中、语料外反例必须为空）。这套基线也是后续「效果评测」子项目的起点。

**[语料质量决定上限]** → 语料是手写的 10 份品类指南 + 常见问题，质量完全取决于写作。缓解：写作时以「用户会怎么问」为线索组织，而不是按参数表罗列。

**[与 `harden-ai-enhancement` 变更的冲突]** → 两个变更都会改动 `src/ai_enhance.py`（本变更新增「基于片段回答」，另一变更新增断言校验）。二者互不依赖，但**同时实施容易冲突**，建议串行。若本变更先做，另一变更的断言校验需要把检索片段中的数值也纳入允许集。

**[合成文档触发一致性校验误报]** → 商品级合成文档包含价格与规格数值，若 `harden-ai-enhancement` 的矛盾检测扫描到这些合成文本，需要确认不产生误报。合成模板保持与商品字段字面一致即可避免。

**[AI 回答超出片段范围]** → 提示词要求只依据片段，但提示词不是强制约束。本变更先做提示词 + 展示来源（让用户能自行核对）；**强制校验**交给 `harden-ai-enhancement` 的断言校验扩展，两者配合才完整。

## Migration Plan

1. 写语料：先写通用知识（FAQ + 2 个品类指南）验证格式，再补全其余 8 个品类
2. `src/knowledge/` 模块与单元测试，用已有语料验证检索质量
3. 建立固定查询集回归基线（正例 + 语料外反例），据结果调阈值与类型系数
4. 接入 `state.py` 的缓存与 `app.py` 导航，页面用本地模式（只展示片段）先跑通
5. 最后接 AI 模式的回答生成

**回滚**：知识库是纯新增功能，不修改既有链路。移除导航项即可让应用回到当前状态。

## Open Questions

1. **商品级知识条目是否必要**——它对「这款耳机怎么样」有效，但也是 D2 里排序问题的来源。若固定查询集显示它弊大于利，可以只保留品类级与服务级。
2. **语料规模到多少需要考虑持久化索引**——当前 120 条量级内存构建无压力，数千条时需重新评估。
3. **是否需要把知识问答接进智能分析页**——目前独立成页。用户在分析过程中追问知识问题时，跳页会打断流程。本次先独立成页，观察实际使用再定。
