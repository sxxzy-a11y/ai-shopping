# Design

## Context

全新仓库（`C:\Users\suchen\Desktop\ai shopping`），无既有代码。开发机为 Windows 10 + Anaconda Python 3.13.9，已安装 `streamlit 1.51.0`、`pandas 2.3.3`、`pydantic 2.12.4`、`pytest 8.4.2`、`httpx 0.28.1`；**未安装** `anthropic` / `openai` SDK。

约束来自需求方：

- 面向大学生 AI 应用创新竞赛，需要能完整演示、界面达到正式产品水准
- 开发者主要靠 Claude Code 辅助，技术方案要便于初学者维护
- 第一版必须完全基于本地模拟数据，不依赖真实电商平台，也不得伪造实时价格
- 评分类结论必须可解释，且不得暗示为真实市场口碑
- 无 API 密钥时必须完整可用；有密钥时增强而非必需

`openspec/` 已初始化在本仓库根目录，代码目录与规格目录同根，因此项目根即仓库根，不再嵌套 `zhigou-assistant/` 子目录。

## Goals / Non-Goals

**Goals:**

- 把「需求理解 → 筛选 → 评分排序 → 比较 → 报告 → 存档」整条决策链路做通并可在 Windows 本地一键启动
- 业务逻辑与界面彻底分离，核心逻辑可脱离 Streamlit 单独测试
- 无密钥、无网络环境下 pytest 全绿
- 评分权重集中可调，换商品类别不需要改算法代码
- 数据源未来可替换（本地 JSON → 真实商品库）而不触及上层

**Non-Goals:**

- 真实电商数据接入、爬虫、价格监控
- 账号体系、多用户隔离、权限控制
- 交易链路（购物车、下单、支付）
- 微服务、K8s、独立前后端
- 向量检索 / RAG / 模型微调

## Decisions

### D1. 单一 Streamlit 应用 + 分层 `src/` 模块，而非前后端分离

**选择**：`app.py` 只做页面编排与状态管理，全部业务逻辑放在 `src/` 下的独立模块中。

**理由**：需求明确要求第一版优先功能完整与运行稳定；Streamlit 单体省去跨进程通信、CORS、构建链路，Windows 上 `streamlit run app.py` 即可演示。同时把逻辑下沉到 `src/` 后，测试可以直接 import 业务函数，不需要启动 Streamlit。

**放弃了什么**：放弃了前端自由度与未来接真实 API 的天然边界。缓解方式是在 `src/` 内保持模块边界清晰（见 D2），后续若要拆 FastAPI，业务模块可原样搬走。

**备选**：FastAPI + React 前后端分离 —— 视觉上限更高、更接近真实产品，但对第一版的交付风险与维护成本明显更大，且需求方明确说「不需要为了显得技术复杂而强行引入」。

### D2. 按职责切分为 9 个模块，`app.py` 不含业务规则

```
app.py                Streamlit 页面编排、session_state、表单校验反馈
src/config.py         环境变量、常量、路径、评分权重表（唯一权重来源）
src/errors.py         领域异常类型 + 面向用户的中文提示映射
src/data_loader.py    商品 JSON 加载与字段校验
src/demand_parser.py  自然语言 → 结构化需求（规则实现 + 可选 AI 实现）
src/recommender.py    预算过滤、候选编排、排序、放宽建议
src/scoring.py        单商品多维度打分与加分/扣分项提取（纯函数）
src/comparison.py     多商品比较表组装
src/ai_service.py     大模型调用封装（httpx），超时/失败降级
src/database.py       SQLite 读写，历史与收藏
src/report_service.py 报告组装与 Markdown/CSV 导出
```

**理由**：需求方要求「每个模块只承担明确职责，不能将所有业务逻辑写进 app.py」。把**评分**从**推荐**中拆出来（`scoring.py` vs `recommender.py`）是因为评分是纯函数、最需要单元测试，而推荐要处理过滤与排序策略，两者变更频率不同。

**关于需求方建议目录的偏离**：需求方给的布局中 `src/` 无 `scoring.py` 与 `demand_parser.py`、`errors.py`。拆出 `scoring.py` 是让权重集中配置（D4）有落点；`errors.py` 是让「不暴露堆栈」的提示映射有统一出口。其余模块与需求方布局一致。

### D3. 数据模型用 pydantic，但加载层容错优先于严格校验

**选择**：`Product` 用 pydantic 模型描述；加载时逐条校验，单条失败只降级该条并记录，不整批失败。

**理由**：需求要求「缺少商品参数时能够安全处理」，同时 `product-catalog` spec 要求缺字段的商品仍可参与流程并标注信息不完整。若用严格校验整批拒绝，一条坏数据就会让演示全废。因此 `data_loader` 捕获逐条 `ValidationError`，把失败条目变成「信息不完整商品」对象。

**权衡**：代价是加载返回值需要同时表达「商品」与「不完整商品」，增加了一点复杂度。用统一的可选字段模型（必填字段缺失时置 `None` 并挂 `missing_fields` 列表）避免引入第二个类型。

### D4. 评分权重集中在一张表里，按类别分维度

**选择**：`src/config.py` 中定义 `SCORING_WEIGHTS: dict[str, dict[str, float]]`，键为商品类别，值为「维度 → 权重」，同一类别内权重和为 1.0。

**理由**：需求明确「评分权重必须集中配置，不要散落在多个文件中」，且「不同商品类别可以使用不同评分维度和权重」。集中在一处还便于竞赛答辩时展示调参。

**权衡**：新增类别需要在此表补一行；用一个小测试断言「每个类别的权重和等于 1.0」来防止漏配导致评分失真。

### D5. 大模型调用用已装的 `httpx` 直连，不引入 SDK

**选择**：`ai_service.py` 用 `httpx` 向可配置的 `base_url` 发请求，请求体按 OpenAI 兼容的 chat completions 格式构造，模型名与端点均由环境变量控制。

**理由**：本机已有 `httpx`，不新增运行时依赖（符合需求「不要安装大量依赖」）；OpenAI 兼容格式覆盖了绝大多数国内外模型服务的接入方式，包括用户可能自己接的代理。若改用 `openai` / `anthropic` SDK，需要新增依赖且反而锁死了端点兼容性。

**权衡**：失去了 SDK 提供的类型与重试封装，需要自己处理超时与响应解析。缓解方式是把这些都收在 `ai_service.py` 内部，并配单元测试用 stub 响应验证降级路径。

**这是需要确认的决策**：若需求方希望用官方 SDK，此处需改；不影响其他模块。

### D6. 需求解析双实现，共用同一个输出类型

**选择**：`demand_parser` 暴露 `parse(text) -> Demand`。本地模式走正则/关键词规则实现；AI 模式走 `ai_service` 返回 JSON 再映射为同一个 `Demand` 类型。两条路径产出一致，调用方不区分。

**理由**：`demand-parsing` spec 要求「未配置大模型时也能完成解析」且「不发起任何网络请求」。统一输出类型让上层（推荐、报告）完全不感知当前是哪种模式，也让降级变得无感。

**权衡**：规则解析的召回率必然低于模型。缓解方式是规则覆盖面聚焦「预算数字 + 类别关键词 + 用途关键词」这三类高频信息，其余字段留空并由界面控件补齐 —— 这正是 spec 里「缺失字段保留空值」而非猜测填充的要求。

### D7. SQLite 用标准库 `sqlite3`，不用 ORM

**选择**：`database.py` 直接使用标准库 `sqlite3`，手写建表与查询，报告内容以 JSON 文本列存储。

**理由**：表结构只有历史记录与收藏两张，ORM 带来的抽象收益小于其学习成本，且需求方强调初学者可维护。报告整段以 JSON 存储是为了满足 `decision-report` spec「再次打开时还原当时结论」，避免用当前数据重算。

**权衡**：手写 SQL 需要自己防注入（统一用参数化查询）与处理并发写。单机单用户场景下并发压力可忽略。

### D8. 异常统一走 `errors.py` 的中文映射

**选择**：业务层抛领域异常（如 `DataFileMissing`、`InvalidBudget`、`AINotConfigured`、`UpstreamTimeout`），`app.py` 在边界处捕获并查表取中文文案；完整堆栈只写日志。

**理由**：`web-ui` spec 要求「不向普通用户暴露完整堆栈」且所有异常都有友好中文提示。集中映射避免每个页面各写一遍 try/except 文案，也便于测试断言文案。

**权衡**：比裸抛异常多一层间接。用映射表默认值兜底（未登记的异常给通用文案）防止漏配导致白屏。

### D9. Streamlit 样式的克制策略

**选择**：通过 `.streamlit/config.toml` 的 `[theme]` 设置主色、背景、字体，辅以少量自有 class 的 CSS。不使用 `st.markdown` 注入依赖 Streamlit 内部类名的样式。

**理由**：spec 明确要求「不要依赖不稳定的内部 DOM 结构」。Streamlit 1.51 的内部类名（`st-emotion-cache-*`）每次发版都可能变，绑上去等于给升级埋雷。`[theme]` 与自建 class 是官方支持的稳定面。

**权衡**：能改的细节比直接覆盖内部 CSS 少（例如无法精细控制某个原生组件的内边距）。接受这个限制，把视觉重点放在卡片、表格、间距这些自己渲染的内容上。

## Risks / Trade-offs

**[规则解析召回率不足]** → 规则只负责预算、类别、用途三类高置信字段，其余留给界面控件；解析结果在界面上可编辑，用户能手动纠正而不是被动接受。

**[Streamlit 版本升级破坏布局]** → 只用官方 `[theme]` 与自有 class；在 README 中固定并写明验证过的 Streamlit 版本。

**[模拟数据被误读为真实数据]** → 数据文件内每条记录强制带来源与更新时间字段；界面上每条商品卡片、报告、导出文件三处都展示该标注；项目说明页单独说明数据限制。

**[评分被当成市场口碑]** → 评分统一命名「系统匹配评分 / 需求适配评分」；界面上展示评分构成与加扣分项，让用户看见分是怎么来的而非只看到一个数字。

**[Streamlit 重跑机制导致重复写入历史]** → 用 `st.session_state` 记录本次分析是否已落库，重复渲染时跳过写入；对应 `web-ui` spec 中「重复提交不产生重复记录」场景。

**[AI 返回内容不可控]** → AI 只被要求做「解释」与「结构化」两件事，事实性字段一律以本地商品数据为准回填；AI 返回的 JSON 解析失败即丢弃并降级到规则结果，不做尽力解析。

**[Windows 路径与编码]** → 所有文件读写显式指定 `encoding="utf-8"`；路径统一走 `pathlib`；数据文件路径相对项目根解析而非依赖当前工作目录。

## Migration Plan

全新项目，无迁移。交付即可用 `git init` 建仓；`data/products.json` 与 SQLite 文件均在 `.gitignore` 中排除本地实例数据（`products.json` 作为演示数据需要入库，SQLite 文件与 `.env` 不入库）。

## Open Questions

1. **大模型接入方式**：用 `httpx` 直连 OpenAI 兼容端点（D5，零新依赖），还是改用官方 SDK？默认按 D5 实现，等确认。
2. **默认类别范围**：第一版覆盖笔记本 / 手机 / 耳机 / 键盘四类。是否还需要扩充（如平板、显示器）？当前按四类实现。
3. **是否需要多用户**：需求说第一版不要求账号体系，因此按单用户本地库实现。若后续要演示多角色，需新增用户表与数据隔离。
