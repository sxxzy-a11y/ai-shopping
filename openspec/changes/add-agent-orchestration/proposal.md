## Why

GPT 方案「5 项核心内容」里的第 4 项。前三项（结构化商品数据库、AI 需求理解与推荐、RAG 知识库）已交付，这是最后一项功能空白——全仓检索 `tool_call` / `function.call` / `agent` 零命中。

现状的能力边界：现有分析链路是**确定性管道**——需求解析 → 硬性筛选 → 多维评分 → 排序 → 解读，步骤顺序写死在代码里。它能很好地回答「预算是 X、用途是 Y，推荐哪几件」，但答不了**需要分步探索的复合问题**：

> 「预算 5000，主要用来编程，帮我看看这几款的续航差别大不大，另外笔记本一般多重适合带出门？」

这句话里同时有商品筛选、参数对比、知识查询三类诉求，且**第二步依赖第一步的结果**。确定性管道做不了这种编排。

同时，这个变更也是「创新点三」的落点——比赛材料里承诺的「受控工具调用的多步骤 Agent」目前还是空的。

## What Changes

- **扩展 `ai_service` 支持 OpenAI 兼容的 `tools` 参数**
  - 请求体带上 `tools` 声明，解析响应里的 `tool_calls`
  - 用 `httpx` 直传，**不引入 LangGraph 或任何 SDK**（沿用设计基线 D5）

- **新增 `src/agent/` 工具层**
  - 四个工具：`search_products`（复用 `recommender`）· `get_product_detail` · `compare_products`（复用 `comparison`）· `search_knowledge`（复用上一变更的检索层）
  - **每个工具自己声明参数 schema 并做程序化校验**：品类必须在 `CATEGORY_LABELS` 内、预算必须是正数、商品 ID 必须真实存在。模型给的参数一律当**不可信输入**处理——这与 `ai_enhance` 的既有立场一致
  - 工具**只能调用已注册的 Python 函数**，不执行模型生成的 SQL，不接受编造字段

- **新增编排循环**
  - 把用户问题 + 工具声明交给模型，模型决定调哪个工具；执行后把结果回灌，继续下一轮
  - **循环上限 5 轮**，超限即停止并说明
  - 每轮设超时；任一步失败即**降级回现有确定性管道**
  - 全程记录**执行轨迹**：每步的工具名、参数、结果摘要

- **新增界面呈现**
  - 智能分析页在 AI 模式下展示执行轨迹：AI 依次调了什么、依据什么得出结论
  - 轨迹**可追溯**——这是比赛演示的核心看点：「展示一条真实的工具执行记录」

- **不做的**：不引入 LangGraph / LangChain 或任何新依赖；不做多轮对话记忆；不开放任意 SQL 或写操作；不改动现有确定性管道本身（它仍是降级路径与本地模式的形态）；不做自动重试

## 边界：Agent 与现有管道的关系

**Agent 不是替代品，是补充。** 两条路径并存：

| | 确定性管道（现有） | Agent 编排（新增） |
|---|---|---|
| 适用 | 条件明确的标准选购 | 需要分步探索的复合问题 |
| 何时走 | 本地模式；或 AI 不可用；或 Agent 失败 | AI 增强模式下 |
| 结果 | 评分、排序、可解释报告 | 同上 **+ 执行轨迹** |

**关键约束：Agent 的产出仍然受抗幻觉防线约束。** 它调用的四个工具返回的都是结构化数据或知识片段，最终解释仍过 `ai_enhance` 的校验链（价格 → 参数数值 → 排他性结论 → 存疑属性），校验失败照样丢弃。

## Capabilities

### New Capabilities

- `agent-orchestration`: 工具注册与参数校验、编排循环与终止条件、执行轨迹的记录与呈现、失败降级回确定性管道。

### Modified Capabilities

- `ai-enhancement`: 「模型调用封装」需求增加对 `tools` 参数的支持——这是该能力原有的「可替换模型端点」在工具调用场景下的延伸，不改变既有行为。

|---|---|

| `src/agent/tools.py` | 四个工具的定义、参数 schema 与校验 |

| 路径 | 改动 |

**依赖**

无新增。仍为 `streamlit` / `pandas` / `pydantic` / `httpx` / `pytest` 五个。

**测试**

- `tests/test_agent_tools.py`：每个工具的参数校验（合法 / 越界 / 编造字段 / 不存在的商品 ID）
- `tests/test_agent_runner.py`：编排循环、**轮次上限**、工具失败、超时、模型不调工具直接作答
- `tests/test_ai_service.py`：`tools` 请求体构造与 `tool_calls` 解析
- `tests/test_app.py`：轨迹的界面呈现

**风险**

- **模型不按格式调工具**：可能返回不存在的工具名、参数缺字段或类型不对。缓解：分发前统一过参数校验，非法即回灌一条错误说明让模型重试，超过轮次上限就降级。
- **编排消耗更多 token 与时间**：每轮都是一次完整请求。缓解：上限 5 轮且每轮有超时；轨迹里显示实际轮数，让耗时可解释。
- **Agent 看起来「像 Agent」但只是套了个循环**：这是方案自己点名的风险——「最容易做成看起来像 Agent、实际只是聊天的形式」。缓解：轨迹展示真实的工具调用与返回值，而不是只展示模型的思考文字。
- **与既有解读功能的重复**：Agent 已经能组织回答，`explain_recommendations` 是否还需要？取舍是：Agent 负责**编排与工具调用**，最终解读仍走既有校验链，避免两套并行的解释生成逻辑。
