## Context

前三个变更已把「结构化商品数据」「AI 需求理解」「RAG 知识检索」做完，剩下的空白是**编排**：现有链路是确定性管道，步骤顺序写死在代码里，能答「预算 X 用途 Y 推荐哪几件」，但答不了需要分步探索的复合问题。

现有可复用的能力：

| 能力 | 位置 | 在 Agent 里的角色 |
|---|---|---|
| 商品筛选与评分 | `recommender.recommend()` | `search_products` 工具的实现 |
| 多商品比较 | `comparison.compare()` | `compare_products` 工具的实现 |
| 知识检索 | `knowledge.search.search_knowledge()` | `search_knowledge` 工具的实现 |
| 抗幻觉检查链 | `ai_enhance` 的四道校验 | 最终解释仍走它 |
| 模型调用封装 | `ai_service.complete()` | 需扩展支持 `tools` |

约束（`openspec/project.md`）：保持 Streamlit 单体、**零新增运行时依赖**、离线可用是硬约束、抗幻觉主线不可违背（模型输出一律当不可信输入）。

方案自己点名过一个风险，这个设计要正面应对：

> 「这块最容易做成看起来像 Agent、实际只是聊天的形式。」

## Goals / Non-Goals

**Goals:**

1. 模型能自主决定调用哪些工具、按结果继续推进，而不是走固定流程
2. **工具参数全部经过程序化校验**——模型给的东西一律不可信
3. 执行轨迹**可展示、可追溯**，且是真实发生过的调用记录
4. 任何失败都能降级回确定性管道，分析不中断
5. 零新增依赖

**Non-Goals:**

- 不引入 LangGraph / LangChain / 任何 SDK
- 不做多轮对话记忆、不做跨会话上下文
- 不开放任何写操作（改数据、写库、发外部请求）的工具
- 不做自动重试与自我修正循环
- 不改动确定性管道本身——它是降级路径，也是本地模式的形态
- 不追求工具的通用性，只做这个项目用得到的四个

## Decisions

### D1. 工具集固定四个，只读

**选择**：`search_products` / `get_product_detail` / `compare_products` / `search_knowledge`。全部只读。

**理由**：这四个覆盖了「找 → 看 → 比 → 查资料」的完整决策动作，而它们背后都已经有实现好的业务函数。**没有第五个**——工具越多，模型选错的概率越高，而且每多一个就多一处需要校验的入口。

**明确不做写操作**：没有修改商品价格、写入数据库、发起外部请求的工具。方案要求「禁止直接执行模型生成的任意 SQL」——本设计的回答更彻底：**根本没有能执行 SQL 的工具**，模型能碰到的只有这四个 Python 函数。

**放弃了什么**：不能做「帮我把这个商品加进收藏」这类操作。本期不需要。

### D2. 参数校验用 pydantic，与项目既有做法一致

**选择**：每个工具用 pydantic 模型声明参数 schema，校验失败捕获 `ValidationError` 并转成模型能读懂的中文说明回灌。

**理由**：项目已经在用 pydantic（`Demand`、`Product`），校验与错误信息都是现成的。手写 `if not isinstance(...)` 会重复造轮子，而且错误信息不如 pydantic 精确。

**校验分两层**：

1. **形状层**（pydantic 负责）：类型对不对、必填有没有、取值范围
2. **语义层**（工具自己负责）：品类是否在 `CATEGORY_LABELS` 里、商品 ID 是否真在数据集中

第二层必须做——模型完全可能编一个「平板」品类或一个不存在的商品 ID，而 pydantic 拦不住。

**放弃了什么**：没有做参数的模糊纠正（比如把「笔记本」纠正成 `laptop`）。模型应该按 schema 给值；给错了就回灌错误让它重来。**猜测纠正等于替模型圆场**，会掩盖它没按格式调用的事实。

### D3. 编排循环：轮次上限 5，超限即停并说明

**选择**：最多 5 轮「模型请求工具 → 执行 → 回灌结果」。达到上限或模型不再请求工具时结束。

**理由**：5 轮够覆盖「筛选 → 详情 → 比较 → 查资料 → 作答」这条最长路径。上限是为了防两件事：模型陷入循环反复调同一个工具；以及单次分析的 token 与时间失控——每轮都是一次完整的模型请求。

**放弃了什么**：更复杂的任务（比如需要十步探索的）做不了。本期问题域不需要，而且**能做但会跑很久**的功能在比赛现场是负担。

### D4. 轨迹记录真实调用，不记录模型的思考

**选择**：轨迹的每一步是 `{轮次, 工具名, 参数, 结果摘要, 状态}`，`状态` 含「成功 / 被参数校验拒绝 / 执行出错」。**被拒绝的调用同样入轨迹**。

**理由**：这是对方案那句警告的正面回应——「看起来像 Agent、实际只是聊天」的典型表现就是展示一段模型的思考文字冒充执行过程。轨迹里必须只有**真的发生过的调用**：调了什么、传了什么、拿回了什么。

**被拒绝的调用也记录**，因为它恰恰是最有价值的展示内容之一：证明参数校验真的在拦，而不是摆设。答辩时这一条比一条成功调用更有说服力。

**界面呈现**：轨迹只展示工具名、参数与结果摘要，**不展示原始返回的完整 JSON**——那会把界面淹掉，也不是给人看的。

### D5. 降级是**逐级**的，不是全有全无

**选择**：三种情况分别处理——

| 情况 | 处理 |
|---|---|
| 未配密钥 / 开关关闭 | 直接走确定性管道（现状，不变化） |
| 编排中途失败（超时、轮次超限、模型格式错） | 用**已拿到的工具结果**或直接重跑确定性管道，并说明降级 |
| 编排成功但最终解释过不了校验链 | 丢弃解释、保留规则结果（与既有行为一致） |

**理由**：「AI 失败 → 整段分析失败」是最不可接受的形态，而项目已有明确的降级先例（本地演示模式）与校验失败策略（丢弃该条、保留结果）。Agent 沿用同一套立场，不另立规矩。

**放弃了什么**：降级时不做「用部分工具结果拼一个半成品结论」——那正是「返回半成品当成有效结果」，项目明令禁止。

### D6. `ai_service` 扩展 `tools`，仍然 httpx 直传

**选择**：`complete()` 增加可选的 `tools` 参数与 `tool_choice`；响应解析里增加 `tool_calls`。请求体与解析都留在该模块内。

**理由**：设计基线 D5 已确立「用 httpx 直连 OpenAI 兼容格式，不引 SDK」——工具调用是这个格式的一部分，不是引入 SDK 的理由。而且换服务商仍只需改环境变量。

**放弃了什么**：失去 SDK 提供的工具调用类型封装。缓解方式与既有做法一致：把构造与解析收在 `ai_service` 内，用打桩响应做单元测试。

### D7. Agent 与既有解读功能的分工

**选择**：Agent 负责**编排与作答**；`explain_recommendations`（既有的逐条解读）在 Agent 路径下**不再调用**。

**理由**：两者都在生成自然语言解释，同时跑会出现两段口径不同的说明——用户看到两个「为什么推荐」，互相矛盾时就砸了整个可解释性。Agent 的最终回答已经过同一条校验链，够用了。

**放弃了什么**：Agent 路径下没有逐条商品的短解读。这是有意的简化——**宁可少一段，不要两段打架**。

## Risks / Trade-offs

**[模型不按格式调工具]** → 分发前统一过 pydantic + 语义校验；校验失败回灌具体原因让模型重试；超过轮次上限就降级。**不猜测纠正**（见 D2）。

**[编排比确定性管道慢且贵]** → 每轮都是完整请求。上限 5 轮 + 每轮超时；轨迹里显示实际轮数，让耗时可解释而不是「莫名其妙卡了 10 秒」。

**[轨迹可能变成新的「看起来像 Agent」]** → 轨迹只记录真实调用（D4），被拒绝的调用也入轨迹。写测试断言「轨迹条数 == 实际调用次数」，防止有人往里塞模型的思考文字。

**[两套解释逻辑打架]** → 已由 D7 处置：Agent 路径下不调 `explain_recommendations`。

**[工具结果与最终回答不一致]** → 最终回答仍过 `ai_enhance` 的四道校验链。尤其 `find_unsupported_spec_claims`：工具返回的是结构化数据，模型可能在回答里编一个数据里没有的数值，这条链能抓住。

**[Agent 可能被当成「必须有的功能」而影响降级]** → 硬约束写进规格：断网时分析功能完全不受影响。测试断言无密钥时走的是确定性管道且结果与本地模式一致。

## Migration Plan

1. `ai_service` 支持 `tools` + `tool_calls`（独立可测，先做）
2. `src/agent/tools.py` 四个工具 + 参数校验（纯函数，可独立测试）
3. `src/agent/runner.py` 编排循环 + 轨迹（打桩测试）
4. 界面接入：AI 模式下走 Agent，展示轨迹
5. 文档同步与验收

**回滚**：Agent 是新增路径，关掉 AI 开关即回到现状。代码层面移除 `src/agent/` 与 `analysis.py` 的接入点即可。

## Open Questions

1. **轨迹放在分析页还是独立页**——先放分析页（与结果同屏，因果对照最直观），若过长再考虑折叠或独立。
2. **是否允许用户手动选择走不走 Agent**——当前是「AI 开关打开就走」。若实测发现简单问题被 Agent 拖慢，可能需要一个「复合问题才走 Agent」的判断；本期先用开关控制，不做自动判断。
3. **工具结果摘要的长度**——模型需要细节，界面需要简洁。当前是同一份结果分别处理：完整结果回灌给模型，摘要进轨迹。摘要的长度阈值需要实测调整。
