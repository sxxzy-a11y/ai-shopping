## Context

系统已有 696 条单元测试、知识检索的固定查询集回归、六类幻觉场景的测试。
缺的是把它们组织成**一份能回答「这个系统到底好不好用」的东西**——
有分母、有口径、可重复跑、能写进答辩材料的评测。

现有可复用的资产：

| 资产 | 位置 | 在评测里的角色 |
|---|---|---|
| 需求解析 | `demand_parser.parse_demand` | 比对解析出的结构化条件 |
| 筛选与评分 | `recommender.recommend` | 算硬性条件满足率、推荐相关性 |
| 知识检索 | `knowledge.search.search_knowledge` | 算检索质量 |
| 编排 | `agent.runner.run_agent` | 工具调用场景 |
| 幻觉场景定义 | README §13.3 | 六类场景的来源 |

约束（`openspec/project.md`）：零新增运行时依赖、离线可用、
**不声称未实现或未验证的东西**。

本变更最大的设计难点不是技术，是**诚实**：一套由作者标注、用于评价作者所建系统的
评测集，天然带着偏向。设计要做的不是消除它（消除不了），而是**把它摆在明处**。

## Goals / Non-Goals

**Goals:**

1. 一份固定、可重复运行的评测集，覆盖 roadmap 要求的四类场景 + 幻觉六类
2. 一个只走公开入口的评测脚本，输出逐条明细与汇总指标
3. 一份**每个数字旁边就写着口径**的报告
4. 明确区分「自动算的」与「要人判断的」，**不合成总分**

**Non-Goals:**

- 不引入 ragas / promptfoo 等评测框架
- 不做 LLM-as-a-judge——那只是把「谁在评分」换成一个模型，不是消除它
- 不追求指标好看；**跑出什么写什么**
- 不为凑数构造大量雷同用例
- 不测与「消费决策」无关的维度（性能、并发等不在本期）

## Decisions

### D1. 评测集是数据文件，每条带预期与来源标注

**选择**：`data/evaluation/cases.json`，每条包含：

```json
{
  "id": "demand_001",
  "category": "需求理解",          // 场景类别
  "input": "预算 3000 买笔记本，主要编程",
  "origin": "依据系统能力构造",     // 来源说明
  "expected": {
    "demand": {"category": "laptop", "budget_max": 3000, "use_cases": ["编程"]},
    "should_match": ["LP001", "LP003"]   // 或 "should_be_empty": true
  }
}
```

**理由**：数据文件可以逐条 review、可以版本管理、可以被脚本与人工共用。
把预期固化下来，才能算出「命中率」这类有分母的数字。

**`origin` 字段是刻意的**：它会出现在报告里，提醒读者这些用例是怎么来的。
**没有它，读者会默认这是一套中立基准。**

**放弃了什么**：没有用真实用户日志（本项目没有用户），
也没有外部标注（没有标注人力）。这是本期能做到的上限，如实说明即可。

### D2. 脚本只走公开入口，不读内部状态

**选择**：评测脚本只调用 `parse_demand` / `recommend` / `search_knowledge` /
`run_agent`，不 import 内部私有函数、不读 `_` 开头的属性。

**理由**：评测若复用被测代码的中间结果，就会「自己测自己」——
比如用 `scoring` 算出的分数去验证 `scoring` 的正确性。**只走公开入口，
测的才是「用户能看到的那条路径」。**

**代价**：有些细粒度信息拿不到，只能从最终结果反推。接受。

### D3. 自动指标与人工指标分开，不合总分

**选择**：报告分两节。

| 自动计算 | 需人工复核 |
|---|---|
| 需求理解准确率（逐字段比对） | 任务完成率 |
| 硬性条件满足率（价格是否真在预算内） | 证据支持率 |
| 检索质量（正例命中 / 反例为空） | 推荐相关性的存疑部分 |
| 幻觉场景通过率 | |
| 推荐相关性（与预标注集合的重合度） | |

**理由**：把人工指标折进一个「综合得分」会让读者以为那是测量结果，
而它其实是主观判断的加权——**加权系数还会是我定的**。那比不报告更糟。

**人工指标只列明细**，并明确写「尚未有实测结论」，不给近似值冒充结论。

**放弃了什么**：没有一个人人都能引用的单一数字。答辩时得说
「在 X 口径下是 Y，Z 项需人工判断」——比一个漂亮的总分啰嗦，但**它是真的**。

### D4. 幻觉场景用「系统的行为是否符合预期」判定，不判文本质量

**选择**：六类场景各有对应的**可判定行为**：

| 场景 | 判据 |
|---|---|
| 1 询问不存在的商品 | 无匹配结果 + 明确说明，不编造 |
| 2 商品缺某参数 | 该维度被排除计算并注明，不给数值 |
| 3 预算低于所有候选 | 明确说明无匹配 + 放宽建议，不伪造结果 |
| 4 知识库无相关资料 | 检索返回空 + 明确说明 |
| 5 资料自相矛盾 | 商品被标记「资料存疑」且不据其下结论 |
| 6 要求无数据依据的性能结论 | AI 解读中的无依据断言被丢弃 |

**理由**：这六类的共同点是**系统应该拒绝或说明**，而拒绝与否是二值的、可自动判定的。
不需要评判模型生成的文本好不好——那才需要人工或另一个模型。

**注意场景 6 的边界**：它只在 AI 模式且模型确实产生了无依据断言时才被触发。
评测里要构造一个**会产生这种断言的桩**，否则测的是「模型很乖」而不是
「防线在起作用」。这与既有测试的做法一致。

### D5. 报告只写实测值，未测就写未测

**选择**：`docs/eval-report.md` 由脚本生成骨架 + 实测数字，人工补充口径说明。
未执行的项目写「尚未测量」并说明原因。

**理由**：这是项目一贯立场的延伸（「不要在没有运行测试的情况下预先宣称
准确率达到 95%」）。报告一旦出现「目标 95%」这类数字，读者就会记住那个数，
而它不是测出来的。

**放弃了什么**：报告读起来不如「我们的准确率达到 95%」漂亮。但那句话本来就不该说。

## Risks / Trade-offs

**[自评的偏向]** → 用例由作者按系统能力构造，天然偏向系统已经做对的场景。
缓解：`origin` 字段进报告；报告开头声明自评性质；
用例尽量覆盖边界与失败情形而不只挑顺利的。

**[口径被忽略，数字被单独引用]** → 缓解：口径写在数字旁边而非附录（写进规格）。

**[脚本与实现同步腐化]** → 加了新功能但评测集没跟上，覆盖率会悄悄下降。
缓解：`tests/test_evaluation_suite.py` 校验评测集自身的完整性
（场景类别齐全、ID 真实存在、六类幻觉场景都在），缺失时报错而不是静默通过。

**[把评测当成绩单]** → 缓解：报告只呈现口径下的结果，不做跨项目比较，
不写「优于/劣于」这类判断。

## Migration Plan

1. 定评测集格式，先写 5 条跑通脚本（验证格式与调用路径）
2. 补齐到约 40 条，覆盖全部场景类别
3. 跑一遍生成报告，人工补充口径说明
4. 测试与文档同步

**回滚**：纯新增，删掉三个文件即回到现状。

## Open Questions

1. **要不要把评测跑进 CI**——当前无 CI。若将来加，评测可以作为一道关卡；
   但评测里的 AI 相关场景需要桩，CI 里跑桩是可以的。本期不做。
2. **人工指标的复核频率**——任务完成率与证据支持率需要人读，多久复核一次没有定论。
   本期先跑一次并把明细留档。
3. **评测集要不要扩到上百条**——当前约 40 条是 roadmap 的建议区间。
   更多用例的主要收益是统计更稳，边际信息量递减。先按 40 条做。
