## Why

「5 项核心内容」里第 5 项的收尾。可解释推荐早已交付，但**效果评测**一直是空的——
README 明确记着这是「当前最需要补的短板之一」：

> 696 条单元测试回答的是「代码对不对」，不是「推荐准不准」——这两件事需要分开证明。

现状是可验证的：单元测试、固定查询集回归、幻觉场景测试都有。缺的是**把它们组织成
一份能回答「这个系统到底好不好用」的东西**。答辩必问「准确率多少」，
现在拿不出任何有分母、有口径的数字。

这也是「不要声称未实现的功能」这条原则的直接延伸：**没有测量就没有发言权**。

## What Changes

- **新增评测集 `data/evaluation/cases.json`**（约 40 条）
  - 每条含：用户输入、人工标注的预期（品类/预算/用途等结构化条件）、
    预期的推荐商品集合或「应当无结果」、所属场景类别
  - 覆盖roadmap 要求的四类：需求理解正例、预算边界、语料外反例、
    **幻觉场景 1–6 全覆盖**
  - 每条标注**数据来源**：哪些是作者按系统能力构造的，哪些来自真实用户表达

- **新增评测脚本 `scripts/evaluate.py`**
  - 跑完整链路（解析 → 筛选 → 评分 → 排序 → 报告；知识问答；工具调用）
  - 逐条比对预期，输出**明细**与**汇总指标**
  - 支持 `--only <类别>` 只跑一类，`--json` 输出机器可读结果

- **新增评测报告 `docs/eval-report.md`**
  - 每个指标标注：**定义、分母、口径、本次实测值**
  - 区分**自动计算**与**需人工复核**两类指标，不混在一起
  - **不预设任何准确率数字**；未跑就不写

- **明确诚实边界（写进报告与文档）**
  - 评测集是本项目自建的、由作者标注——**这是自评，不是第三方基准**
  - 报告的用途是「证明系统在明确定义的口径下达到什么水平」，
    不是「宣称达到了某个行业指标」

- **不做的**：不引入评测框架（ragas / promptfoo 等）；不做 LLM-as-a-judge
  （那会把「谁在评分」这个问题的答案换成一个模型，而不是消除它）；
  不追求指标好看，**跑出什么写什么**。

## 指标的自动与人工之分

这是本变更最关键的判断。README 十三章定义了五个指标，但它们的可计算性差别很大：

| 指标 | 能否自动算 | 说明 |
|---|---|---|
| **硬性条件满足率** | ✅ 完全自动 | 推荐商品的价格是否真的在预算内，纯数值判断 |
| **检索质量** | ✅ 完全自动 | 正例是否命中预期文档、反例是否返回空 |
| **需求理解准确率** | ✅ 完全自动 | 解析出的结构化条件与标注预期逐字段比对 |
| **幻觉场景通过率** | ✅ 完全自动 | 六类场景是否按预期拒绝/说明 |
| **推荐相关性** | ⚠️ 半自动 | 比对预标注的应推荐集合；集合本身是人工标的 |
| **证据支持率** | ❌ 需人工 | 「理由能否被资料支持」要人读 |
| **任务完成率** | ❌ 需人工 | 「用户能否完成选购」要人judge |

**分两类呈现，不合成一个总分。** 把人工指标折进一个「综合得分」会让读者以为
那是测量结果，而它其实是主观判断的加权——**加权系数还会是我定的**。
那比不报告更糟。

## Capabilities

### New Capabilities

- `evaluation`: 评测集的构成与标注要求、评测脚本的执行与输出、指标的自动/人工分类、
  评测报告的口径披露要求。

### Modified Capabilities

无。本变更只新增评测能力，不改变系统行为。

## Impact

**新增文件**

| 路径 | 内容 |
|---|---|
| `data/evaluation/cases.json` | 评测集（约 40 条，含预期与标注） |
| `scripts/evaluate.py` | 评测脚本：跑链路、比对、出报告 |
| `docs/eval-report.md` | 评测报告（口径 + 实测值） |
| `tests/test_evaluation_suite.py` | 评测集自身的完整性校验 |

**修改文件**

| 路径 | 改动 |
|---|---|
| `README.md` | 十三章「推荐效果评估」由 📋 改为 ✅，接上报告 |
| `docs/testing.md` | 补评测套件一节 |
| `docs/demo_script.md` | 答辩话术补上「准确率多少」的回答 |
| `docs/roadmap.md` | 阶段 4 状态翻转 |

**依赖**

无新增。脚本只用标准库与项目已有模块。

**测试**

- `tests/test_evaluation_suite.py`：评测集**自身**的校验——
  场景类别覆盖齐全、每条预期格式合法、标注的商品 ID 真实存在、
  幻觉场景 1–6 各有至少一条。**评测集错了，报告就是错的**，
  所以它自己也要被测。

**风险**

- **自评的正当性**：评测集由作者标注，天然偏向系统已有的能力。
  缓解是把边界说清楚（写进报告与答辩话术），而不是假装它中立。
- **指标被当成成绩单**：报告里的数字一旦脱离口径就会被误读。
  缓解是每个数字旁边就写分母与口径，不把口径藏在附录。
- **脚本与业务逻辑耦合**：评测脚本若复用被测代码的中间结果，
  就会「自己测自己」。缓解是脚本只调用**公开入口**（`parse_demand`、
  `recommend`、`search_knowledge`、`run_agent`），不读内部状态。
